# sni-flow

每次只处理用户指定的一个上游版本，默认严格依次执行完整六步，包括第五步实施、验证及本地提交，第六步提交后点评。版本号是参数，不能把 286 写成固定目标，也不能自动接着合并下一个版本。创建或修改本技能，只交付技能文件，不启动合并。

## 默认执行与“执行全部”

- 用户调用本技能处理指定版本，即授权按本轮范围完成六步，包含修改代码、验证和本地提交；第五步不再另问实施或提交许可。记录本轮调用及适用范围。用户明确限定“只讨论”“只写文档”或“不提交”时，遵守该限定。
- **默认模式**：常规事项按推荐继续；遇到上游行为与 SNI／本地已修改逻辑冲突、新功能取舍，或无法判断是否影响这些逻辑，保存证据、推荐办法和用户能看到的影响，停止推进，等待用户答复。
- **“执行全部”模式**：只有用户将“执行全部”作为本轮执行指令时启用；引用、举例或否定这句话不算。可以在启动时指定，也可以在暂停后补充。此时冲突和功能取舍由主代理按推荐处理，记录理由并继续六步，不等待逐项回复。该模式仅适用于当前目标，不自动扩展到下一个版本。
- 自动处理优先保留 SNI、本地已改逻辑及长期约定，在这个前提下兼容上游。无法同时保留时，保留本地决定，对冲突的上游部分不照搬，并写明处理、未纳入内容和影响；其他可兼容部分继续。新功能取舍采用符合本轮目标的推荐方案，不借机扩大范围。“执行全部”不代表撤销 ADR、恢复原生客户端或允许创建工作树。
- 默认模式下，用户答复后先更新 Markdown 决定，再从暂停处继续。“同意”仍只确认当前方案并保存文档，本身不新增实施授权；本轮调用已授权六步时，依据已有授权继续。不能把超时、沉默或子代理建议当作用户答复；不能从“同意”推断已切换为“执行全部”。
- 已有长期排除项、本轮已明确决定的同一个问题，以及能在保持双方既定行为前提下解决的文本冲突，直接按已有决定处理。其余冲突和取舍统一服从本节模式，后文不再单独增加等待条件。
- “执行全部”免除冲突和功能取舍的人工等待；遇到缺少目标、工具不可用、无法保护他人已有修改等客观阻塞，先自行排查可行办法，确实无法完成时报告实际停点，不能伪造审查、验证或提交结果。
- 本流程包含本地提交，采用中文提交信息，改动很大时分批提交。推送、标签、发布和部署仍需对应明确指令，不因“执行全部”自动包含。

所有问题、进度、审查、清单和交付报告用 Markdown 和大白话。复杂取舍给一个具体例子。默认模式暂停时说明停在哪一步、需要决定什么；自动处理时记录实际采用的推荐及理由。

## 开始前：固定本轮依据

1. 从当前仓库读取适用的 `AGENTS.md`、`CLAUDE.md`、`CONTEXT.md`（存在时）、`docs/agents/issue-tracker.md`、`docs/agents/triage-labels.md`，以及相关 ADR。确认这是 Forwardx／sni-panel 项目；不匹配时先澄清，不把本项目约定套到别的仓库。
2. 按名称找并完整读取 `/grilling`、`/to-spec`、`/to-tickets`、`/implement` 的真实 `SKILL.md`。先用当前技能目录；缺项时查 `~/.agents/skills/<名称>/SKILL.md` 和 `~/.codex/skills/<名称>/SKILL.md`。这些技能即使未出现在当前目录清单中，也可按用户指定的流程读取执行。仍找不到时报告缺项，停在需要它的步骤，不伪称执行、不擅自安装或替换。
3. 检查 `codex --version`、`codex exec --help`。两次独立审查都必须实际使用 Codex CLI；不可用时保留已完成工作，在审查入口等待恢复。
4. 规范目标，例如 `286` → `v2.3.286`；用户给的完整版本保持不变。没有目标、一次给出多个目标且未定顺序，或短版本有歧义时，先澄清。
5. 读取当前分支、HEAD、远端地址和工作区状态；保留现有未提交内容，不重置、不覆盖、不创建工作树。有进行中的合并／变基，或需改动与他人未提交代码重叠且无法安全区分时，暂停说明。
6. 核实上游目标标签及其实际提交。必要时只抓取指定上游参考；不移动本地已有标签，不自动跟随上游最新分支。记录本地 HEAD、目标标签、目标提交；标签后来移动或用户更换目标，重新核对并更新依据。
7. 从“本地当前代码 → 指定上游目标”核对差异，结合上一轮记录和上游版本间差异解释来源；不能只看两个上游标签的差异。单列已有工作区修改和本地独有文件，本地独有不等于应删除。历史规格不证明相关功能已经实施或验收。
8. 复用该目标已有且与本轮相符的目录；新建时用 `.scratch/YYYY-MM-DD_合并上游vX.Y.Z/`。不同目标分开保存。维护 `编排进度.md`：目标和比较依据、现有修改、六步状态、本轮调用及执行模式、用户决定或自动推荐及证据、待答问题、实施前提交、本轮提交清单、文件链接和下一动作。恢复时先读进度，再核对实际文件、代码与提交，不重复开单或提交，不把旧结论当成本轮完成。

## 每轮必须保留的本地决定

以当前仓库约定和 ADR 原文为准，特别读取并遵守：

- `docs/adr/0006-sni-group-ddns-uses-confirmed-entry-health.md`：SNI 落地检测缺失、过期或失败，不单独阻止入口选择、DDNS 或导致整组切换；仍要求入口在线、当前完整分流配置生效、已开启的国内检测和观察等待。
- `docs/adr/0008-host-failover-groups-use-entry-health.md`：仅主机型主备组（`groupType=host`、`groupMode=failover`）按入口运行与健康选入；保留规则运行、计时延续、当前有效副本及发布前复核等完整条件，不把这一决定扩展到其他类型。
- Android、iOS／iPadOS 原生应用及其专属依赖、版本和发布内容按长期约定排除。`client/` 中的面板网页继续纳入；混合文件按实际用途拆分，不能整目录排除。原生应用不列为待完成事项。
- 其他本地 SNI、计费、安全、权限、品牌、安装来源等改动逐项核对；“上游没有”不能成为删除理由。读取与本轮有关的其他 ADR，不把历史某轮的全部功能取舍机械延续为永久决定。
- `origin` 是上游参考来源；代码、标签、发布仅允许按仓库约定推往 `sni-panel` 的 `main`。执行任何已授权远端操作前核实实际地址。

例如，某个 SNI 域名的落地检测失败，但入口完整分流配置已生效，不能因此照搬上游判断把整个入口排除。若上游新功能确实要求这样处理，默认模式说明冲突并等用户决定；“执行全部”模式保留本地入口判断，记录兼容处理后继续。

## 第一步：用 `/grilling` 收敛本轮合并

从本地代码和已有本轮讨论继续，只讨论指定目标带来的变化、本地兼容办法和本轮验收。不要借机讨论其他版本、原生应用恢复、无关重构或新功能。

按 `/grilling` 梳理决定之间的前后关系并查明事实。用户已预先指定：**不冲突 SNI 和本地逻辑、且不涉及功能取舍的事项，全部采用推荐做法**。把这些推荐及理由记入文档，不逐项提问、不等待形式确认。后续文档和工单的常规推荐同样直接处理，本轮调用已授权六步实施及提交。

默认模式只向用户提出真正的冲突或功能取舍；每项写清本地现状、上游变化、用户影响、推荐办法和依据。按先决条件分轮提问，不提前猜测尚未答复的决定。“执行全部”模式由主代理按推荐完成这些决定并写入文档，不发问等待。任一步后来发现同类问题，都回到执行模式规则。

完成条件：本轮纳入项、兼容项、长期排除项、保留项均有依据；需要的决定已由用户答复或在“执行全部”模式下按推荐落实，没有悬而未决的问题。

## 第二步：用 `/to-spec` 写本地规格

按实际技能整理讨论，不重新采访。遵守本项目本地 Markdown 问题平台：规格保存为本轮 `spec.md`，不用 GitHub／Linear 发单。沿用技能的规格结构，写清本轮比较依据、已定行为、本地保护、范围之外、验收场景和未验证内容。具体提交、文件对照等证据放附录或旁边的证据文件。

采用项目现有的验证入口，优先检查用户可见结果；常规推荐记入规格即可。新验证方式若涉及功能取舍，按本轮执行模式处理。规格不能把已取消的原生应用重新加入，也不能把计划验证写成通过。

完成条件：本地规格完整，范围与第一步一致，验收可观察，实施权限记录准确；无占位内容或悬而未决的功能决定。

## 第三步：让 Codex CLI 独立审查需求

读取 [Codex CLI 审查约定](references/codex-review.md)，按“需求审查”模式启动一个全新、只读的 Codex CLI 子代理。交付本轮规格、本地比较依据、差异证据、用户已定事项、仓库约定及相关 ADR；不要只给主代理的总结。

实际完成一次独立审查后，逐条核对问题。文档漏项、措辞矛盾或已决定事项的遗漏直接补齐；涉及 SNI／本地行为冲突或新功能取舍时，按本轮执行模式等待或采用推荐。无关的扩展建议记为范围之外。问题不成立时保存依据，不为了满足审查而改变已定行为。

保留 `审查/需求审查.md`、运行记录和 `审查/需求审查处理.md`，后者逐项链接修改或不采纳依据。审查结论只针对交给它的版本；重大规格变化须补充针对变更的复核，不无限重跑同样的审查。

完成条件：CLI 成功返回实际报告，发现的问题逐条有处理，未解决的阻塞为零。调用失败、报告缺失、仍有待答问题均不能进入第四步。

## 第四步：用 `/to-tickets` 按推荐拆本地工单

以第三步补齐后的规格为唯一依据。按能独立演示或核对的一小段完整功能拆分，写明真实依赖；只安排本轮需要的准备改造，不新增旁支任务。

用户已授权常规拆分采用推荐粒度，无须再问一遍粗细。按仓库约定逐单保存到本轮 `工单/NN-中文名称.md`，从 `01` 按依赖编号，状态使用项目约定。仓库的 `工单/` 约定优先于技能模板的 `issues/` 默认位置。每单写清交付行为、前置工单、验收和必须保留的本地保护；给出规格与工单对应关系。

完成条件：本轮所有纳入项与验收都有工单承接，没有重复单、循环依赖、无关事项或原生应用待办。开单不表示已经实施或验收。

## 第五步：用 `/implement` 实施、验证并提交

本轮调用已授权实施、验证和本地提交，不另设确认关口。先记录实施前提交和已有修改，再按实际 `/implement` 和工单依赖推进，只处理本轮范围，不创建工作树。

本编排调整 `/implement` 的收尾顺序：先完成第五步实施、验证及提交；其默认的最终 `/code-review` 由第六步全新 Codex CLI 的提交点评承接，不再重复调用另一套审查。

沿用约定的验证方式，按改动运行必要检查并记录真实结果；检查覆盖不足或环境不可用如实写“未验证”。原生应用无需构建、签名或验收。常规实现与范围内修补直接继续；发现冲突或功能取舍，默认模式停下来等用户，“执行全部”模式按推荐处理并更新文档后继续。

实施和必要检查完成后，只提交本轮应交付的改动，不夹带他人已有或无关修改。提交信息使用中文，改动很大时按可理解的功能分批提交。在 `编排进度.md` 保存提交编号、各提交交付内容、验证结果和残留修改说明；不能把提交成功当成验证通过。

完成条件：范围内工单落实，文档与实现一致，必要检查结果及限制有据可查，本轮应交付代码已经提交；残留无关修改有记录，不把未提交的本轮代码算作已交付。随后直接进入第六步点评这些提交。

## 第六步：让 Codex CLI 进行提交点评

按审查约定的“提交点评”模式，启动另一个全新、只读的 Codex CLI 子代理，承接 `/implement` 的最终代码审查。提供实施前提交、本轮完整提交清单、规格、工单、前次审查处理及验证记录，要求检查需求覆盖、本地行为保护、漏合／误合和实际风险。

点评对象是第五步已完成的提交及其最终代码状态。覆盖本轮全部提交，不能只看最后一个提交；若期间存在无关提交，用本轮提交清单界定范围。核对工作区有无遗漏：未提交的本轮代码必须说明并补交后再点评，不能混进已提交代码的结论；无关旧修改按实施前记录排除。

保留 `审查/提交点评.md`、运行记录和逐项处理结果。范围内明确缺陷直接修复、运行相应检查，并另做中文后续提交，不重写已有提交；新的取舍或冲突按本轮执行模式处理。修补提交形成后，补充对受影响部分的独立复核，记录实际覆盖的提交编号，不沿用修补前的结论宣布修补后已通过。

完成条件：提交点评实际完成，阻塞问题已有修复或按执行模式明确处置，最终提交、文档和点评一致；无法检查的内容明确列出。最终给出本轮范围、实施结果、提交清单、两次审查及处理链接、实际验证、剩余限制和下一动作。本地提交、检查通过、推送、部署与人工验收分别按实际证据说明；不用 Stop、提交成功或子代理通过代替用户验收。

## 调用示例

- `$sni-flow 合并上游 286`：默认执行六步，包括实施、本地提交和提交点评；遇到冲突或功能取舍才等待用户。
- `$sni-flow 合并上游 287，执行全部`：按推荐处理本轮冲突及功能取舍，不等待逐项答复，连续完成六步。
- 已在本轮因冲突暂停，用户回复 `执行全部`：记录模式变更，按推荐处理当前问题并继续剩余步骤。
- `$sni-flow 继续 .scratch/2026-10-20_合并上游v2.3.288/`：核对记录、代码与提交，从未完成处按该轮已记录的模式恢复；不重复开单或提交。
