## 本单修正

1. **晚到旧报告会虚增当前时段的覆盖。** 先保存累计 600 次，再收到晚到的累计 300 次，不能把旧报告当作新观察。面板现将每一路探测的最新进度持久保存，更新进度和记录新增次数在同一事务完成。重复、倒退、已关闭周期和成功次数差额不合法的报告不入账。面板重新连接数据库及并发投递也保留此保护。失败与通过证据见 [旧报告复现](late-snapshot-red.log)、[修正验证](late-snapshot-green.log)。
2. **面板已经收到的健康尾批会在 Agent 重启后漏算。** 两轴审查发现：面板收到成功 3 次、累计成功 6 次，第二份被降频省略，随后新周期失败 3 次，旧实现只能算 6 次、失败率 50%。现保存每份已收到且累计次数前进的报告，健康曲线仍按原规则减少记录；实际公开报告路由与统计接口验证结果为 9 次、成功 6 次、失败率 33.33%。数据库重连、旧周期晚到和重投不改变该结果；后续大累计值为 3006 次、成功 3003 次。见 [失败复现](received-tail-red.log)、[通过验证](received-tail-green.log)。面板会为这些有效累计报告增加持久记录，避免收到后又丢失。
3. **旧延迟抽样会影响新稳定性评分。** 旧延迟 2000 ms 曾把新准确统计的评分拉到 55。现在旧曲线及延迟卡片继续保留，评分仅使用有效累计报告对应的真实延迟批次，同例为 100。原稳定性算法继续使用；低失败率区间的原有插值仍可能四舍五入为 100。见 [失败复现](legacy-score-red.log)、[通过验证](score-green.log)。
4. **准确计数与延迟样本的上限分开处理。** 总次数及成功数汇总全部有效新增记录；评分用的成功延迟样本最多保留最近 2880 个有效报告批次，并明确返回及显示裁剪提示。3000 个批次的 9000 次探测完整保留，只有延迟样本裁剪为 2880 个批次。
5. **周期、升级和旧 Agent 兼容补齐。** Agent 在随机周期身份外增加可排序的周期起始时间，同一进程内递增；首次看到某周期只计当前批次，不补算未观察到的历史。准确统计要求报告实际携带完整字段，不因旧本地 Agent 3.2.0 数字较大就认为支持。旧累计字段的原有延迟处理保持可用。三种数据库的新字段可空，旧行不会凭升级默认值变成准确统计；新增进度表已纳入结构同步、迁移名单与归属 ID 映射。
6. **中英文表达同一口径。** TCP 连接失败、Ping 丢包、逐跳失败及旧记录不可用提示均有对应英文；动态窗口标题中的探测方法也会翻译。

887 份开工文件副本的哈希全部一致，本单修改 14 份已有文件，新增真实 Agent 验证脚本 `scripts/verify-probe-agent-counters.mjs`。准确差异见 [06 代码差异](06代码差异.diff)，文件清单和产物哈希见 [环境与产物](环境与产物.json)。原有上游集成及 01–05 的修正未被覆盖。

累计数据只能覆盖有效报告观察到的进度。首次报告前的历史不会补算；Agent 未上报便结束的尾批不能凭空恢复；时间段边界受报告间隔影响。面板已收到的有效进度则会保存，避免因面板降频漏算。延迟样本的上限不会裁剪累计次数与失败率。
