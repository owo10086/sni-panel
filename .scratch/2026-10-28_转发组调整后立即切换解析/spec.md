# 转发组调整后立即切换解析

**Status:** completed

**Decision date:** 2026-10-28

**决策：** 见 [ADR-0010](../../docs/adr/0010-host-failover-group-edits-switch-without-recovery-wait.md)。主机型转发组中，管理员调整引起的规则重新下发不触发恢复观察；移除或停用当前入口时先接后断。

## Problem Statement

管理员调整主机型转发组后，组域名要等好几分钟才指向新的当前入口，期间流量中断。

2026-10-28 线上转发组 33「入口-tj2直接转发」（`tj2.diaonima.com`，48 条普通规则，恢复时间 120 秒，自动回切关闭）。管理员移除当前入口美国9929（主机 17，`68.166.252.58`），只留新加坡lin（主机 12，`172.237.72.159`）。实测时间线（UTC）：

| 时间 | 事件 |
| --- | --- |
| 04:28:54 | 保存编辑；面板向主机 17 下发三批撤销动作（04:28:58、04:29:26、04:30:35） |
| 04:30:34 | 没有合格成员，保留解析 `68.166.252.58` |
| 04:30:44 | 向主机 12 下发 49 个动作；04:30:47 成员 87 的规则全部报运行 |
| 04:32:46 | 恢复观察满 120 秒后切换解析到 `172.237.72.159` |

主机 17 上该组规则最后一条流量记录为 04:28:30，主机 12 从 04:33 起才有该组流量。两台入口约 4.5 分钟都没有该组流量。

等待由两段组成：

1. **先断后接。** 编辑先撤销旧入口的转发，再给剩余成员部署，约 1 分 50 秒。这段时间解析仍保留旧入口的地址，而旧入口已经不再转发。
2. **调整被当成故障。** 剩余成员的规则重新下发，期间短暂未运行，被当作故障，要等满 120 秒恢复观察。

新建组、增删规则、调整顺序也会遇到第二段等待：新规则副本一出现就被记为"出过故障"。

## Solution

主机型转发组（`groupType=host`、`groupMode=failover`）中：

- **管理员调整不是故障。** 调整引起的重新下发，只要规则重新运行（SNI 组为当前完整分流配置重新确认），成员就直接合格，不等恢复观察，组域名随即切换到应选的入口。
- **真实故障照旧。** Agent 离线、重启、重连，确认过期，入口明确上报失败，仍按组的故障时间与恢复观察处理。
- **运行确认门槛照旧。** 规则未运行、SNI 分流配置未确认的成员仍不合格。不会为了"立即"把解析发布到没有准备好的入口。
- **移除或停用当前入口时先接后断。** 原入口继续转发，直到下一个成员合格、解析切换并经过一个 DDNS TTL 后才撤销。下一个成员 5 分钟内仍未合格时，照常撤销原入口。
- **其他移除照常。** 移除非当前成员、移除唯一成员时，与现有行为一致，立即撤销。
- **手动排序保留接管意图。** 新首选成员暂未准备好时保留本次排序目标；它取得资格后接管，即使自动回切关闭也一样。真实故障后的恢复观察仍不能跳过。
- **可用性目标。** 避免先撤销旧入口造成的新连接空窗，并覆盖约定 TTL 内仍使用旧解析的新连接；不承诺迁移已有连接或在撤销旧入口后继续保留其长连接。5 分钟仍未切换时的强制撤销是明确接受的兜底例外。

## User Stories

1. As a 面板管理员, I want 移除当前入口后组域名一经剩余成员确认运行就切过去, so that 不必等满恢复时间。
2. As a 面板管理员, I want 移除当前入口时原入口在解析切走前继续转发, so that 不因提前撤销造成新连接空窗。
3. As a 面板管理员, I want 原入口在解析切换后再过一个 DDNS TTL 才撤销, so that 仍按旧解析缓存连过来的客户端还能接通。
4. As a 面板管理员, I want 停用当前入口与移除当前入口同样先接后断, so that 停用也不会因提前撤销造成新连接空窗。
5. As a 面板管理员, I want 下一个成员 5 分钟内仍未合格时原入口照常撤销, so that 被移除的主机不会无限期保留转发。
6. As a 面板管理员, I want 剩余成员需要重新下发时，规则重新运行后立即切换, so that 等待只有下发和运行确认那几秒。
7. As a 面板管理员, I want 保存编辑后先给剩余成员下发规则，不排在撤销原入口之后, so that 新入口尽早准备好。
8. As a 面板管理员, I want 新建组后首个合格成员的规则一运行就发布解析, so that 新域名不必额外等恢复时间。
9. As a 面板管理员, I want 往组里增加规则后保留当前解析，新规则运行后当前入口立即重新合格, so that 新规则的首次下发不会额外触发恢复观察。
10. As a 面板管理员, I want 修改组内规则后成员重新运行即合格, so that 改目标或端口不会拖慢后续的切换与回切。
11. As a 面板管理员, I want 删除组内规则不让成员进入恢复观察, so that 清理规则不影响入口资格。
12. As a 面板管理员, I want 调整成员顺序后新的首选成员取得资格就接管，暂未就绪时保留本次接管意图, so that 自动回切关闭也不会丢失我的手动排序要求。
13. As a 面板管理员, I want 修改组域名后立即发布到新域名, so that 新域名不等恢复观察。
14. As a 面板管理员, I want 增加备用成员后，它规则运行即可作为合格备选, so that 当前入口故障时有现成的接管者。
15. As a 面板管理员, I want 调整后规则在组的故障时间内都没有运行时按真实故障处理, so that 下发失败的入口不会被当成已准备好。
16. As a 面板管理员, I want 入口明确上报规则应用失败时仍按故障处理, so that 管理员调整不会掩盖入口真正的问题。
17. As a 面板管理员, I want Agent 离线后恢复的入口仍须等满恢复时间才能被选为当前入口或回切, so that 真实故障后的防抖保护不变。
18. As a 面板管理员, I want Agent 重启或重连后的入口仍须重新确认并完成恢复观察, so that 刚恢复的入口不会立即承接流量。
19. As a 面板管理员, I want SNI 分流确认过期仍按故障处理, so that 失去确认的入口不会因调整被放行。
20. As a 面板管理员, I want 调整前已经在恢复观察中的成员继续按原有时间等待, so that 调整不能被用来跳过真实故障后的恢复观察。
21. As a 面板管理员, I want SNI 组调整后仍须确认当前完整分流配置才合格, so that ADR-0006 的完整配置要求不被削弱。
22. As a 面板管理员, I want SNI 组调整确认后不等恢复时间, so that SNI 组也能立即切换解析。
23. As a 面板管理员, I want 没有合格成员时保留原入口的解析，而原入口此时仍在转发, so that 保留的解析是可用的。
24. As a 面板管理员, I want 新入口的 DDNS 发布失败时原入口不被撤销, so that 解析仍指向的入口继续可用，直到 5 分钟兜底。
25. As a 面板管理员, I want 面板在先接后断期间重启后接着按原时间完成撤销, so that 重启不会让原入口永久保留，也不会提前撤销。
26. As a 面板管理员, I want 移除非当前成员时立即撤销它的转发, so that 与现有行为一致。
27. As a 面板管理员, I want 移除组里唯一成员时立即撤销, so that 没有接管者时行为与现在一致。
28. As a 面板管理员, I want 组没有域名或 DDNS 未开启时移除当前入口立即撤销, so that 没有切换解析这个时间点可等时行为与现在一致。
29. As a 面板管理员, I want 删除或停用整个组时立即撤销全部转发, so that 整组下线不受先接后断影响。
30. As a 面板管理员, I want 待撤销期间把同一主机加回组里时立即撤销旧副本再按新成员部署, so that 同一主机上不会出现同端口冲突。
31. As a 面板管理员, I want 待撤销的原入口不出现在成员列表、不参与选入口, so that 界面和选择都只反映我保存的配置。
32. As a 面板管理员, I want 手动"同步"和整组启停的行为保持不变, so that 本次改动只影响我同意的那几类调整。
33. As a 面板管理员, I want 入口组、出口组、转发链、端口转发资源、隧道型主备组保持原有行为, so that 改动不扩大到其他组类型。
34. As a 业务用户, I want 管理员调整入口时新连接在交接和约定的旧解析缓存期内仍有入口承接, so that 不因先断后接而无法建立连接；超过撤销期限仍留在旧入口的长连接不在本次保证内。
35. As a 后续合并上游的维护者, I want 管理员调整与真实故障的区分有明确的场景测试, so that 上游改动健康判断时能发现是否破坏了本决定。

## Implementation Decisions

**成员健康窗口（恢复观察判断）**

- 每个成员的每个观察项（Agent、SNI 分流、每条普通规则副本、国内检测）各有窗口。现在任一项未运行都会记为"出过故障"，新出现的观察项在成员已被观察过时也直接继承"出过故障"。
- 新增"管理员调整"来源。仅本次实际需要部署或重新确认的观察项可进入调整等待，不记故障；调整后新出现的规则副本观察项从未故障开始。其他观察项照常判断，不能因为同组刚发生编辑而统一豁免。
- 调整引起的等待在组的故障时间（failoverSeconds）内恢复，直接合格。达到故障时间仍未恢复，按真实故障记，并从本次持续等待的最早起点累计故障时间，不再额外等一轮故障时间；之后恢复时照常走恢复观察。不新增设置项。
- 调整不清除已有的故障记录：调整前已在故障或恢复观察中的观察项保持原状。
- Agent 观察项、国内检测观察项、确认边界失效（离线、重启、重连）、确认过期、入口明确上报失败（规则带运行诊断，或分流应用失败回执）不受调整影响。
- 面板重启后窗口本来就会重建，仍沿用现有的保守规则。ADR-0008 中"故障等待在面板重启后接着计算"的持久化故障起点，只记录真实故障，不记录调整引起的等待。

**调整标记**

- 在管理员操作入口记录本次变更涉及的组、成员、根规则／副本，以及期望配置内容或版本、等待起点和截止时间。组级时间只用于索引，不能单独用作调整归因的证据。标记只存内存；面板重启后标记丢失，退回现有保守行为，即需要恢复观察。
- 标记与成功保存的配置绑定，并在相关下发及健康评估前可见；保存回滚不得留下可用的调整标记。对新建成员或副本，保存后将其实际身份关联到本次变更。
- 覆盖的操作：新建组；编辑组（增删成员、停用成员、调整顺序、改域名）；拖动排序；组内规则的增、改、删。
- 覆盖操作不代表豁免整组：只为实际变化导致的规则首次部署、重新部署或 SNI 完整配置重新确认建立等待。仅改组域名、名称或顺序而未改变运行配置时，不给已有规则建立新的调整等待；如果保存确实同时改变了继承配置，则只覆盖实际受影响的观察项。
- 调整前已有的真实故障和恢复约束不得因标记更新或副本身份变化而被清除；故障计时仍遵守 ADR-0008 的同一规则、同一当前副本边界，不借用其他副本的时间。
- 连续编辑不能延长同一观察项尚未完成的调整等待：期望配置可以更新，等待起点和截止时间保留最早一轮。新增加且此前无等待的观察项各自计时；已有等待超时或出现明确失败后，后续编辑也不能清掉真实故障记录。
- 普通规则仍沿用既有运行报告判断，不新增 SNI 等级的完整配置确认协议；调整归因使用面板本次实际部署的差异。普通规则重新运行、或 SNI 当前期望配置完整确认时，立即结束该项调整等待。随后与该次变更无关的未运行，按真实故障处理；SNI 旧配置的延迟报告不能完成新配置确认，旧调整标记也不能替后续故障重新取得豁免。
- 标记不能放在组规则同步流程内部，因为每轮故障转移巡检也会调用同步。
- 手动"同步"、整组启停不打标记，行为不变。

**SNI 运行观察的中断原因**

- SNI 运行观察现在只记录中断时间。改为同时记录原因和相关配置身份：
  - 面板下发内容变化或路由数量变化：必须与本次实际变更的成员、规则及期望配置相符，并且等待未超时，才可归入调整。只有时间接近或路由数量不同不足以证明来自本次调整；无关规则丢失仍是真实故障。
  - 确认边界失效、确认过期、分流应用失败回执，以及无法归因于本次配置变更的中断：始终是真实故障。它们与调整同时发生时，真实故障及其恢复约束优先，不能被后续配置变化覆盖。

**手动排序后的接管**

- 编辑组显式改变成员优先级顺序、或拖动成员排序时，将新顺序中的首个启用成员记为本次手动接管目标。仅增加备用成员、改域名或增改删规则，不产生这项意图。
- 目标已经合格时按现有手动排序行为立即选入；目标暂未合格时保留当前解析，继续准备目标。当前入口发生真实故障时仍可按既有主备规则选择其他合格成员，不为等待排序目标阻止故障转移。
- 后续维护任务继续尝试本次目标；目标满足在线、运行确认、已开启的国内检测、流量政策及必要恢复观察后即可接管，不受自动回切开关限制。这是完成一次手动排序，完成后继续遵守原自动回切设置。
- 手动接管意图持久化保存目标成员和本次排序身份。面板重启后继续等待，但重新建立健康证据，不能沿用丢失的调整豁免跳过恢复观察。
- 只有目标成为当前入口且本次解析发布有效提交后，才算完成并清除意图；系统 DDNS 未启用时按现有选入口提交行为完成。DDNS 失败或过期响应不消耗意图。后续显式排序覆盖旧意图；目标被移除或停用、整组删除或停用、组类型或模式改变时取消。

**先接后断（成员替换与停用）**

- 触发条件：被移除或停用的是当前入口，组里还有其他启用成员，组配置了域名，并且 DDNS 已开启。
- 保存时：成员记录照常删除或停用；原入口的规则副本保持运行，记为"待撤销"。
- 持久化：每批待撤销状态包含组与原成员／主机、保留的规则副本、原解析身份（服务商、域名、记录类型和原值）、开始时间、5 分钟兜底截止时间，以及首次有效切换成功时间、TTL 快照和最终撤销截止时间。需要一次表结构增补，SQLite、MySQL 与 PostgreSQL 都要支持，覆盖全新建库与已有数据库升级；面板重启后据此继续。
- 组规则同步清理过期副本时跳过待撤销副本。待撤销副本不参与成员健康评估、选入口、成员列表和成员数量限制。
- 保存后立即给剩余成员下发规则，不排在撤销原入口之后。
- 选入口：当前入口被移除或停用后立即视为没有当前入口，选下一个合格成员，不等故障时间。暂时没有合格成员时保留原解析，这是现有行为。此时原入口仍在转发，所以保留的解析有效。
- 切换成功的定义：必须是该批原解析身份已发布到合格的新入口，且通过现有发布前／提交前资格复核的有效提交。保留原值的 DDNS 请求、系统 DDNS 未启用时的跳过，以及已过期的服务商响应，均不能启动 TTL 计时。改域名或记录类型后的发布也不能当成旧解析已经切走。
- TTL 快照：保留旧解析最后一次成功发布时使用的 TTL；历史数据缺少该值时，以开始待撤销时的 DDNS 设置值作为基准。同时记录本次有效切换使用的 TTL，撤销等待取两者较大值，避免切换时调低 TTL 提前停止仍使用旧缓存的入口。本次按面板记录和设置计算，不承诺覆盖外部手工修改的 TTL 或客户端超期缓存。
- 撤销时机：首次有效切换成功时，在同一次本地提交中保存成功时间、TTL 快照和固定的撤销截止时间（成功时间加本次等待 TTL）。后续修改 DDNS TTL、重复同步成功或面板重启都不重算、不提前也不顺延该截止时间。
- 5 分钟兜底仅适用于尚未有效切换的批次：从开始起满 5 分钟仍未切换，照常撤销；有效切换已先提交的批次改按固定 TTL 截止时间撤销，不再受开始后 5 分钟截断。例如开始后第 4 分钟切换、等待 TTL 为 600 秒，应在开始后第 14 分钟撤销。
- DDNS 发布失败时保留原入口，直到原先的 5 分钟兜底截止时间；反复编辑、失败重试均不重置这条期限。成功回执与兜底到期并发时，按同一批次的持久化状态串行判定；已经进入撤销的批次不能被迟到回执恢复。
- 由现有的转发组与 DDNS 维护任务以及组复查计时驱动。面板启动时恢复未完成批次并注册原截止时间，已到期的立即尝试撤销，不从重启时重新等待；后续重试也沿用原批次身份和截止时间。
- 以下情况立即撤销，与现在一致：
  - 移除非当前成员；
  - 移除唯一成员；
  - 组没有域名或 DDNS 未开启；
  - 删除或停用整个组；
  - 待撤销期间把同一主机加回组里（先撤销旧副本，再按新成员部署）。

**不变的部分**

- 运行确认门槛：普通规则须在该入口运行；SNI 组须确认当前完整分流配置生效。
- 优先级和自动回切设置不变；手动排序意图按上节完成一次后恢复原有调度。发布解析前的资格复核、ADR-0008 的入口健康判断与两项配套修补继续保留。
- 入口组、出口组、转发链、端口转发资源、隧道型主备组。

## Testing Decisions

- **好的测试只看对外结果。** 测试检查组域名发布给 DDNS 的值、切换发生的时刻、原入口在 Agent 收到的期望配置里何时不再有该组规则、组的当前入口与状态。不直接测窗口函数、调整标记等内部实现。
- **行为验收切入点。** 沿用 SNI 转发组健康测试的做法；数据库方言兼容另作同一行为的迁移与持久化验证：
  - 独立进程，真实 SQLite 数据库；
  - 通过转发组和规则的管理接口调用方改组；
  - 通过真实的 Agent 心跳接口上报规则运行和分流表；
  - 用 webhook 接收 DDNS 请求；
  - 用模拟时钟推进时间。
- **普通规则组。** 在同一套测试里增加普通规则组（与 tj2 同类）的初始化，覆盖以下场景：
  - 移除当前入口，剩余成员规则已运行：确认运行即切换，不等恢复时间；切换后约一个 TTL，原入口才撤销；切换前原入口一直收到该组规则。
  - 移除当前入口，剩余成员需要重新下发：重新运行后立即切换。
  - 停用当前入口：同上，先接后断。
  - 移除当前入口，下一个成员 5 分钟内都不合格：5 分钟后照常撤销原入口。
  - 新建组：首个合格成员规则运行后即发布解析。
  - 增、改、删组内规则：必要的运行确认期间保留原解析，普通规则重新运行（SNI 为当前完整分流配置确认）后立即重新合格，不进入额外恢复观察。
  - 调整后规则达到故障时间仍未运行：按真实故障处理，不额外等第二轮故障时间，之后恢复仍要求恢复观察。
  - 改域名或排序期间，未受本次变更影响的规则停止运行且没有诊断：仍按真实故障处理，恢复后不能直接取得资格。
  - 连续编辑同一尚未就绪的规则：期限不被反复顺延；新增加的另一条规则有自己的期限；超时后的编辑不能清掉既有真实故障或恢复观察。
  - 调整涉及的规则明确上报应用失败：立即退出调整豁免，按原故障与恢复规则处理；当前配置已确认后再次未运行也不复用旧豁免。
  - 当前入口 Agent 离线后恢复：仍须等满恢复时间。
  - 调整前已在恢复观察中的成员：调整后仍按原时间等待。
  - 先接后断期间面板重启：按持久化的时间完成撤销。
  - 切换使用 600 秒 TTL，之后改为 60 秒并重启：旧入口仍保留至原截止时间；旧解析此前使用 600 秒、切换时已降为 60 秒时同样不能提前撤销。
  - 在开始后第 4 分钟成功切换、TTL 为 600 秒：第 5 分钟不撤销，第 14 分钟按原截止时间撤销；期间重复同步不能延长期限。
  - DDNS 一直失败：编辑和重试不重置 5 分钟兜底；过期回执、保留原值或仅新域名发布成功不能误触发旧解析的切换成功。
  - 自动回切关闭，排序时新首选未运行：原入口先保留，新首选在调整期限内确认后直接接管；发布失败时意图保留并重试。
  - 排序目标此前已有真实故障：先完成恢复观察再接管；等待期间重启不丢目标，也不提前取得资格；再次排序覆盖旧目标，移除或停用目标、删除或停用整组则取消。
  - 移除非当前成员、移除唯一成员、组没有域名：与现有行为一致。
- **SNI 组。** 在同一套测试里增加：调整后当前完整分流表确认即切换，不等恢复时间；未确认时仍不合格。调整同时发生重启、重连、确认过期、应用失败或无关域名丢失时，真实故障优先；短暂失败被两次配置报告夹住也不能漏记。旧配置的延迟报告不能完成新配置确认。
- **改写现有场景。** 逐项核对现有测试，只修改与本决定直接冲突的准备步骤和断言，至少包括：
  - `member-release`：DDNS 有效切换成功并经过固定 TTL 截止时间后，原入口副本才清零；
  - `member-release-ddns-error`：发布失败时保留到原 5 分钟兜底期限；
  - `configuration`：修改目标或限制引起的调整等待，不再统一断言为 `unhealthy`；当前完整配置确认后直接检查备选成员 `selectionReady` 以及应发生的选择／发布，不再要求额外恢复观察。不能仅以当前入口暂未改变推断备选仍在恢复等待；
  - `ddns` 等包含管理员修改规则的场景：当前配置尚未确认时仍拒绝过期发布结果；有效确认后立即恢复资格，保留再次核对解析的要求；
  - 涉及真实故障的恢复等待断言继续保留，不为通过新测试而整体放宽。
- **数据库兼容。** SQLite、MySQL、PostgreSQL 均验证全新建库和已有库升级；保存待撤销批次、TTL／截止时间和手动排序意图后重新连接或重启进程，继续使用原身份和时间。不得只用 SQLite 行为通过代替另外两种数据库的迁移和持久化验收。
- **连接可用性验收。** 行为测试检查旧入口在有效切换前和 TTL 等待期持续收到应运行配置，新入口确认后才发布解析。集成或人工验收再实际建立新连接，分别覆盖切换前、使用新解析、TTL 内使用旧地址；不把期望配置断言当作真实连通性证明，也不把跨撤销期限的已有长连接不中断列为通过条件。未切换满 5 分钟的强制撤销单独验证为兜底例外。
- **回归。** 主备组回归测试和 SNI 转发组健康测试全部通过；与新决定直接冲突的断言按上节调整，其余行为和断言保留，作为 ADR-0006、ADR-0008 核对表的验证。
