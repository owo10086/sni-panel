### R04：新增每 IP 连接限制采用 A 方案

普通端口转发按上游执行：对同一台入口主机，同一个用户的普通 TCP 转发端口共享每个来源 IP 的连接数限制。设置取该用户当前生效的账户或套餐限制；不是新增一套自动开启的固定额度。上游排除的隧道规则和 UDP 继续排除。

例如，用户甲的两个普通转发端口分别是 `10001`、`10002`，每个来源 IP 上限为 5。同一个来源 IP 在这两个端口上分别建立 3 条、2 条连接后，共用的 5 个名额已经用完。另一台入口主机分别计算，不承诺所有入口之间共用一个总数。

**所有 SNI 分流规则都排除在本轮新增的端口级限制之外。** 包括单机、转发链、直接隧道、主机型转发组及其成员派生的配置，不得仅凭某一种承载方式判断是否排除。

例如，用户甲的 `a.example` 和用户乙的 `b.example` 共用同一台入口的 `443`。两条规则不进入这套新增限制，不得因任一用户设置了每 IP 额度而误限整个 `443`，也不得因端口重复让其他普通转发的限制整批失败。

合并时应同时保护以下行为：

- 新增限制只改变适用的普通 TCP 转发，不把 UDP 或 SNI 连接计入它的共享名额。
- 规则新增、移除、停用、归属或额度变化后，限制随完整配置更新；不再需要的限制能够清理。
- `0` 表示不限；用户原来已有的有效非零设置会在具备能力的 Agent 应用后开始约束普通转发，不能把“沿用设置”说成“所有旧规则都不受影响”。它限制的是每个来源 IP 的连接数，不是允许接入的不同 IP 数量。
- 全部适用规则被移除、额度改为不限、普通规则改成 SNI 后，仍要下发完整的空结果，清除本功能此前建立的旧限制；不能因结果为空而跳过。清理只处理本功能拥有的配置，不清空整台主机的防火墙，也不动其他业务的限制。
- 新增或移除普通端口时保留仍有效的共享计数；重复同步不重复占用名额。本机发起的连接不能在同一次连接中被算两次。
- 仅修改每 IP 设置时，按上游保留普通转发的现有进程、连接和运行状态；需要刷新现有隧道限制时继续刷新。限速、总连接数等其他限制也同时变化时，不能误走“只改每 IP”的省略路径。
- 沿用上游对已有转发连接的保护。限制设置或同步失败要如实显示，不能误报已生效，也不通过重启健康业务作为补救。
- 缺少新版 Agent 能力或必要运行条件时，明确说明限制未能应用，按上游保留既有转发。
- 这项限制不是已取消的 SNI 自动来源白名单，不得恢复旧来源名单或地址变更联动。

本轮不另做 SNI 按来源 IP、域名或用户限制连接数的扩展。

### R05：SNI 继续使用当前已经确定的规则

保留同一入口端口按域名区分规则、不同用户合法共用端口、未知域名或无 SNI 拒绝、可读明文 SNI 和带 ECH 扩展请求的既有处理，以及分流表更新时对其他域名连接的保护。

SNI 现有最大连接数的含义不变：转发链、单机和直接隧道由最终出口分流器执行；主机型转发组由各成员分别执行。旧连接与 DNS 缓存可能让多台成员同时服务，不能写成全组严格共用一个总上限。实际用量继续按当前方式汇总和计费。

保留 `3.3.2` 的转发组选择规则：入口在线、当前完整分流配置已确认生效、已开启的国内检测通过，并完成必要观察等待后才可选择。SNI 落地目标失败、缺失或过期不再单独卡住 DDNS 或触发整组切换；混合组中的普通规则仍执行原有目标检测。

旧 [ADR-0001](../../docs/adr/0001-sni-splitting-runs-as-a-standalone-fxp-role-at-the-exit.md) 中要求全部落地目标健康的历史表述已经被上述 `3.3.2` 决定调整。本轮以[当前更新日志](../../CHANGELOG.md)和已有修复为准，不恢复旧行为。

### R06：主机删除纳入新提示和清理确认

删除前列出仍在使用主机的规则、转发组、转发链、入口组、出口组和隧道，并提供前往处理的入口。停用但尚未移除的真实配置仍受保护，不能以停用代替解除关联。

在线主机还有待清理的旧规则时，等待 Agent 完成清理并刷新结果；离线主机无法确认实际停止时，用户明确确认后才允许移除。离线确认只处理旧规则清理的不确定性，不能绕过仍在使用主机的真实配置。

继续保留 `3.3.8` 的要求：

- 从组中移除成员后，旧主机的逻辑引用正确释放，不要求逐条重新保存业务规则，也不因旧主机离线而无限保留失效引用。
- 不通过删除整个转发组、主规则或累计用量消除旧引用。
- 删除前按最新保存的配置再次检查引用和操作权限，保存失败时一起恢复。
- 删除 Token 要检查全部相关主机；不能误删其他主机仍在使用的 Token。
- 主机名称和关联配置名称只向有权限的人展示。普通用户不能通过新的删除预览看到其他用户的资源名称；需要阻止删除时仍应给出权限范围内可理解的提示。

例如，旧入口已从组中移除，但还有一条旧成员规则等待离线主机清理：不能再把已经转给新成员的 44 条主规则算成旧入口的真实引用；离线确认也不能被用来删除仍被独立隧道使用的主机。

上游的新删除流程与本项目现有的最后检查、保存顺序不同，需要兼容处理，不能直接覆盖本地保护。

预览和准备清理也必须先检查操作权限。纯查询只读取；允许进行的历史修正或清理请求不得把“等待主机确认”改成“直接把状态标成已停止”。普通用户看不到其他人的名称，必须在返回数据和错误提示时就落实，不能只在网页上隐藏。

预览成功不是最终删除许可。点击删除时重新读取当前的操作权限、真实引用、在线状态及待清理数量；预览后新增引用、主机重新上线或归属变化时，按最新状态处理。在线主机不得凭之前勾过的离线确认跳过实际清理；查询或准备失败、尚未完成时不能继续删除。

### R07：保留现有批量操作和导入行为

保留 `3.3.1` 至 `3.3.8` 中已经完成的功能与修复，尤其是：

- 主机型转发组的 SNI、备用配置确认、观察等待、DDNS 和现有计费关系。
- SNI 批量删除、编辑和切换入口的保存顺序，合法共用 `443`，以及失败时完整保留原配置。
- 普通、SNI 和混合规则文件都整批提交并集中保存，不能退回普通规则逐条保存的旧方式。
- 按原有规则保留逐项成功或失败结果；单项失败撤回该项，最终公共保存失败时撤回本批新增，保留原有规则。
- 普通手动导入支持 `规则名称#源端口#目标地址#目标端口`，指定端口先处理，不得在指定端口失败后偷偷换成随机端口；文件导入保留当前的处理顺序。
- 已成功的规则不重复提交，失败项保留原文、行号和必要信息供重试。
- DNS 等后续操作失败不能把已经保存的配置误报为未保存，也不能恢复已经移除的组成员。

网页换主题、精简文案或翻译时，不能丢掉这些入口、说明和反馈。

继续保留现有每批最多 500 条、规则文件最大 5 MiB、格式错误的整体拒绝边界，以及管理员 SNI 权限、归属用户的资源与配额检查。明确填写零限额与未传限额字段的托管含义不变。混合文件的先后顺序不能因规则类型改变。

“保存失败”和“应用失败”分别处理：数据库统一保存成功前，按上述规则撤回；保存成功后的通知失败、主机离线或监听应用失败，只能报告待同步或应用失败，不得声称已撤回数据库，也不得静默删除已经保存的规则。

### R08：隧道批量新增采用上游改进

纳入 GOST、V1/V2 隧道只增加新监听的能力。正常新增时保留未变化的健康监听、进程和长连接；确定发生新增端口冲突或准备失败时，只撤回本次尚未完成的新增监听和相关准备，不触碰原有业务。

例如，隧道中原有 A、B 两条规则正在使用，再导入 C。C 新增失败时，应保留 A、B；不能为使 C 生效而重启承载 A、B 的健康进程。

旧运行时不支持局部新增时，沿用上游的明确失败处理，不用重启旧进程强行完成新增。修改、删除已有监听、首次启用、更新运行程序及故障恢复仍可能重启，不承诺升级全过程不断线。

与本项目的整批保存、逐项结果、SNI 共享监听和成员调整配合处理，不改写这些功能的现有规则。

还要保留上游已经处理的这些情况：

- 主机已经应用新配置，但回复丢失，或后续配置文件保存失败时，结果可能不确定。不能把所有超时都当作“什么也没应用”，不能盲目删除可能已在使用的监听或 V2 转发准备；继续按实际状态核对、重试和收敛，不用重启共享进程掩盖问题。
- 重复发送同一份新增配置不重复建立监听。并发批次先后到达或较旧快照晚到时，不能把另一批已成功新增的监听误删；明确的停用、删除仍应按当前配置生效，不能把合并快照当作恢复旧规则的指令。
- GOST 为实际业务让出同一隧道、同一端口的临时自测占位时，只替换该占位。新增失败后按上游恢复占位，不把真实业务或其他隧道的监听误当成占位删除。
- 新增过程中出现部分成功、重复名称或端口被其他程序占用时，只清理本次有权清理的新增对象。必要的 V2 转发准备保留到结果确认后再清理，不因反复重试无限累积。
- 局部新增的控制入口只在主机本地、沿用上游的访问限制，不新增公网管理端口。错误提示和日志不回显令牌、密钥或完整业务配置。

这里的“撤回新增”指主机应用过程中的监听和准备配置，不代表数据库中已经保存的规则也被撤回；二者按 R07 分别报告。GOST、V1、V2 和其实际支持的 TCP／UDP 路径分别核对，不能只测一种模式后宣称全部通过。
