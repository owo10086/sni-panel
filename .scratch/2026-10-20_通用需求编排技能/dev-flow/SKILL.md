# dev-flow

用于按已有需求文档完成一轮开发，沿用 `sni-flow` 的后五步及执行模式。第一步只确认本轮最新需求文档，不开展 `/grilling` 访谈，也不先凭聊天补造需求。创建或修改本技能，只交付技能，不启动实际开发。

## 执行模式与权限

- 用户调用本技能处理一轮需求，默认执行六步，包含第五步代码实施、验证和本地提交，第六步提交点评。不再逐步索取形式确认；用户明确限定“只整理文档”“不实施”或“不提交”时，按具体限定处理。代理自行发现本技能或仅阅读其内容，不算用户授权实施。
- **第一步是固定前提：没有有效的最新需求文档就中断；有多份候选就暂停，必须由用户明确选定。即使用户说“执行全部”，也不能跳过、代选或把多份需求自动合成一轮。**
- **默认模式**：需求唯一后，常规事项按推荐继续；遇到与本地行为、项目决定冲突，功能取舍或无法判断其影响，保存证据、用户影响和推荐办法，停止等用户。
- **“执行全部”模式**：用户将“执行全部”作为本轮执行指令时，需求选定后由主代理按推荐处理冲突和功能取舍，记录理由并继续，不逐项等回复。启动时或暂停后均可指定；引用、举例、否定这句话不算。该模式只适用于本轮选定的需求，不自动扩展到其他任务。
- 自动处理优先遵守本项目约定、已有明确决定及本地保护，在选定需求范围内兼容实现；无法同时保留时，记录冲突和处理影响，不暗中改掉既定行为或把未实现的要求写成完成。“执行全部”不撤销项目规则，也不扩大需求范围。
- “同意”只确认当前方案，并保存本地 Markdown；本身不增加实施权限，也不切换“执行全部”。若本轮调用已授权六步，则沿用已有授权。不能把沉默、超时或子代理建议当成用户答复。
- 不创建 Git 工作树，保留他人已有修改。提交使用中文信息，较大改动分批提交；推送、标签、发布和部署需另有对应明确指令。
- 工具、环境或访问确实不可用时，自行排查可行办法后报告真实阻塞；不能用“执行全部”跳过必要审查、伪造验证或宣称未完成的提交已经完成。

问题、进度、报告和交付用 Markdown 与大白话。复杂取舍给例子；需要用户答复时，直接说停在哪一步、要决定什么和推荐什么。

## 开始前：读取当前项目约定

1. 读取当前项目适用的 `AGENTS.md`、`CLAUDE.md`、`CONTEXT.md`、需求／问题平台配置及相关 ADR（存在时）。项目决定以本项目为准，不把 SNI、上游版本号、某个仓库地址或客户端排除规则固定套到其他项目。
2. 第一轮需求选择只做只读查找。第一步通过后，读取 `/to-spec`、`/to-tickets`、`/implement` 的真实 `SKILL.md`；按当前技能目录查找，缺项再查 `~/.agents/skills/` 和 `~/.codex/skills/`。缺少依赖时停在需要它的步骤说明，不伪称执行或擅自安装替代。
3. 第一步通过后，核对分支、HEAD、工作区和远端，记录实施前依据及无关修改；不重置、不覆盖、不创建工作树。对已有合并／变基或无法区分归属的修改，先确保能保护原工作，无法做到时说明实际阻塞。
4. 复用本轮需求已有的工作目录；无约定时使用 `.scratch/YYYY-MM-DD_需求名称/`，规格为 `spec.md`，逐单保存到 `工单/`。项目已有位置及问题平台约定优先；没有配置时使用本地 Markdown，不为使用本技能额外安装问题平台。
5. 维护本轮 `编排进度.md`：源需求路径和版本依据、选定方式、六步状态、执行模式、用户决定或自动推荐、原有修改、规格与工单链接、实施前提交、完整提交清单、检查结果、人工验收状态和下一动作。恢复时核对实际文件、需求版本和代码，不重复开单、实施或提交。

## 第一步：确认本轮最新需求文档

### 查找范围与有效性

- 先按用户给定的文件、目录、需求主题或本轮进度查找。未给定时，读取项目约定的需求位置，再在实际存在的 `.scratch/`、`docs/`、`specs/`、`requirements/` 等位置用 `rg --files` 查找。不要搜索其他项目或把全项目的旧文档混成当前任务。
- 读取可能的需求正文及其状态、版本说明、替代关系和已有交付记录。常见名称包括 `spec.md`、`requirements.md`、`prd.md` 及中文需求／规格文档；名称相似不证明它就是本轮需求。审查报告、工单、进度记录、日志、普通说明文档不能单独代替需求正文。
- 待处理需求可以是新增、明确更新或尚未完成的需求。已有明确证据表明完成且没有新修订、废弃或被新版取代的文档，不作为新的候选；不能只凭文件日期、修改时间或 Git 是否跟踪判断新旧和完成状态。
- 认定“最新”须有依据，例如用户明确指定、文档版本与修订说明、明确替代关系或本轮已有记录。几份文档都还有效时，不能只取时间最近的一份。无法确认哪份生效时，列为多个候选让用户选，而不是猜测。
- 用户明确给出一份文件，视为人工指定本轮对象，但仍需读取并确认有效；若它明确已被替代，或最新生效版本仍存在歧义，先说明并让用户确认。本轮生成的规格、工单和审查结果，不再次算成额外的源需求。

### 按数量处理

| 有效最新候选 | 动作 |
| --- | --- |
| 0 份 | 中断，说明已查范围及缺少什么，提醒用户提供或先写好最新需求文档；不进入第二步，不自行补造需求后继续。 |
| 1 份 | 读取全文，记录路径、版本／日期及认定依据，固定本轮范围，直接进入第二步。 |
| 2 份及以上 | 暂停，逐份列出路径、主题、版本依据及待确认事项，请用户明确选择；不按时间排序代选，不批量执行，也不提前实施其中一份。 |

用户回答后重新核对：只回复“同意”却没有指出选择哪份，不算选择完成；明确选定一份后，再沿用原执行模式继续。用户说“执行全部”但仍未选需求，也继续等待选择。

第一步完成条件：有且仅有一份本轮有效最新需求已被固定，或用户已明确从多份中选定本轮对象；未确认则不能进入后五步。外部后续修订若改变本轮范围，重新核对第一步并更新受影响的规格、工单和审查，不悄悄换需求。

## 第二步：用 `/to-spec` 整理规格

以第一步选定的文档为来源，结合本地代码和项目约定，按实际 `/to-spec` 整理为本轮规格，不重新开展需求访谈，不擅自加入新功能。保留源文档路径和版本证据，说明用户问题、交付行为、范围、保留条件和验收要求。

源文档已经是本轮 `spec.md` 且结构足够时，直接复用并按需补齐，不另造一份相互竞争的规格；更新时保留可核对的原始版本或变更记录。其他来源整理到本轮 `spec.md`，不覆写无关文档。

沿用项目现有的验证入口，检查用户可见结果，常规推荐直接记入文档。遇到未定的冲突或功能取舍按执行模式处理；没有依据的内容不能写成用户已确认，计划检查不能写成通过。

完成条件：规格完整、来源可追溯、范围与选定需求一致，验收可观察，没有占位内容或尚未处置的决定。

## 第三步：让 Codex CLI 独立审查需求

读取 [Codex CLI 审查约定](references/codex-review.md)，启动全新只读 Codex CLI 子代理，提供选定的源需求、整理后的规格、本地代码依据、项目决定和相关 ADR，不只给主代理总结。

实际完成一次审查后逐条处理：漏项、矛盾或已定事项的遗漏直接补齐；冲突与功能取舍按执行模式等待或采用推荐。无关扩展记为范围之外，不成立的问题保存依据。若发现选错需求或来源仍有多个候选，回到第一步等待用户，即使在“执行全部”模式也不代选。

保存 `审查/需求审查.md`、运行记录及 `审查/需求审查处理.md`。重大规格变化对受影响内容补充独立复核，不反复审查同样的问题。

完成条件：CLI 成功返回实际报告，问题逐项有处理，没有未解决阻塞或第一步选择歧义；调用失败、报告缺失不能进入第四步。

## 第四步：用 `/to-tickets` 按推荐开单

以第三步补齐的规格为依据，按能独立交付或核对的一小段完整功能拆单，写清真实依赖和对应验收。采用推荐粒度，不重复询问粗细；只安排本轮需要的准备改造，不附带无关重构。

遵守项目问题平台约定；本地模式一单一份 Markdown，按依赖从 `01` 编号，项目无指定位置时使用本轮 `工单/NN-中文名称.md`。外部平台操作遵守已有授权；没有授权时先把本地工单准备好，不自行发布。每单写清交付行为、前置工单、验收及应保留的本地条件，给出规格与工单对应关系。

完成条件：全部范围内需求与验收有工单承接，无重复、循环依赖和范围外待办。开单不代表已实施或验收。

## 第五步：用 `/implement` 实施、验证并提交

按工单依赖实施，本轮用户调用已包含代码、验证和本地提交授权；遵守用户针对本轮的更具体限定。先记录实施前提交及原有修改，只处理本轮范围，不创建工作树。

沿用 `/implement` 的实施及检查方式，按改动运行必要验证并记录实际结果，未覆盖或环境不可用如实写明。常规修补继续；冲突和功能取舍按执行模式处理。若出现需求来源歧义，仍回第一步人工选择。

实施及必要检查完成后，仅提交本轮交付内容，不夹带他人原有或无关修改。中文提交，大改动按功能分批；记录完整提交编号、交付内容、检查结果及残留说明。先完成提交，再进入第六步；`/implement` 默认的最终 `/code-review` 由第六步独立 Codex CLI 提交点评承接，不重复调用另一套审查。

完成条件：工单落实、文档与代码一致、检查及限制有据可查，应交付代码已提交；不把未提交内容或提交成功当成验证通过。

## 第六步：让 Codex CLI 进行提交点评

按审查约定启动另一个全新只读 Codex CLI 子代理，提供源需求、最终规格、全部工单、实施前提交、本轮完整提交清单、需求审查处理和验证记录。

点评第五步全部本轮提交及最终状态，核对需求覆盖、本地保护、范围、实际缺陷和验证不足，不能只看最后一笔或夹带无关提交。发现遗漏的未提交本轮代码时补交后再点评，未提交内容不计入已点评提交的结论。

保存 `审查/提交点评.md`、运行记录及逐项处理。明确缺陷在本轮范围内修复、验证并新增中文后续提交，不重写已有提交；冲突或取舍按模式处理，需求选择仍服从第一步。修补提交形成后，补充受影响部分的独立复核，标明实际点评的提交编号，不沿用修补前结论宣布新提交通过。

完成条件：点评实际完成，阻塞已有修复或明确处置，最终提交、规格与审查一致，限制如实记录。本轮范围、完整提交、审查及处理链接、实际检查和剩余事项保存在交付 Markdown，随后交接人工验收。

## 收尾与下一步

- 六步完成后直接说“代码实施和审查已完成，下一步需要你人工验收”，在进度中记录“六步已完成，待人工验收”。先完成代理能做的环境准备，提供实际可访问的入口，再列少量验收项目：在哪里操作、做什么、怎样算通过。
- 环境尚未准备好时，说明下一步先准备什么，不让用户对着不存在的环境验收。只有用户明确确认实际验收通过，才记录“人工验收已通过”。
- 暂停时直接说“停在第 N 步，需要你确认：……；推荐：……”。第一步缺文档时说明需提供需求；有多个时列出候选让用户选择。用户问进度或下一步时直接回答当前动作，细节放本地 Markdown 链接。
- “执行全部”、自动检查、独立审查、本地提交和“同意方案”均不代替人工验收。后续推送、发布与部署按对应授权执行。

## 调用示例

- `$dev-flow`：在当前项目查找最新需求；没有则中断，多份则等用户选择，唯一则按默认模式完成后五步。
- `$dev-flow 按 .scratch/2026-10-20_导出报表/spec.md 执行`：核对指定文档后完成六步，冲突或功能取舍默认等待。
- `$dev-flow 按 docs/需求/导出报表.md 执行，执行全部`：第一步仍须确认需求唯一；之后按推荐处理冲突与取舍，连续推进到提交点评。
- `$dev-flow 继续 .scratch/2026-10-20_导出报表/`：读取本轮进度，核对选定需求及实际提交，从未完成处按已记录模式恢复。
