# 01 — Agent 只上报规则入口端口的占用，删除全量快照与截断机制

**What to build:** Agent 不再上报整台主机的监听清单，改为只上报自己规则用到的入口端口上的占用情况，并**明确声明本次核实过哪些端口与协议**。删除的是「按重要程度裁剪 + 按端口号声明覆盖」这套组合，不是裁剪本身——新的两道上限按端口成组丢弃，丢掉的端口同时退出覆盖声明。面板侧接收、缓存与占用判定跟着收窄。

**Blocked by:** None — can start immediately

**Status:** ready-for-agent

## 上报内容

- [ ] 上报的端口集合 = Agent **自己启用中的转发规则的入口端口与传输协议**，由 Agent 从完整期望启用规则清单计算；面板不发起按需端口询问
- [ ] 面板从该主机实际应生效的全部启用规则构造完整清单，每条至少含规则标识、该主机实际使用的入口端口、协议和转发方式；不依赖 `isRunning` 或是否有动作，隧道及 SNI 分流按有效入口端口计算
- [ ] **修订号要落到一个明确的存放位置**——现有状态段签名都是每次请求现算、不落盘的，没有现成的家。二选一：主机维度的落库计数器，或「面板启动标识 + 进程内递增序号」的有序组合（Agent 按字典序比较，重启后启动标识增大，整体仍单调）。**不允许**直接用进程内整数计数器：面板重启后从头开始，Agent 会把新清单当成旧推送无声丢掉
- [ ] 清单作为独立带签名状态段沿现有完整心跳和 SSE 推送，不增加一轮问答；面板维护随配置更新单调递增的修订号，重启后不得回退；Agent 记录已见最高修订号，收到不低于该号且签名校验通过的完整清单时原子替换内存缓存，包括明确的空清单和同修订号的合法补传；旧修订号推送不得覆盖新状态
- [ ] 省略清单时仍携带修订号和签名：签名与有效缓存一致且修订号不旧则保留缓存并更新已见最高修订号；对不旧的修订号，签名变化但清单缺失、清单不完整或签名校验失败则记下修订号、撤销覆盖并清除下一次心跳通告的清单签名，以请求完整清单；迟到的旧修订号完整推送不能重新启用旧缓存
- [ ] **不得**用面板下发的「已运行规则」清单作为来源：它按「已启用且已在运行」过滤，一条因端口被占而起不来的规则不在其中，而那正是最需要查明占用者的端口
- [ ] **不得**只从本次要执行的动作列表提取端口：不需要动作的存量规则会整批漏掉
- [ ] **现有 `desiredState` 仅含 `Actions`，本地标记仅记录成功应用过的规则，二者都不是完整清单**；新增清单要覆盖从未成功启动的规则和无需动作的存量规则
- [ ] 凡是在最新完整清单里处于启用状态的规则，其入口端口都进入集合，不以动作是否执行成功、运行时是否就绪为条件；停用、删除或修改端口后及时更新集合与签名
- [ ] 这一条**只作用于端口集合的计算**：不改变「规则是否就绪」的上报口径（起不来的规则照样报未就绪），不得因此多写一个标记文件，也不得让规则回收把它当成一条已经落地的本地规则
- [ ] Agent 重启后尚未收到完整清单时覆盖集合为空；在下一次正常心跳取得完整清单后恢复，不从本地标记推断当前启用规则，也不把缺失清单误认为已核实的空闲端口
- [ ] 用户态与内核转发的规则端口**都要报**；停用规则的端口不报
- [ ] 都要报的理由是**解耦**：哪些 `forwardType` 呈现占用警告是面板一侧的呈现决定（工单 03），编进 Agent 的过滤条件等于以后调呈现范围就要发一版 Agent。**理由不是**「面板要从这份数据里查出占用者的名字」——红色 bind 失败里那个名字由 Agent 在本地从监听快照生成、随动作状态回报，与本工单无关，两条路径不得互相依赖
- [ ] 每个条目保留：端口、传输协议、绑定地址、可识别的进程名、是否属于受管运行时及其实例标识
- [ ] 绑定地址必须保留，`127.0.0.1` 与 `0.0.0.0` 不得合并或省略
- [ ] Agent 的**监听采集**动作不变，仍复用既有的全量监听扫描结果，只在上报时过滤
- [ ] 端口集合从最新完整清单计算并缓存在内存；保活包从缓存读取，不扫描本地状态目录，收到清单变更后立即更新缓存和占用签名

## 两侧的端口口径

- [ ] **清单里那个端口，和面板拿去查覆盖集合的那个端口，必须由同一段推导算出来**
- [ ] 现状是分家的：清单侧按「该主机实际使用的入口端口」算（隧道出口主机上得到出口端口），警告侧直接取规则行上的 `sourcePort`（那是入口那台主机的端口）；取规则的查询本身不做逐主机换算，同一条规则在入口和出口两台主机上读到同一个 `sourcePort`
- [ ] 不一致的后果与本次缺陷同形：Agent 覆盖 A 端口、面板查 B 端口，B 永远不在覆盖集合里 ⇒ **永远未经核实、永远不出警告、不报任何错**。受影响的是 gost / nginx 隧道的出口规则
- [ ] 因此：**「本主机有效入口端口」只有一处实现，清单构造与占用判定都调用它**，任何一侧都不得自己取 `sourcePort`；隧道入口与出口、SNI 分流、转发组成员各算各的有效端口，但都走这一处

## 覆盖声明

- [ ] 上报内容除占用条目外，带一份**本次实际核实过的端口与传输协议的集合**，逐个端口枚举，与占用条目用同一套端口与协议的说法，**不是一个范围界限**
- [ ] 覆盖集合按**端口与传输协议逐条枚举**
- [ ] 占用判定分三种结论：在集合里且有匹配监听 ⇒ 占用；**在集合里但没有匹配监听 ⇒ 空闲**；**不在集合里 ⇒ 未经核实**
- [ ] 规则协议为 `both` 时，**该端口的 TCP 与 UDP 都在覆盖集合里**才算被核实；只覆盖一个协议时结论为未经核实，不得拿覆盖到的那一半当整体答案
- [ ] 任何原因导致某端口没能完整上报（完整清单尚未到达、单端口条目触顶、整份上报触顶、采集时读取失败），该端口**不得出现在覆盖集合里**
- [ ] 未经核实的端口**不得参与提醒的解除判定**，提醒状态里上一次的有效占用原样保留（界面侧如何处理见工单 03——那一侧是隐藏，与这里的保留不是同一件事）

## 采集完整性按传输协议与地址族判定

- [ ] 「本次采集是否成功」不再是一个整体布尔值：备用采集路径逐个读取多个内核文件（TCP / TCP over IPv6 / UDP / UDP over IPv6），现状是其中一份读不到就跳过，只要其余任一份读到监听，整份仍被标记为可用
- [ ] 按传输协议与地址族分别记录读取成败；任一族读取失败时，依赖该族判断的端口不得进入覆盖集合
- [ ] 允许取保守做法：备用路径下任一族读取失败即把本次采集整体判为失败、覆盖集合为空——备用路径本身已是降级场景，不值得为它做精细的部分覆盖
- [ ] 主采集路径是单条命令，整体成败无歧义，行为不变

## 体积约束

- [ ] **单端口条目上限**：同一端口上可以有多条监听（IPv4 与 IPv6、不同绑定地址各一条），受规则数约束的是端口集合而不是条目数
- [ ] **整份上报上限**：单台主机的规则数在数据模型里没有上限，心跳请求体有大小限制，整份上报必须在它之下留出余量
- [ ] **上限按最终请求体计量，不是按占用数据自己的 JSON 字节数**：心跳整包会被加密，密文再按十六进制编码放进信封——**编码后体积是明文 JSON 的两倍**，信封外还有其它心跳字段挤在同一个请求体里。拿占用数据自己的长度去对着服务端请求体上限算余量，至少差两倍
- [ ] **面板的接收上限必须不小于 Agent 的发送上限，两个数成对定义**：现状是两侧各有一套互不知情的常量。面板一侧更紧时，每一份合法上报都会被判非法——而按下面「兼容」一节，被判非法的后果不是「这次没核实」，是把 Agent 推进 2 秒一次的重发循环
- [ ] 超限时**按端口成组丢弃**，不做半个端口；被丢弃的端口**同时从覆盖集合里去掉**，按未经核实处理
- [ ] 绝不允许出现「声称覆盖了某端口、却少报了它的条目」的状态
- [ ] **两道上限都要落成具体数字，并写明它对着哪一个量**：现有实现的 256 条 / 32 KB 是可以沿用的量级起点，但那 32 KB 原本是对着占用数据自己的 JSON 算的，沿用前按上面的计量基准重新核对

## 删除的机制

- [ ] 删除面向**整台主机全量清单**的条目数上限与字节上限（取而代之的是上面按端口成组丢弃的两道上限）
- [ ] 删除**布尔完整标志 + 单一端口号界限**这种表达覆盖范围的方式（取而代之的是逐条枚举的覆盖集合）
- [ ] 删除按重要程度排序的截断策略（受管 → 80/443/10000-49151 → 其余低位 → 高位）
- [ ] 删除占用判定中「该端口落在截断范围外时返回未经核实」这一分支，由上面的覆盖集合取代
- [ ] 上述机制的既有测试一并删除，不保留开关、不保留兼容路径

## 心跳字段与签名

- [ ] 保留独立字段、独立签名、「本次采集是否成功」三项设计；签名的输入随上报内容收窄到规则端口
- [ ] **签名的输入同时包含占用条目与覆盖集合**：新增一个没有任何监听的规则端口时，占用条目不变而覆盖集合变化，签名必须翻转——否则面板认为缓存有效、不要求补传，Agent 也不主动补传，那个端口会永远停在未经核实且无法自行走出
- [ ] 采集成功 + 签名一致 ⇒ 刷新最近核实时间，内容不变
- [ ] 采集成功 + 签名不一致 ⇒ 面板要求补传完整内容
- [ ] **采集失败 ⇒ 最近核实时间与内容都不刷新**
- [ ] 「最近核实时间」与「采集时刻」仍是两个独立的值，陈旧度判断用前者，沿用仓库既有的「新鲜期 + 未来偏移容忍值」约定
- [ ] **面板的新鲜期不得等于 Agent 完整心跳的周期**（两者现在都是 5 分钟，完整心跳还带最多 10% 的向下抖动，余量最少可以是 0）：或把新鲜期放大到不少于完整心跳周期的两倍，或让更高频的那类心跳也带上签名以刷新核实时间；推荐前者
- [ ] 回归断言：上报之后经过一个完整心跳周期、下一次上报尚未到达时，结论仍然有效，警告不在周期之间翻转

## 占用判定

- [ ] 判定仍是一处独立实现，只依赖上报内容、主机、端口、传输协议、执行方式与受管端口集合，不依赖请求上下文、不碰数据库连接
- [ ] 判定区分 TCP 与 UDP、IPv4 与 IPv6、不同绑定地址；只陈述客观事实，冲突判断交给按 `forwardType` 分流的那一层
- [ ] **受管占用不等于端口可用**：只有规则要用的确实就是那个已存在的受管监听本身时才算可复用
- [ ] 数据缺失、采集失败、过期、端口不在覆盖集合里时判定返回**未经核实**，绝不返回「空闲」
- [ ] 判定仍产出按角色分别构造的两份说明：管理员那份含进程名，普通用户那份从构造时就不含

## 兼容

- [ ] 新版 Agent 的完整心跳与保活包始终携带 `portOccupancySchemaVersion: 2`；面板遇到缺失或未知版本时忽略旧结构及同签名简报，使原占用缓存失效，不解析旧格式、不报错、不要求补传
- [ ] 新版完整快照若因字段非法或占用字段超过面板接收上限被拒绝，立即判为未经核实并记录被拒签名；**随后的同签名简报不得重新启用此前缓存的内容**，合法完整快照才能清除拒绝状态
- [ ] 拒绝当次不要求立即补传；对同一主机至少冷却 5 分钟，其后正常心跳可要求一次完整补传。再次拒绝则重新冷却，不能形成每 2 秒持续重发；主动上传的合法新快照可随时恢复
- [ ] 无有效缓存时也按上述冷却规则处理被拒签名；新 Agent 刚启动或面板重启后收到从未被拒绝的有效签名简报，仍可按既有机制要求一次补传

## 不做

- [ ] 本工单不改动创建路径上的任何校验（见 02）、不改动警告的呈现范围（见 03）、不改动提醒（见 04）

## 测试

- [ ] Agent 侧：上报内容只含启用规则用到的入口端口；绑定地址与进程名保留；TCP/UDP 分开；IPv4 与 IPv6 分别识别；采集时刻带上
- [ ] Agent 侧（本次缺陷的直接回归用例）：主机上存在大量与规则无关的监听时，**上报覆盖的端口集合只随规则集合变化**，与无关监听的数量无关——断言的是端口集合，不是条目数
- [ ] Agent 侧：覆盖集合与占用条目一致；因单端口条目触顶或采集失败而未完整读取的端口不出现在集合里
- [ ] Agent 重启后尚未收到清单与收到明确空清单时覆盖集合均为空，收到完整清单后恢复
- [ ] Agent 侧：一条已启用但尚未就绪的规则及不需要动作的存量规则，端口仍在覆盖集合里
- [ ] Agent 侧（来源扩充的回归用例）：完整清单中一条用户态规则第一次 `apply` 就因端口被占而失败，端口仍进入覆盖集合；Agent 重启并重新接收清单后依然进入，不能用「先成功一次再失败」代替
- [ ] Agent 侧：停用、删除、修改源端口及收到旧修订号清单的测试；端口集合在有效清单变化时更新，旧修订号推送不能覆盖新清单
- [ ] Agent 侧：同签名省略清单时保留有效缓存；签名变化但清单缺失或不完整时撤销覆盖并停止通告旧签名，同修订号的合法完整补传能恢复覆盖；之后迟到的旧修订号完整推送不能恢复旧覆盖
- [ ] Agent 侧：内存缓存使连续两次保活包都不读取本地规则状态；清单变化后的下一次保活包使用新集合
- [ ] Agent 侧：整份上报上限按最终请求体计量——占用数据与其它心跳字段同时存在、经过加密与十六进制编码后，请求体仍在面板接收上限之下
- [ ] Agent 侧：备用采集路径下某一传输协议或地址族读取失败时，本次采集不被标记为完整，受影响端口不出现在覆盖集合里
- [ ] Agent 侧：单端口条目触顶、整份上报触顶时，被丢弃的端口同时从覆盖集合里消失，且丢弃以端口为单位
- [ ] Agent 侧：上报结构中不再出现布尔完整标志与按端口号表达的覆盖界限，取而代之的是逐条枚举的覆盖集合
- [ ] Agent 侧：签名同时随占用条目与覆盖集合变化——**加入一个没有任何监听的规则端口时签名翻转**，移除时同样翻转；主机上无关进程的起停不影响它
- [ ] 心跳侧：签名一致时刷新核实时间而不重传内容；签名不一致时补传；采集失败时核实时间不前进
- [ ] 心跳侧：完整清单同时包含首次应用失败和无需动作的规则，规则停用后从清单移除；Agent 重启可由正常心跳恢复完整清单
- [ ] 心跳侧：旧格式上报及其后同签名简报均不产生占用判断、不报错、不要求补传；版本字段出现后合法快照能自动恢复
- [ ] 心跳侧：新版非法完整快照当次不要求补传，同签名简报不能重新核实旧缓存；冷却时间内不要求补传，冷却后只要求一次，合法完整快照恢复，重复非法快照不会形成持续快速重发
- [ ] 心跳侧：超出面板占用字段接收上限的上报按新版非法快照处理；另断言「面板接收上限 ≥ Agent 发送上限」
- [ ] 判定侧（端口口径回归用例）：一条经 gost / nginx 隧道的规则，在出口主机上的有效端口与它行上的 `sourcePort` 不同；断言该主机上报的覆盖集合与面板查询的端口是**同一个**，出口端口上存在外部监听时警告能正常出现。不写这条，两侧口径一旦分家不会有任何测试发现
- [ ] 心跳侧：面板重启后修订号不回退——重启前后各下发一次清单，断言后一次严格大于前一次，Agent 不把重启后的新清单当成旧推送丢掉
- [ ] 判定侧：协议为 `both` 的规则，只有 TCP 在覆盖集合里时结论为未经核实，不为空闲
- [ ] 判定侧：端口不在覆盖集合里时返回未经核实而非空闲——**规则刚建好、上报集合尚未跟上的那一轮**，新规则上得不到任何结论，且不触发解除提醒
