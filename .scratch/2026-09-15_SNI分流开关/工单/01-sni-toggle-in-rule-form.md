# 01 — 规则表单加入 SNI 分流转发开关

Status: resolved

**What to build:** 管理员在添加/编辑转发规则时，能用一个显式开关声明这是一条 SNI 分流规则。开关打开后表单整体切换到分流形态：入口端口 443 锁定、域名必填、协议锁 TCP、不做端口探测。开关关闭时表单与今天完全一致。

规格见 `../spec.md`。

**Blocked by:** None

## 验收标准

### 开关本身
- [x] 开关位于「协议」与「源端口」之间，整行宽，标题「SNI 分流转发」，副文案说明多条规则共用一个入口端口
- [x] 普通用户完全看不到开关
- [x] 新建规则时开关默认关闭
- [x] 打开一条已有 SNI 规则编辑时，开关显示为开
- [x] 开关打开但 SNI 域名为空时保存被拦下，提示填写域名

### 源端口
- [x] 手动把开关从关拨到开 → 源端口变为 443 且不可编辑
- [x] 打开一条入口端口为 8443 的已有 SNI 规则 → 端口显示 8443 且不可编辑，不被改写为 443
- [x] 锁定状态下有「修改入口端口」折叠入口，点开后端口恢复可编辑
- [x] 开关从开拨回关 → 域名、限速、最大连接数清空，源端口恢复为打开开关之前的值

### 校验
- [x] 开关打开时不发起 `rules.checkPort`，端口框不出现「不可用」标记
- [x] 开关打开时 `portStatus` 不再阻止保存（今天新建规则要求 `portStatus === "available"`）
- [x] 开关关闭时端口探测行为与改动前一致
- [x] 填完 SNI 域名后校验该域名在当前入口主机上是否已被占用，冲突时在域名框下方写明冲突规则
- [x] 域名为空时不发起任何域名校验请求

### 联动
- [x] 开关打开时协议锁定为 TCP 并显示为只读
- [x] 开关打开时出现「规则限速 Mbps」「最大连接数」，关闭时消失
- [x] 开关打开时出站策略/故障转移不可用

### 不支持的资源
- [x] 转发组模式下开关置灰，写明转发组不支持 SNI 分流
- [x] 多出口或启用负载均衡的隧道下开关置灰，写明仅支持单出口
- [x] 非主机型、或含多台启用主机的端口转发资源下开关置灰，写明原因
- [x] 置灰情形下若表单原本带着域名（切换资源导致），域名与限速被清空

### 其它
- [x] SNI 批量导入弹窗的源端口默认填 443，仍可修改
- [x] `docs/guide/sni-routing.md`、`rules.md`、`cloudflare-cdn.md` 与新流程一致
- [x] 纯函数逻辑（拨开关、恢复端口、置灰判定）有单元测试

## Comments

**2026-09-14** — 实现完毕，面板版本推到 `3.2.1`（纯面板改动，Agent 与 FXP runtime 不动）。

落点：
- `client/src/lib/sniRuleForm.ts` —— 开关的纯逻辑（拨动、还原端口、置灰判定、域名格式），配 `sniRuleForm.test.ts` 14 条单测。
- `client/src/pages/Rules.tsx` —— 开关 UI、端口锁定与折叠入口、域名框条件渲染、跳过端口探测、保存校验。
- `server/routers/rules.ports.ts` —— 新增 `rules.checkSni`，只做域名维度判定，不碰端口策略与端口占用。

实现期间补了一个规格里没写的防护：承载资源列表尚未加载完时，`sniToggleSupport` 返回 `pending`，此时「不支持」只是暂时结论，不能据此清空正在编辑的规则的 SNI 域名。否则在隧道列表加载完成之前打开编辑弹窗，规则的域名会被静默抹掉。

未做浏览器实机验证：类型检查、`vite build` 与全部相关单测通过，但没有在运行中的面板里截图确认视觉效果。

**2026-09-15** — 代码评审提出两项，均成立，已修。

**预检越界（对应规格「开关打开时不做端口探测，改做域名校验」）。** 初版 `checkSni` 直接复用了 `assertSniEntryPortCanUseSni`，而该断言除域名重复外还报两种端口维度的冲突（入口端口被普通规则占用、被其它承载资源的分流组占用），结果是端口错误显示在 SNI 域名输入框下方。现在预检只读 `duplicateRule`，端口维度的判定留给保存时的服务端校验。新增 router 级测试 `checkSni only reports domain duplicates, never entry-port occupancy` 钉住这条边界，并已确认把旧逻辑放回去时该测试会失败。

**重复实现。** `excludeRuleIds` 的展开在三个 procedure 里逐字重复，转发组与隧道的 SNI 状态查询也各写了一遍。抽出 `resolveExcludeRuleIds` 与 `loadSniEntryPortState`；后者返回 `duplicateRule`、`shareableRuleIds` 和一个完整断言闭包，调用方各取所需，判定口径只有一份。域名重复的文案也收口到 `sniEntryPort.ts` 的 `sniDomainDuplicateReason`，两处断言复用它。
