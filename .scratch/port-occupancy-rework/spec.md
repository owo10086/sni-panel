# 端口占用检测：只核实规则真正用到的端口

**Status:** ready-for-agent

**Supersedes:** `.scratch/sni-port/spec.md` 中与端口占用有关的全部内容。该规格已于 3.1.0 实现并上线，本规格修正它的核心缺陷并撤除其中一部分能力。

## Problem Statement

3.1.0 上线的端口占用检测，在最需要它的主机上完全不工作。

管理员打开创建规则表单，源端口旁边恒定显示「未核实」，下面写着「主机 1：主机端口信息未经核实；主机 2：主机端口信息未经核实」。两台主机都在线、Agent 都是当前版本、心跳就在几十秒前——按规格，这个状态本该只在主机离线或 Agent 过旧时出现。规则卡片上同样如此：每一条规则旁边都挂着一个灰色感叹号，写着同一句话。

**原因已在真实环境中核实。** 那台入口主机上有 732 个监听端口，其中 704 个属于一套与 ForwardX 无关的中转节点客户端，另有 25 个属于第三套系统，ForwardX 自己只占 1 个。端口占用快照有 256 条上限，装不下，于是按规格要求「优先裁掉最不可能被问到的条目」挑着报：保住受管监听、80、443 以及 10000-49151 这一段，把 22 这样的低位端口排在后面丢掉。

丢完之后，Agent 要声明这份快照的完整性。它的算法是**取所有被丢弃条目中最小的端口号减一**——被丢掉的最小端口正好是 22，于是声明成「我只担保核实到第 21 号端口」。面板据此把 21 号以上的每一个端口判为未经核实，其中包括 443，尽管 443 的监听数据**好端端地留在那份快照里**，正是 Agent 特意保下来的。

于是这台主机上除了 1 到 21 号，没有任何端口能被核实，永远。同一套代码在另一台只有 31 个监听的主机上一直正常工作——不触发截断，结论完全正确。这就是缺陷长期没有暴露的原因：**它只在监听数量越过上限时发作，而越过上限的主机恰恰是最需要这项检查的主机**。

根因是上一版规格里两条互相矛盾的要求：

1. 截断时**优先裁掉最不可能被问到的条目**——这要求按「重要程度」排序，必然保高位丢低位；
2. 快照要**能表达自身是否完整**——这被实现成一个「我从 1 号一路核实到第 N 号」的单一界限，而这种表达只有在按端口号顺序截断时才成立。

两条都被忠实实现了。只要按重要程度挑，那句「核实到第 N 号」就会立刻塌到最低的那个被丢端口上。**截断策略与完整性表达落在了两个不同的维度上，这是本次缺陷的唯一根因。**

除此之外还暴露了第二个问题：即使快照正确，「未核实」这个状态在界面上也是一句笼统的话，它同时覆盖主机离线、Agent 过旧、采集失败、快照过期、时钟偏移、被截断六种处境——其中三种会自愈、三种需要人动手，而界面无法区分。管理员看到它时，得不到任何可执行的下一步。

## Solution

**把「核实整台主机」换成「核实规则真正用到的那几个端口」。**

Agent 不再上报全量监听清单，改为只上报**自己所有启用规则的入口端口**的占用情况。这个集合的规模由**这台主机上的规则数**决定，而不再由主机上无关进程的数量决定——暴露此缺陷的那台主机上是 4 条，对着 732 个监听。于是按重要程度排序的截断策略、按端口号表达的完整性界限、以及两者之间那个无法同时成立的不变式，一起删除。

**但「规模由规则数决定」不等于「永远装得下」。** 单台主机的规则数在数据模型里没有上限，同一个端口上也可以有多条监听，所以体积约束不能取消，只能换一种不会自相矛盾的表达方式——见下面「上报必须声明自己覆盖了哪些端口」与「体积约束」两节。

Agent 自身的**监听采集**动作不变：它本来就在跑全量监听扫描以判断受管运行时是否就绪（实测一台 732 个监听的主机上耗时 43-55 毫秒），本规格只改变**上报时的过滤**，不增加也不减少这一项的成本。规则端口集合在完整清单变化时于内存中重算；保活包只读取缓存，不为取得端口集合额外扫描磁盘——见「端口集合的开销约束」。

**同时，创建那一刻的端口检查整体撤除。**

这是一个有意的能力收缩。上一版规格把创建校验列为主线，为它贯穿六个表单入口、给校验结论加了第三态和确认入参。撤除的理由是：只上报规则端口之后，Agent 不再知道任意端口的占用情况，而为一个尚不存在的规则实时问一次主机，需要新的往返通道、Agent 在线依赖和一整套超时降级——成本高于它挽回的价值。取而代之的是「**先建，冲突了再在规则上报错**」：

| 转发方式 | 端口被外部占用时的表现 | 由谁负责 |
| --- | --- | --- |
| 用户态（realm / socat / gost / nginx / FXP） | 受管运行时 bind 失败，规则卡片显示**红色运行失败**并点名占用进程 | 3.1.0 已实现，保留 |
| 内核转发（iptables / nftables） | 规则仍在运行，卡片上显示**独立的黄色占用警告** | 本规格保留并收窄到这一类 |

**占用警告收窄到只对内核转发生效**，理由是用户态规则只要还在运行，就说明端口已被它自己 bind 成功，别人抢不走；真出问题只有一种形态，就是它起不来，而那已经是卡片上的红色失败。在用户态规则上再挂一个黄色警告，多数时候与红色失败说的是同一件事，少数时候是纯噪音（对方绑 `127.0.0.1`、自己绑 `0.0.0.0`，两条监听并存但并不冲突）。

内核转发相反：它不 bind，外部进程可以大大方方在同一端口上监听，而 DNAT 在 PREROUTING 就把入站流量截走——**两边都以为自己在正常工作，谁也不会报错**。这是唯一一种除了主动告知之外无法被发现的处境，也是这个警告存在的全部理由。

**「未核实」不再有任何界面出口。** 主机离线、Agent 过旧、采集失败时，规则卡片上什么都不显示。一个挂在每条规则旁边、永远不消失、只表示「我不知道」的灰色图标，会把管理员训练成彻底忽略这个位置——等它真的变成黄色警告那天，一样会被跳过。主机是否在线在主机列表里本来就看得见，不需要在每条规则上重复一遍。

## User Stories

1. 作为管理员，我想让端口占用检测在监听数量很多的主机上照样工作，从而不会因为主机上跑着别的系统就失去这项保护。
2. 作为管理员，我想让这项检测的成败与主机上无关进程的数量无关，从而它的可靠性可以预期。
3. 作为管理员，我想让面板只核实我的规则真正用到的那几个端口，从而不必为一项检查上传整台主机的监听清单。
4. 作为运维，我想让上报内容的体积与规则数量成正比、而不是与主机上的进程数成正比，从而心跳负担可控且可预测。
5. 作为运维，我想让 Agent 的监听采集动作维持原样，从而这次改动不增加主机上的扫描开销。
6. 作为管理员，我想让内核转发规则的入口端口被外部进程监听时得到一个明确的警告，从而这种双方都不报错的处境能被发现。
7. 作为管理员，我想让这个警告是一个与运行状态并列的独立标记，从而仍在正常工作的内核转发规则不被误报成故障。
8. 作为管理员，我想让这个警告在规则卡片显示为绿色、延迟正常时依然可见，从而不被运行状态掩盖。
9. 作为管理员，我想让这个警告覆盖本功能上线前就已存在的规则，从而不需要为了得到保护而重建它们。
10. 作为管理员，我想让警告在占用消失后自动消失，从而不需要手动清理。
11. 作为管理员，我想让用户态转发规则因端口被占而起不来时，卡片上直接显示占用者是谁，从而不必去翻 Agent 日志。
12. 作为管理员，我不想在用户态规则上同时看到红色失败和黄色警告，从而同一件事不被说两遍。
13. 作为管理员，我想在主机没能上报端口信息时，规则卡片上什么都不显示，从而那个位置上的图标一旦出现就一定意味着真有占用。
14. 作为管理员，我想让主机是否在线只在主机列表里表达一次，从而不必在每条规则上重复看到同一个事实。
15. 作为管理员，我想让创建转发规则时不再做主机端口占用检查，从而填表过程不被一个我无法处置的「未核实」标记打断。
16. 作为管理员，我想让源端口输入框回到只判断「这个端口在面板里有没有被别的规则占用」，从而它的结论稳定且可解释。
17. 作为管理员，我想让同一主机同一端口不能建两条规则这条约束继续生效，从而面板内部的一致性不受本次改动影响。
18. 作为管理员，我想让批量导入不再因为主机端口占用而失败或改写结论，从而导入行为与单条创建保持一致。
19. 作为管理员，我想让随机端口分配回到只避开面板已知的端口，从而它的结果不依赖一份可能取不到的主机数据。
20. 作为管理员，我想让修改规则源端口、启用此前停用的规则时同样不做主机端口检查，从而各个入口的行为一致。
21. 作为管理员，我想在内核转发规则的端口出现占用时收到 Telegram 提醒，从而不必盯着面板也能知道。
22. 作为管理员，我想在占用者换人时也收到一次提醒，从而让位这件事不被静默吞掉。
23. 作为管理员，我想在占用消失后收到一条解除提醒，从而知道这件事可以收工。
24. 作为管理员，我不想因为 Agent 掉线就收到一批「占用已解除」的好消息，从而观测中断不会被说成问题已解决。
25. 作为管理员，我想让同一个持续存在的占用只提醒一次，从而不被重复打扰。
26. 作为管理员，我想让占用者反复起停时仍受冷却窗口保护，从而不被刷屏。
27. 作为管理员，我想让这条提醒沿用规则上既有的开关，从而不增加新的配置项。
28. 作为管理员，我想让提醒的措辞与「运行异常」明确区分，从而不把一个仍在工作的规则误读成故障。
29. 作为普通用户，我想在自己无权查看主机细节时仍能知道端口存在占用，从而不因权限差异拿到误导性的结论。
30. 作为普通用户，我不想看到主机上其它进程的名字，从而不越权获知与我无关的主机信息。
31. 作为运维，我想让面板遇到尚未升级的旧 Agent 时静默忽略它上报的旧格式数据，从而升级过程中不会出现错误结论。
32. 作为运维，我想让主机升级 Agent 之后警告自动恢复，从而不需要任何手工干预。
33. 作为运维，我想让面板重启后警告在下一个心跳周期内自动恢复，从而重启不需要额外操作。
34. 作为维护者，我想让上一版规格中已被撤除的能力在文档里被明确划掉，从而后来的人不会照着一份过时的规格重建它。
35. 作为维护者，我想让「截断策略与完整性表达必须落在同一维度」这条教训被记录下来，从而同类缺陷不再发生。
36. 作为维护者，我想让领域词汇表跟着更新，从而「端口占用快照」这个词的定义与实际含义一致。
37. 作为管理员，我想让上报内容说清楚它核实过哪些端口，从而「没核实到」不会被当成「没人占用」。
38. 作为管理员，我想在规则刚建好、上报还没跟上时不收到「占用已解除」的提醒，从而观测缺口不会被说成问题已解决。
39. 作为管理员，我想让 Agent 从完整的期望启用规则清单计算端口集合，从而不需要执行动作的存量规则、以及启用了却起不来的规则都不会被漏掉。
40. 作为管理员，我想让数据过期时卡片上那条旧警告消失，从而看到的警告一定是有人核实过的。
41. 作为管理员，我想让占用者换人时旧的提醒状态被正确接替，从而不残留永远不会被清理的记录。
42. 作为管理员，我想让一条因端口被占而起不来的规则，其端口照样在核实范围内，从而最需要查明占用者的那个端口不会恰好被漏掉。
43. 作为管理员，我想让新增一条端口空闲的规则也能及时得到结论，从而不会因为占用条目没变化而一直停在未经核实。
44. 作为管理员，我想让采集只读到一半时不被当成读全了，从而只在 IPv6 上监听的端口不会被判成无人占用。
45. 作为运维，我想让上报在装不下时丢弃整个端口并如实缩小覆盖范围，从而「装不下」永远不会变成「谎称核实过」。
46. 作为管理员，我想让警告在两次上报之间保持稳定，从而不会因为新鲜期和心跳周期相等而周期性地闪现和消失。

51. 作为运维，我想让规则端口集合的计算带缓存，从而保活包不会为了这项检查每几秒扫一次磁盘。
52. 作为维护者，我想让上一版规格的工单也被标记作废，从而不会有人捡起一张已经不作数的工单照着做。

## Implementation Decisions

### 上报内容：从全量清单改为规则端口

Agent 每次心跳上报的不再是整台主机的监听清单，而是**自己所有启用规则的入口端口**上的占用情况。

**端口集合由 Agent 自己算，面板不发起按需询问。** 面板沿现有心跳响应及 SSE 推送同步一份完整的期望启用规则清单；这是配置状态，不是为创建规则临时下发的问题清单，也不增加一次往返。

**现有的三份数据都不能单独作为完整来源：**

- **本次的动作列表**只含需要变更的规则，不需要动作的存量规则全部缺席——而那恰恰是持续监测最主要的服务对象。
- **面板下发的「已运行规则」清单**按「已启用**且**已在运行」过滤。一条启用了、但因为端口被别人占着而起不来的规则**不在这份清单里**——这正是最需要查明占用者的那个端口。拿它当来源，会让整套机制在它唯一真正被需要的场景里失灵。
- **Agent 的本地运行时规则状态**用于报告已经配置的规则是否就绪；未曾成功应用的规则可能没有本地标记。它也不能独自判断标记对应的规则现在是否仍被启用。

现有 `desiredState` 仅含待执行的 `Actions`，持久化记录也只有动作签名及成功状态；Agent 当前并未持有完整的启用规则集合。因此必须新增一份**完整替换式的期望启用规则清单**，由面板从该主机实际应生效的启用规则构造，不以 `isRunning` 或动作是否产生为过滤条件。每条至少包含规则标识、该主机实际使用的入口端口、传输协议及转发方式；隧道与 SNI 分流仍按该主机的有效入口端口计算。

清单作为独立的带签名状态段随现有心跳及 SSE 同步，沿用状态段的按签名省略机制。该状态段同时携带由面板维护、随配置更新单调递增的修订号，面板重启后也不能回退。

**「重启后不能回退」要求这个修订号有一个明确的存放位置，而现有的状态段签名都是每次请求现算、不落盘的，没有现成的家。** 工单必须把它定下来，二选一：

- **落库**：在主机维度存一个计数器，随该主机的启用规则集合变化递增。行为最直白，代价是多一次写。
- **不落库的等价物**：修订号取「面板启动标识 + 进程内递增序号」的有序组合，Agent 按字典序比较。面板重启后启动标识增大，整体仍然单调，不需要持久化。

不允许的做法只有一种：直接用一个进程内的整数计数器——它在面板重启后从头开始，Agent 会把新清单当成旧推送丢掉，而且丢得无声无息。Agent 记录已经见到的最高修订号，低于该修订号的心跳响应或 SSE 推送不能覆盖较新的状态；收到修订号不低于已见最高值、签名校验通过的完整清单时原子替换内存清单，包括明确下发的空清单和同修订号的合法补传。

面板省略清单时仍下发修订号与签名：签名与 Agent 当前有效清单一致且修订号不旧，表示内容未变，保留内存清单并更新已见最高修订号。对不旧的修订号，签名不同却没有完整清单、清单不完整或签名校验失败时，记下修订号，撤销原清单的端口覆盖并清除下一次心跳通告的清单签名，使面板重新下发完整清单；即使之后收到更旧的完整推送也不能重新启用旧清单。Agent 重启后没有清单就声明空覆盖，随后在正常心跳中取得完整清单并恢复上报。规则创建、停用、删除或修改端口时，新的完整清单必须更新 Agent 的端口集合缓存和占用签名；保活包从内存读取该集合，不扫描本地状态目录。

**凡是在最新完整清单里处于启用状态的规则，其端口都参与上报，不以动作是否执行成功、运行时是否就绪为条件。** 清单仅用于占用端口集合，不写本地规则标记，也不改变规则就绪报告、流量统计或规则回收。一条首次 bind 失败的用户态规则仍报告未就绪，但它的端口能够被核实。

集合的构成：启用中的转发规则的入口端口与传输协议。停用的规则不报，因为启用时不再做端口检查，报了也没有消费者。

**用户态与内核转发的规则端口都要报，但理由不是「面板要从这份数据里查出占用者的名字」。** 那个名字不经过本规格：Agent 在本地从监听快照直接生成 `port N occupied by X` 随动作状态回报，面板解析那条消息得到它，与端口占用上报没有任何关系，两条路径也不得互相依赖。都要报的真正理由是**解耦**：哪些 `forwardType` 呈现占用警告是面板一侧的呈现决定（见工单 03），把它编进 Agent 的过滤条件，等于以后想调整呈现范围就要发一版 Agent。Agent 只负责如实核实自己所有启用规则的端口，呈现范围由面板收口。

每个条目仍然至少包含：端口、传输协议、绑定地址、可识别的进程名、是否属于受管运行时。**绑定地址必须保留**——只绑 `127.0.0.1` 的进程与绑 `0.0.0.0` 的进程对入站流量的影响完全不同。

### 上报必须声明自己覆盖了哪些端口

**删掉的是那个失效的覆盖界限，不是「声明自己覆盖了什么」这件事本身。** 两者必须区分清楚，否则会掉进本次缺陷的镜像版本。

上报内容除了占用条目，还要带一份**本次实际核实过的端口与传输协议的集合**。占用判定据此分三种结论，缺一不可：

| 端口在覆盖集合里 | 有匹配的监听条目 | 结论 |
| --- | --- | --- |
| 是 | 有 | 占用（附占用者） |
| 是 | 无 | **空闲**——确实核实过，确实没人 |
| 否 | —— | **未经核实** |

没有这份声明，「这个端口没被核实」与「这个端口没人监听」在数据上完全无法区分，判定只能把前者当成后者。**这不只是少一个标记的问题**：结论为空闲时占用警告会被清除，提醒判定会把占用者从「有」变成「无」，于是发出一条「占用已解除」——一个观测缺口被说成了一个问题被解决。规则刚建好、刚启用，而 Agent 的上报集合还没跟上时，这条假消息就会发出。

覆盖集合按**端口与传输协议逐条枚举**，与占用条目用同一套说法，不是一个范围界限。

**协议同时决定覆盖是否成立。** 规则的传输协议可以是 `both`，判定时会把 TCP 与 UDP 一起查。这种规则只有在**该端口的 TCP 与 UDP 都在覆盖集合里**时才算被核实；只覆盖其中一个，结论必须是未经核实，不能拿覆盖到的那一半当成整体答案。单协议规则只要求对应那一个协议被覆盖。这正是本次教训要求的那个不变式：**裁剪的维度与声明的维度必须是同一个**。任何时候上报内容因为任何原因少报了某个端口（完整清单尚未到达、单端口条目触顶、整份上报触顶、采集时该端口读取失败），那个端口就不能出现在覆盖集合里。

### 采集的完整性必须按传输协议与地址族分别判定

「本次采集是否成功」不能是一个整体的布尔值。主采集路径是一条命令，失败就整体失败，没有歧义；但**备用采集路径逐个读取多个内核文件**（TCP、TCP over IPv6、UDP、UDP over IPv6 各一份），现状是其中一份读不到就跳过，只要其余任何一份读到了监听，整份采集仍被标记为可用。

后果是一个**静默的半份事实**：IPv6 那份读取失败时，一个只在 IPv6 上监听的端口会表现得和「无人监听」一模一样，判定给出空闲，警告被清除，提醒发出一条解除。这与本次缺陷是同一类错误——声明的覆盖范围大于实际核实的范围。

因此采集要**按传输协议与地址族分别记录读取成败**，任何一族读取失败时，依赖该族才能判断的端口不得进入覆盖集合。实现上允许取保守做法：只要有任何一族读取失败，就把本次采集整体判为失败（覆盖集合为空），因为备用路径本身已是降级场景，不值得为它做精细的部分覆盖。

### 体积约束：两道上限，都必须反映进覆盖集合

同一个端口上可以有多条监听（IPv4 与 IPv6 各一条、绑在不同地址上各一条），所以受规则数约束的是**端口集合**，不是条目数；而单台主机的规则数在数据模型里也没有上限。因此保留两道上限：

- **单端口条目上限**：防止个别端口上的极端监听数量把上报撑大。
- **整份上报上限**：心跳请求体有大小限制，整份上报（占用条目**与覆盖集合一起**计算）必须在它之下留出余量。超限时**按端口成组丢弃**——丢就丢掉一个端口的全部条目及其覆盖声明，不做半个端口。

**上限必须按最终请求体计量，不能按占用数据自己的 JSON 字节数。** 心跳整包会被加密，密文再按十六进制编码放进信封——**编码后的体积是明文 JSON 的两倍**，信封外还有其它心跳字段一起挤在同一个请求体里。拿占用数据自己的 JSON 长度去对着服务端的请求体上限算余量，会至少差两倍。工单里给出的余量必须说明它是对着哪一个量算的。

**面板能接收的体积必须不小于 Agent 会发出的体积，这两个数要成对定义。** 现状是两侧各有一套独立的常量，谁也不知道对方是多少。一旦面板这一侧更紧，每一份合法上报都会被判非法——而按「兼容与发布」一节，被判非法的后果不是「这次没核实」，是把 Agent 推进每 2 秒一次的重发循环。

两道上限的处理方式相同，也是本规格唯一允许的处理方式：**被丢弃的端口必须同时从覆盖集合里去掉**，按未经核实处理。绝不允许出现「声称覆盖了某端口、却少报了它的条目」这种状态——那正是本次缺陷的形状。

**两道上限都要在工单里写成具体数字，并说明它是对着哪一个量算的。** 按实测数据，真实主机上每个端口平均不到两条监听，正常规模下离任一上限都差着数量级；现有实现的 256 条 / 32 KB 是可以直接沿用的量级起点，但 32 KB 这个数原本是对着占用数据自己的 JSON 算的，沿用前要按上面的计量基准重新核对一遍。

这两道上限是廉价保险，不是容量方案；它们存在的意义不是「装下更多」，而是**保证在装不下的那一刻，说出来的话仍然是真的**。

### 端口集合的开销约束

**端口集合从最新有效完整清单派生并缓存在内存中。** 保活包在有人查看主机指标时可以每 3 秒发送一次，但读取这份内存集合无需扫描本地规则目录或加载 FXP 配置。清单更新时立即重算集合并使占用签名随之变化；没有有效清单时覆盖集合为空，同签名省略清单时仍使用有效缓存，不从磁盘标记推测当前启用规则。

### 删除的机制

**删除的是「按重要程度裁剪 + 按端口号声明覆盖」这套组合，不是裁剪本身，也不是覆盖声明本身。** 这个区分必须写清楚，否则读者会以为上限被取消了——上限没有取消，见上一节的两道上限。

以下内容连同它们的测试一并删除，不保留开关、不保留兼容路径：

- 面向**整台主机全量清单**的条目数上限与字节上限（取而代之的是按端口成组丢弃的两道新上限）
- **布尔完整标志 + 单一端口号界限**这种表达覆盖范围的方式（取而代之的是逐条枚举的覆盖集合）
- 按重要程度排序的截断策略（受管 → 80/443/10000-49151 → 其余低位 → 高位）
- 判定中「该端口落在截断范围外时返回未经核实」这一条分支

**旧机制的矛盾不能靠调参解决，这也是它必须被整套替换而不是修补的原因。** 提高上限只是把发作点推后；改成按端口号顺序截断能让界限重新成立，却要牺牲高位端口的保护。只要「裁剪按重要程度、声明按端口号」这个组合还在，两者就永远对不齐。新方案保留了裁剪，也保留了声明，但把两者放在**同一个维度**上：裁剪以端口为单位，声明也以端口为单位，丢掉哪个端口就从声明里去掉哪个端口。这才是这条教训的落地方式——不是取消其中一个。

### 心跳字段与签名

保留独立字段、独立签名、「本次采集是否成功」标志这三项设计，它们与本次缺陷无关且仍然必要：

- 采集成功 + 签名一致 ⇒ 刷新最近核实时间，内容不变。
- 采集成功 + 签名不一致 ⇒ 面板要求补传完整内容。
- **采集失败 ⇒ 什么都不刷新。** 心跳到达本身不构成核实。

**签名的输入必须同时包含占用条目与覆盖集合，缺一不可。** 只对占用条目取签名会漏掉一整类变化：新增一条规则、它的端口上没有任何监听时，占用条目一个字没变，覆盖集合却多了一个端口。此时签名若保持原值，面板认为自己的缓存仍然有效、不会要求补传，Agent 也不会主动补传，于是**面板会一直按旧的覆盖集合判定那个新端口为未经核实**，而且没有任何机制能让它自己走出这个状态。空闲端口的加入与移除必须翻转签名。

签名的输入随上报内容一起收窄到规则端口。这带来一个附带的好处：主机上无关进程的起停不再翻转签名，补传频率随之大幅下降。

「最近核实时间」与「采集时刻」仍是两个不同的值，陈旧度判断用前者，并沿用仓库既有的「新鲜期 + 未来偏移容忍值」约定。

### 新鲜期必须明显大于上报周期

**面板的新鲜期与 Agent 完整心跳的周期现在恰好相等（都是 5 分钟），这是一个必须改掉的巧合。** 占用数据只搭在完整心跳与保活包上，更高频的存在性心跳不带它；而完整心跳带一个最多 10% 的向下抖动，所以实际刷新间隔落在四分半到五分钟之间，对着一个五分钟的窗口——**余量在 0 到 30 秒之间，由 Agent 的启动标识哈希固定下来**，再减去请求本身的耗时（实测一套真实部署上完整心跳需要 1.8-2.7 秒）。

后果是抖动系数接近零的那些主机，会在每个周期末尾短暂越过新鲜期。在旧设计里这个问题被完全掩盖——那台触发本次缺陷的主机上结论恒为未经核实，看不出来。在新设计里它会成为**剩下的主要失败形态**，而且症状正是本规格要解决的那一个：警告该在的时候不在，并且周期性地闪现与消失。

要求：**这两个常量不得继续相等。** 二选一即可——把新鲜期以实际上报周期为基准并留出明确余量（不少于完整心跳周期的两倍），或者让更高频的那类心跳也带上签名，使最近核实时间能在完整心跳之间被刷新。前者改动更小，推荐前者。

### 两侧的端口口径必须是同一套

**清单里那个端口，和面板拿去查覆盖集合的那个端口，必须由同一段推导算出来。** 这一条单独成节，因为面板现在这两处用的不是同一套：清单侧按「该主机实际使用的入口端口」算，隧道出口主机上得到的是出口端口；而警告侧直接取规则行上存着的 `sourcePort`，那是入口那台主机的端口。取规则的查询本身也不做逐主机换算，同一条规则在入口和出口两台主机上读到的 `sourcePort` 是同一个值。

两者一旦不一致，后果与本次缺陷同形：**Agent 覆盖了 A 端口，面板去查 B 端口，B 永远不在覆盖集合里，于是永远未经核实、永远不出警告，并且不报任何错。** 受影响的是 gost / nginx 隧道的出口规则——它们恰恰是内核转发之外最容易被外部进程撞上的一类。

因此要求：**「本主机有效入口端口」只有一处实现，清单构造与占用判定都调用它**，不允许任何一侧自己取 `sourcePort`。隧道入口与出口、SNI 分流、转发组成员各算各的有效端口，但都走这一处。

### 占用者归类与可复用判定

归类逻辑不变：区分**受管占用**（ForwardX 自己安装并托管的运行时）与**外部占用**（其余一切），且**受管不等于端口可用**——只有当规则要用的确实就是那个已存在的受管监听本身时才算可复用（同一入口端口上的多条 SNI 分流规则共用分流器的同一个监听即属此类，见 ADR-0002）。

归类只陈述客观事实，不下「算不算冲突」的结论；冲突判断按 `forwardType` 收敛在一处。本次改动后这一处只剩一个分支有实际产出：内核转发。

### 呈现规则

- **占用警告只对内核转发规则呈现。** 用户态规则不再产生占用警告。
- **未核实不产生任何界面标记。** 主机离线、Agent 过旧、采集失败、数据过期、该端口不在覆盖集合里时，规则卡片上不出现图标、不出现文字。
- **过期的警告要被隐藏，而不是继续展示。** 面板的警告缓存在上报失效时不会被刷新，里面留着的是上一次有效结论。规则接口必须在数据已不新鲜时**不再返回这些条目**，否则卡片上会挂着一条无人再核实的旧警告。这与下一节的提醒状态是两种不同的存活期，不能用同一份逻辑处理。
- 警告内容只陈述可核实的事实：该端口上存在监听、绑定地址、传输协议、管理员可见的进程名、采集时刻与最近核实时间。**不得断言原监听进程将收不到数据**——对一个只绑 `127.0.0.1`、只服务本机客户端的进程来说这句话是错的。
- 警告是与运行状态并列的独立标记，不得写进规则的运行状态字段。内核转发规则在有警告时仍显示为运行中。
- 权限边界不变：进程名只给管理员，普通用户得到不含进程名的说法，两份内容在服务端分别构造。

### 提醒状态的形状与存活期

**状态键必须是稳定的，占用者身份是它的值，不是它的一部分。** 键取「规则 + 入口主机 + 端口 + 传输协议」，占用者身份（进程名、绑定地址、受管实例标识）作为与该键关联的值保存。判定靠**比较同一个键的前后两个值**得出三种转移：无 → 有（占用出现）、有 → 另一个有（占用者换人）、有 → 无（占用解除）。

把占用者塞进键里会同时坏掉两件事：占用者从 A 换成 B 时产生一个新键，A 那个键再也不会被访问到、永远留在内存里；而 B 消失时，判定看到的是「B 这个键从有变无」，A 是否还在无人知晓——解除提醒可能发错，也可能永远不发。

**存活期与界面相反：数据失效时提醒状态要保留，不能清空。** 上报缺失、采集失败、数据过期、端口不在覆盖集合里——这些处境下判定**不产生任何转移**，上一次的有效占用原样留着，直到一份明确显示占用已经不在的有效上报把它翻成解除。界面在这些处境下什么都不显示，提醒状态却记得占用还在：**前者回答「现在能不能告诉用户」，后者回答「上次确定的事实是什么」**，两个问题不同，答案自然不同。

既有的冷却窗口留在最外层，与变化检测各司其职：变化检测负责「该不该发」，冷却负责「占用者反复起停时别刷屏」。

### 创建路径的撤除范围

以下与**主机端口占用**有关的行为全部删除：

- 源端口输入框旁的 可用 / 有占用 / 未核实 标记及其下方的说明文字
- 提交时因外部占用而拒绝创建（用户态转发）
- 提交时因外部占用而要求显式确认（内核转发），以及承载它的确认入参
- 批量导入中的同类检查
- 随机端口分配对主机已知占用端口的避让
- 修改源端口、启用停用规则时的同类检查

以下行为**保留**，它们与主机占用无关：

- 面板数据库层面的端口唯一性校验（同一主机同一端口不能建两条规则、隧道端口冲突、SNI 分流规则共用入口端口的既有规则）
- 端口范围策略与套餐端口范围校验
- 受管运行时 bind 失败时的规则级错误回报

### 兼容与发布

面板**不为旧格式保留兼容路径**。新版 Agent 在完整心跳与保活包里都携带独立的 `portOccupancySchemaVersion: 2`，包括没有完整快照或本次采集失败的心跳。旧版 Agent 没有此字段；面板忽略它的旧结构及后续只有签名的简报，令该主机原有的占用缓存失效，也不要求补传。升级后，新版 Agent 在后续正常心跳中重新取得有效快照，无需解析旧格式或保留旧判定逻辑。

**旧版忽略与新版校验失败必须分开处理。** 现状是面板要求补传后，Agent 会把下一次心跳间隔压到 2 秒；若旧结构每次都被拒绝且每次都要求补传，就会形成持续重发。旧版及未知版本的心跳始终不要求补传，也不得用旧签名重新核实缓存。

新版 Agent 的完整快照若因字段非法或超过面板的占用字段接收上限而被拒绝，面板立即把该主机判为未经核实，记录被拒绝的签名，**不能在下一次同签名简报到达时重新启用旧快照**。拒绝当次不要求立即补传；对于随后持续上报的同一签名，按主机设置至少 5 分钟的补传冷却时间。冷却时间到期后的正常心跳可以要求一次完整补传；如仍不合法，重新开始冷却时间，不能形成每 2 秒一次的持续重发。Agent 主动上传的合法新快照可随时清除拒绝状态。面板没有该签名的有效缓存时，同样遵守这一冷却规则，而不是每次收到简报都立即索取完整内容。

改动涉及 Agent，按仓库既有的版本规则，面板与 Agent 一起推小版本位，ForwardX FXP runtime 跟随 Agent。

## Testing Decisions

好的测试只验证外部可观察的行为：给定的上报内容下，管理员在规则上看到什么、规则能不能建出来、提醒发不发。不测内部函数怎么拆、缓存长什么样。

三道缝，全部沿用现有缝，不新增。

### 缝一：面板（上报 → 结论 → 界面）

起真实 sqlite、心跳路由与 tRPC 规则路由的子进程测试，一条链路走完：Agent 上报规则端口的占用 → 面板派生结论 → 从规则接口读回时警告出现或不出现。

必须显式断言的行为：

- 内核转发规则的入口端口上存在外部监听时，**运行状态保持为运行中**，同时规则上带出占用警告——两件事缺一不可。
- 用户态规则的入口端口上存在外部监听时，**不产生占用警告**；该规则报告未就绪时，其卡片上的运行失败信息里含有占用者名字。
- 主机未上报、上报采集失败、数据过期时，规则上**不出现任何标记**，且不呈现为端口空闲。
- **端口不在覆盖集合里时判定为未经核实，不判定为空闲**；界面上不出现结论，提醒状态里上一次的有效占用不被清除，也不触发解除提醒。
- **规则集合变化期间的回归用例**：先上报一份覆盖旧规则端口的内容并造出一条占用警告，再新建或启用一条规则，在 Agent 的上报集合尚未跟上的那一轮，断言新规则上不出现任何结论、且**不发出解除提醒**。
- 数据已不新鲜时，规则接口**不再返回**缓存里那条上一次的有效警告。
- **新鲜期与上报周期的关系**：上报之后经过一个完整心跳周期、下一次上报尚未到达时，结论仍然有效——断言警告不会因为两个常量相等而在周期之间翻转。
- 协议为 `both` 的规则只有一个协议在覆盖集合里时，结论为未经核实。
- **隧道出口规则的端口口径回归用例**：一条经 gost / nginx 隧道的规则，在出口主机上的有效端口与它行上存着的 `sourcePort` 不同；断言该主机上报的覆盖集合与面板查询的端口是同一个，出口端口上存在外部监听时警告能正常出现。不写这条，两侧口径一旦分家不会有任何测试发现。
- 同一入口端口上的多条 SNI 分流规则不因分流器自身的监听而产生警告（ADR-0002 的回归用例）。
- 普通用户读到的结论不含进程名。
- 创建、更新、启用规则以及批量导入**不再因主机端口占用被拒绝或要求确认**；面板数据库层面的端口唯一性校验仍然拒绝重复端口。
- 面板下发的完整期望启用规则清单包含从未启动成功的规则，也包含不需要执行动作的存量规则；停用及删除后清单及时移除对应规则，Agent 重启后可重新取得完整清单。
- **面板重启后修订号不回退**：重启前后各下发一次清单，断言后一次的修订号严格大于前一次，Agent 不会把重启后的新清单当成旧推送丢掉。
- 旧版 Agent 的完整上报及后续同签名简报均被忽略，不产生占用判断、不报错、**不要求补传**；升级到带版本字段的 Agent 后自动恢复。
- 新版 Agent 上报非法快照后，同签名简报不能重新核实旧缓存；冷却时间内不要求补传，冷却时间后只要求一次，合法完整快照恢复占用判断。超过面板占用字段接收上限时遵守同一规则，并断言「面板接收上限 ≥ Agent 发送上限」。

**Prior art**：`server/portOccupancyHeartbeat.test.ts` 与 `server/rulesPortAvailability.test.ts`——两者都以真实数据库 + 路由的子进程形式运行，前者已挂载心跳路由并在其后用 tRPC 读回结论，新用例照此扩展；后者中与主机占用有关的断言随实现删除。

### 缝二：Agent（上报内容的构造）

Go 单测，断言上报内容只含最新完整期望启用规则清单中该主机实际使用的入口端口、保留绑定地址与进程名、TCP 与 UDP 分开、IPv4 与 IPv6 分别识别、采集时刻带上，且**不再出现布尔完整标志与按端口号表达的覆盖界限**——取而代之的是逐条枚举的覆盖集合。

另需断言，这三条都是本次缺陷的直接回归用例：

- 主机上存在大量与规则无关的监听时，**上报覆盖的端口集合只随规则集合变化**，与主机上无关监听的数量无关。注意被约束的是端口集合而不是条目数——同一端口上 IPv4 与 IPv6、不同绑定地址各算一条。
- 覆盖集合与占用条目一致：集合里的端口都被实际核实过，因单端口条目触顶或采集失败而未能完整读取的端口**不出现在集合里**。
- Agent 重启后尚未收到完整清单时覆盖集合为空；收到明确的空清单后仍为空，不借助本地标记猜测当前启用规则。
- 一条已启用但尚未就绪的规则，其端口仍在覆盖集合里；不需要执行动作的存量规则也在集合里。
- **从首次 apply 失败起算**：一条在完整清单里已启用、但动作从未执行成功过的用户态规则（第一次就因端口被占而 bind 失败），其入口端口仍进入覆盖集合；Agent 重启并重新取得清单后仍能报告该端口。
- 收到较新的清单后端口集合和签名随之更新；停用、删除及修改源端口后旧端口退出集合，较旧的心跳响应或 SSE 推送不能覆盖新清单。
- 同签名省略清单时保留有效缓存；签名变化却缺少完整清单或清单不完整时覆盖集合为空且下一次心跳不通告旧签名，同修订号的合法完整补传能恢复覆盖；此时迟到的旧修订号完整推送不能使旧端口重新进入覆盖集合。
- 签名同时随占用条目与覆盖集合变化：**加入一个没有任何监听的规则端口时签名翻转**，移除时同样翻转。
- 备用采集路径下某一传输协议或地址族读取失败时，本次采集不得被标记为完整；受影响的端口不出现在覆盖集合里。
- 单端口条目触顶、整份上报触顶时，被丢弃的端口同时从覆盖集合里消失，且丢弃以端口为单位、不出现半个端口。
- 整份上报上限按**最终请求体**计量：断言在占用数据与其它心跳字段同时存在、且经过加密与十六进制编码（体积翻倍）之后，请求体仍在面板接收上限之下。
- 规则端口集合缓存在内存：连续两次保活包不重新读取本地规则状态，收到清单变更后下一次保活包使用新集合。

**Prior art**：`agent/port_occupancy_test.go`——以构造的监听快照驱动上报结构的既有测试，删除截断相关用例，补上端口集合过滤的用例。

### 缝三：提醒触发判定

纯函数地驱动提醒判定并断言真假，不发真实消息。覆盖：同一占用持续存在只发一次、占用者换人算一次新变化、占用消失发出解除提醒、**未核实不触发解除提醒**、冷却窗口仍在最外层生效、范围只含内核转发规则。另需断言状态形状：键稳定、占用者作为值参与比较；占用者换人后旧值被接替，不留下新旧并存的记录。

**Prior art**：`server/forwardRuleErrorNotifier.test.ts`。

### 明确不为此单开缝

「Agent 该报哪些端口」这个集合的计算、以及占用者归类，都是纯逻辑且没有独立的用户可见行为，其正确性完全体现在缝一与缝二的结论上，不单开缝。

## Out of Scope

- **提交时向 Agent 实时探测端口。** 本规格已明确撤除创建时的主机端口检查，不以任何形式（往返问答、按需探测、预热缓存）重新引入。
- **把主机上所有监听端口做成一个可浏览的页面。** 上报内容已收窄到规则端口，面板不再持有全量数据。
- **为「未核实」区分原因并在界面上分别提示。** 界面上已不存在未核实这个出口，区分它的原因失去意义。
- **自动停止占用端口的外部进程。** 面板不代管不属于它的进程。
- **自动推荐替代端口。**
- **历史占用记录与趋势。** 只保留最近一次上报。
- **为端口占用警告单独设一个提醒开关。** 沿用规则上既有的开关。
- **凭占用信息自动停用或修改已有规则。** 只告知，不代替管理员处置。
- **非 Linux 主机。** 采集依赖 `ss`。
- **容器内端口占用的穿透判断。** Agent 看到的是宿主机视角。
- **为旧版 Agent 保留兼容路径。**

## Further Notes

**这个缺陷是在真实环境中定位的，不是推演出来的。** 暴露它的入口主机上有 732 个监听端口，其中 704 个属于一套与 ForwardX 无关的中转节点客户端。同一套代码在另一台 31 个监听的主机上结论完全正确。**故障条件是「主机上无关监听的数量」，而这个变量在任何测试环境里都不会自然出现**——上一版规格的四道测试缝全部通过，功能在上线后的第一个真实环境里就失效了。补上的回归用例（缝二那条「覆盖的端口集合只随规则集合变化」）针对的正是这个变量。

**教训：截断策略与完整性表达必须落在同一个维度上。** 上一版规格同时要求「优先裁掉最不可能被问到的条目」（按重要程度排序）与「快照能表达自身是否完整」（按端口号表达一个覆盖界限）。两条单独看都合理，合在一起构成一个无法同时成立的不变式：只要按重要程度挑，就必然保高位丢低位，那个按端口号表达的界限就会塌到最低的被丢端口上。**任何时候一份数据既要被有选择地裁剪、又要声明自己覆盖了什么，裁剪的维度与声明的维度必须是同一个**——否则声明会在裁剪生效的那一刻变成一句无意义的话，而且是偏向「更少覆盖」的那一侧，悄悄把整个功能关掉。

**一项能力被有意撤除，理由记录在此以免回退。** 创建时的主机端口占用校验（上一版规格的主线之一，贯穿六个表单入口）在本规格中整体删除。撤除的直接原因是上报内容收窄后，Agent 不再持有任意端口的占用信息；根本原因是这项校验的价值低于它的成本——用户态规则端口被占时必定 bind 失败并在卡片上点名占用者，内核转发规则被占时有持续警告，两条路都能在事后给出准确结论，而事前校验要为此维护一条实时问答通道、一个第三态结论和一套确认入参。**如果将来要重新引入，必须先回答：它比「先建、冲突了再报错」多提供了什么。**

**「未核实」在界面上彻底消失是一个有意的取舍。** 上一版规格坚持「绝不把未知呈现为空闲」，方向正确，但它在规则卡片上的落地形态是一个挂在每条规则旁、永不消失、只表示「我不知道」的灰色图标。当主机因任何原因不上报时，这个图标出现在该主机的每一条规则上，训练管理员彻底忽略这个位置——等它真的变成黄色警告那天，一样会被跳过。**一个永远亮着的警示灯不提供信息，只消耗注意力。** 现在这个位置只有真正存在占用时才会出现东西。

**与 ADR 的关系。** 本规格不与 ADR-0001、ADR-0002 冲突。ADR-0002 放开的「SNI 分流规则共用入口端口」仍然是最容易被这项检查误伤的能力，缝一的回归用例必须保留。

**工单顺序。** 01（上报内容改写）是其余工单的地基。02（撤除创建校验）与 01 无代码依赖，可并行，但它同时删掉 01 的一部分消费者，合并时要注意不要互相踩。03 依赖 01，04 依赖 03。05 最后做。

**01 里有一处不是纯删减。** 新增的完整期望启用规则清单只供端口集合计算，不写 Agent 的本地规则标记，也不参与流量统计与规则回收。启用规则即使从未应用成功，也要持续保有端口占用核实资格；停用或删除后则由新清单撤销这一资格。
