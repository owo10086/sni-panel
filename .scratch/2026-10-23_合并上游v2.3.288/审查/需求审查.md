**必须解决的发现**

**R1｜P2｜指定告警收件人的内嵌用户 ID 缺少迁移映射要求**

- **规格位置：** [spec.md:52](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-23_合并上游v2.3.288/spec.md:52)、[spec.md:55](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-23_合并上游v2.3.288/spec.md:55)、[spec.md:79](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-23_合并上游v2.3.288/spec.md:79)。这些位置要求纳入逐主机配置、数据库迁移和权限验证，但没有明确 JSON 内指定收件人的身份映射及验收结果。
- **固定代码证据：**
  - `U:shared/operationsMonitor.ts:5` 定义 `notifyUserId`。
  - `U:server/operationsMonitor.ts:33` 将整个配置写入 `hosts.resourceAlertConfig` JSON。
  - `U:server/migration.ts:1147` 从源行复制字段；`:1156` 的 `hosts` 分支只映射 `row.userId`，保留 `resourceAlertConfig` 原文。
  - `U:server/migration.ts:1868` 根据目标已有数据选择增量导入；`:2036` 记录源 ID 到新 ID 的映射，说明迁移前后用户 ID 确实可能不同。
  - `U:server/operationsMonitor.ts:77` 直接以 `settings.notifyUserId` 查询目标库用户，再发送包含主机名称、资源指标及告警状态的通知。
- **用户后果：** 例如，源面板指定收件人甲为用户 `7`，迁入目标库后甲映射成 `42`，目标库原有用户乙恰好是 `7`。如果原样复制 JSON，后续告警会查询乙并可能发送给乙；若目标库没有 `7`，则指定收件人收不到通知。有效账号和渠道绑定检查无法识别这种身份错配。
- **具体推荐：** 在现有唯一规格中补充：需要重映射 ID 的导入，必须解析 `resourceAlertConfig`，将非空 `notifyUserId` 按本次用户映射转换；原本为空的配置继续保持上游所有者回退语义。映射缺失时不得沿用原数字，也不得静默改成所有者；应按现有迁移依赖缺失机制明确报错或记录拒绝结果。保持 ID 的快照迁移应保留原身份关系。
- **必要验收：** 增加“源用户 ID 与目标用户 ID 不同、旧数字已属于另一有效且绑定通知渠道的账号”的隔离场景；确认最终配置指向映射后的账号，旧数字对应账号不会收到通知，同时覆盖空收件人及映射缺失情况。
- **处理性质：** 这是实现 Q2 已选收件人语义所需的兼容补齐，无须重新询问 Q2。若主代理拟以清空配置、改收件人或丢弃配置替代身份映射，则属于新的行为取舍，应按本轮**默认模式**记录影响并等待用户决定。

- **真实位置：** [spec.md:64](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-23_合并上游v2.3.288/spec.md:64) 写为“SNI 落地结果缺失/过期/失败不单独阻止入口/DDNS/切换”。
