# SNI 转发组 DDNS 健康判断调整

**状态：** 规格草案，待用户确认。\
**日期：** 2026-10-12。\
**当前授权：** 撤回本轮提前实施的修改，只编写规格。方案同意、规格确认、开单和实施是不同步骤；本文件不代表实施授权。本次尚未创建工单。

## 一、要解决的问题

主机型转发组已经可以承载多条共用入口端口的 SNI 规则，但当前健康判断仍要求每条规则都有落地目标的检测结果。

本次远程排查发现：每台入口有 12 条共用 443 的 SNI 规则，自动检测只产生其中一条代表规则的结果，其余规则没有检测记录。两台入口在线，配置的 `www.bing.com:80` 检测也已经通过，但面板仍等待规则检测结果，转发组的新域名没有得到 DDNS 更新。

用户确认此次要解决的是**入口故障转移**：入口能够正常提供 SNI 分流、现有入口健康条件满足时，不应因某个落地目标失败或缺少单条规则的检测结果，卡住整个组的 DDNS。

## 二、已经确认的方案

SNI 成员取得切换资格，需要同时满足：

1. **入口 Agent 在线。** 沿用现有在线和离线判断。
2. **应运行的 SNI 分流规则已经准备好。** 分流程序正常运行，相关规则的最新配置已经生效。
3. **已开启的国内健康检测通过。** 继续使用组内设置的检测目标，例如 `www.bing.com:80`；没有开启时，不额外要求这一项。

以上条件满足后，曾发生故障或失去有效分流确认的入口，还须完成第五节规定的恢复观察，才能取得自动故障切换或自动切回资格。

**SNI 落地目标的连接结果不再作为这项资格的条件。** 缺少、过期或失败的目标检测结果，都不能单独阻止 SNI 入口参与 DDNS，也不能单独触发整组切换。

这项判断继续使用已有 Agent 上报和面板调度。本次不增加从外部连接入口 443 的检测，也不增加检查机器或新的配置开关。

### 举例

首选入口 A、备用入口 B 都承载两个业务域名，共用入口端口 443。

- A、B 在线，分流配置已生效，已开启的 Bing 检测正常：A 可以作为当前入口，即使没有每个业务目标的检测结果，也能更新 DDNS。
- 某个业务目标停止服务，但 A 的分流和 Bing 检测正常：不因这个目标故障切换整个组。
- A 的分流程序停止，B 已准备好：按组内故障时间判断，满足切换条件后将 DDNS 指向 B。
- A 恢复：按面板恢复时间和“恢复后切回”设置决定是否回到 A。

## 三、调整范围

| 范围 | 本次要求 |
| --- | --- |
| 主机型转发组中的 SNI 规则 | 使用本规格的入口健康判断 |
| 普通转发组及普通规则 | 保持原有目标检测和故障转移行为 |
| 同组混有普通规则和 SNI 规则 | SNI 部分不再依赖目标检测；普通部分仍需通过原有判断，不因同组存在 SNI 而被放行 |
| 其他资源上的 SNI | 转发链、单机端口转发、隧道等不在此次调整范围内 |
| 规则停用、到期、限额、权限限制 | 沿用现有处理；只检查按现有规则应运行的分流内容 |
| 主机流量排除 | 保留现有超量退出与解析处理，不因入口网络正常而重新纳入 |

同一组可以有多个入口端口，本次不把端口写死为 443。所有应运行的 SNI 配置仍须确认生效，但不按端口或域名新增网络检测。

## 四、入口准备状态

以下情况不能被判为已准备好，也不能被选作新的当前入口：

- Agent 不在线或不满足现有 SNI 能力要求。
- 分流程序未运行，或应运行的规则尚未补齐。
- 域名存在，但仍使用旧的目标地址、目标端口或限制设置。
- 新配置保存成功，但入口尚未确认应用成功。

配置确认继续以现有实际运行状态为依据。仅有“保存成功”“命令已下发”“端口存在”或“曾经应用成功”的记录不够。

### 运行确认何时有效、何时失效

1. **在线与分流正常分别确认。** Agent 在线、Bing 检测正常，都不能代替分流运行确认。有效确认必须能证明当前入口上所有应运行的 SNI 配置正在运行，且与面板当前要求一致。
2. **确认离线后重新上线，或 Agent 重启后，重新取得确认。** 不能沿用离线或重启前的分流成功报告，也不能靠晚到的旧报告恢复资格。这里的离线沿用现有在线判断，不把未被判为离线的短暂通信波动额外算作一次故障。
3. **正常运行期间的确认也有有效期。** 沿用现有 Agent 健康结果的有效期（当前为 5 分钟），不新增开关。收到有效分流确认后才续期；只有在线信号、Bing 结果、命令回执，不能续期。沿用现有报告方式：入口明确确认运行内容未变化，且面板能对应到已核实的完整配置时，可以续期，不要求每次重复上传完整配置。面板缺少对应内容时，必须重新取得完整确认。
4. **确认失效后，立即停止授予新的入口资格。** 当前入口从确认失效时开始按面板故障时间观察；到期仍未重新确认且有合格备用时，执行切换。不能从稍后偶然收到报告时才开始计时，也不能因为持续在线而无限等待。已由其他条件完成的故障观察不重新计算。没有合格备用时，按第六节保留现有解析。
5. **首次等待与恢复等待分开处理。** 首次启用尚未收到分流确认时，不选作入口；之前有效、后来失效或被判故障的入口，重新确认正常后按第五节完成恢复观察。报告缺失期间不能累计为正常时间。

例如，B 曾经确认分流正常，随后离线。B 重新上线后，即使 Bing 已正常、面板保存的配置也没有改动，在取得本次上线后的有效分流确认前，仍不能把解析切到 B。确认后还须按恢复规则判断。

修改落地地址后，入口必须确认新配置生效；确认后不必再等新落地地址的连接检测。DDNS 更新期间发生配置变更，仍须保留现有再次核对的保护，不能凭旧判断宣布切换成功。

## 五、故障时间、恢复时间和切回

**故障观察时间和恢复观察时间全部读取面板设置，不固定为 30 秒、60 秒或其他数值。** 第四节的报告有效期用于判断报告还能不能作为依据，与这两项观察时间分别处理。保留现有成员优先顺序及自动切回开关的含义。

### 故障处理

1. 短暂异常处于既定观察时间内时，不随意切换。
2. 某项入口故障已经满足既定切换条件，且有健康备用入口时，按优先顺序选择备用。
3. Bing 一直正常，不能反复清掉分流程序故障的计时，使停止的分流器永远不触发切换。
4. 国内检测或其他保留条件已经完成故障观察时，不能因为分流程序刚出现另一个故障，就把已经到期的故障时间重新计算一遍。

### 恢复处理

1. 分流程序刚恢复，不能借用“Bing 一直正常”的时间，提前认定分流程序已稳定足够久。分流恢复观察从重新取得有效运行确认时开始；观察期间再次故障或确认失效，已累计的本轮分流恢复时间清零，下次确认正常后重新观察。
2. 普通规则或国内检测已经按现有方式完成恢复观察，不能仅因同组存在始终正常的 SNI，再额外等待一轮相同恢复时间。
3. 开启自动切回时，满足全部恢复条件后回到优先级更高的健康入口；关闭时，继续使用当前健康备用入口。该开关只决定是否主动回到更高优先级入口，不免除恢复资格要求；当前入口故障时，即使关闭自动切回，也可以选择已经完成恢复观察的更高优先级入口。
4. 等待期间修改面板时间设置，应按现有设置更新后的规则判断；到期后的检查也必须正确安排，不能只能靠下一次偶然上报才能推进。
5. 面板重启或状态重新建立后，不能凭不完整的旧状态提前认定恢复完成。具体状态保存方式留待开单设计，本规格不预先指定缓存或数据库方案。

本节要求的是各类状态共同作用时的最终行为。沿用现有 Agent 和面板已完成的有效观察，不重复等待，也不能把一种状态正常的持续时间，当成另一种状态正常的持续时间。

### 首次启用、故障时选备用与恢复切回

| 情况 | 是否需要等待分流恢复时间 |
| --- | --- |
| 首次启用，此前没有该入口的分流故障或确认失效记录 | 首次有效确认全部应运行配置后，不额外增加一轮分流恢复等待；其他现有条件仍须满足 |
| 当前入口故障，候选备用曾发生分流故障、离线、重启或有效确认失效 | 候选备用必须完成恢复观察，不能因当前入口已坏而跳过 |
| 当前备用健康，准备切回曾发生故障的更高优先级入口 | 候选入口必须完成恢复观察，并遵守自动切回开关 |
| 面板重启或状态重新建立，无法证明之前的状态 | 不当作从未故障的首次启用；重新确认后完成恢复观察，有完整有效依据的已完成观察不重复等待 |

例如，恢复时间设为 120 秒，A 已故障到需要切换，B 的分流才重新确认正常 5 秒，则 B 还不能被选中。如果 C 已满足全部条件，按优先顺序选择合格的 C；如果没有其他合格入口，保留现有解析并显示等待恢复。B 持续正常满 120 秒且其他条件仍满足后，应自动重新判断是否切换，不等待下一次偶然上报。

## 六、DDNS 更新与失败处理

- 入口满足资格后，现有 DDNS 更新流程应正常执行。新建或更换入口域名时，即使选中的入口和地址没有变化，也不能仅凭旧域名的成功记录跳过新域名更新。
- 国内检测开启但结果缺失、过期或尚未确定时，不当作检测通过；继续使用现有等待或失败处理。
- 所有入口都不可用时，保留当前解析并等待恢复，不因为普通健康故障主动删除已有解析。现有流量超量排除属于原有特殊处理，保持原规则。
- 没有旧解析、没有可用地址等情况沿用现有失败处理，不新增放宽入口资格的机制。
- 解析服务更新失败时，不宣布切换成功；继续显示失败原因并沿用现有重试方式。
- 原有手动同步、成员排序、事件记录和已开启的切换通知继续适用，不新增管理入口。

## 七、状态说明

状态应反映实际阻塞原因，例如入口离线、分流未运行、配置未生效、等待重新确认分流、分流确认已过期、恢复观察尚未完成、国内检测等待或失败、DDNS 更新失败。

不能把 SNI 落地目标未检测继续显示成阻止切换的“等待国内健康度检测”。普通规则的目标检测仍保留，不能为消除提示而直接忽略普通规则的问题。

此次不新增监控或告警功能。现有单条规则的目标检测和历史记录可以继续用于查看业务情况，但不参与 SNI 部分的入口资格判断。

## 八、验收标准

验收观察实际成员状态、DDNS 请求和切换结果；涉及 Agent 报告与面板计时的场景，必须经过真实的报告处理流程，不能只靠手工改一个健康字段证明正确。

| 编号 | 场景 | 应有结果 |
| --- | --- | --- |
| A01 | 同端口多条 SNI 已运行且配置生效，没有逐条目标检测 | 满足其他现有条件时可以更新 DDNS |
| A02 | SNI 目标检测失败或过期，入口自身正常 | 不单独触发整组切换，不阻止 DDNS |
| A03 | 原入口和地址不变，只更换组入口域名 | 对新域名执行更新，不沿用旧域名的成功结论 |
| A04 | 入口离线、分流停止、规则缺失或旧配置仍在运行 | 不选为健康备用；当前入口按故障条件处理 |
| A05 | 国内检测开启，结果未知、失败或过期 | 不判为已通过国内检测 |
| A06 | 国内检测关闭，入口和分流配置正常 | 不等待该项检测 |
| A07 | 分流停止期间持续收到正常 Bing 报告 | 故障时间不被反复清空，达到设置后可切换 |
| A08 | 分流刚恢复，Bing 一直正常 | 按分流恢复条件等待，不提前切回 |
| A09 | 国内检测已完成故障观察，同时分流刚停止 | 不重置已经到期的故障观察，不额外拖延切换 |
| A10 | 国内检测完成恢复观察，SNI 始终正常 | 不重复等待相同恢复时间 |
| A11 | 混合组普通规则失败，随后 Agent 确认已稳定恢复 | 普通规则仍影响组健康；恢复不额外多等一轮 |
| A12 | 使用非默认时间，并在等待中修改设置 | 判断与后续到期检查都遵守面板设置 |
| A13 | 开启或关闭自动切回 | 分别遵守优先顺序切回或保留当前健康备用 |
| A14 | 所有入口故障 | 保留现有解析，明确显示不可用，不虚报恢复 |
| A15 | DDNS 服务失败或响应期间配置再次变化 | 不宣布错误切换成功；旧配置不能取得资格 |
| A16 | 分流规则停用、到期、受限或主机流量超量 | 保留原有排除条件，不借本次修复绕过限制 |
| A17 | 面板重启后重新取得入口状态 | 不凭缺失状态错误放行或提前切回 |
| A18 | 普通转发组及其他资源上的 SNI | 保持原有行为 |
| A19 | 国内检测关闭，Agent 确认离线后重新上线，或 Agent 重启；旧配置内容未变，但本次尚未取得分流确认 | 旧成功报告和晚到的旧报告都不能取得资格；本次有效确认后还须完成恢复观察 |
| A20 | Agent 持续在线，Bing 持续正常，但不再提供有效分流确认 | 在线与 Bing 报告不能续期；确认到期后停止新的选择资格，当前入口从到期时开始故障观察，到期自动检查并按条件切换；无合格备用则保留解析 |
| A21 | Agent 按现有方式确认分流运行内容未变，没有重复上传完整配置 | 面板有对应的完整已核实内容时可续期；面板没有对应内容时继续等待完整确认，不误判为正常 |
| A22 | 首次启用，分流首次确认正常，其他条件满足 | 不额外等待一轮分流恢复时间，可以选择入口并更新 DDNS；面板重启后历史状态缺失不能套用这一例外 |
| A23 | 当前入口已满足故障切换条件，备用分流刚恢复但未满恢复时间；分别开启和关闭自动切回 | 两种设置下都不能提前选中该备用；有其他合格入口则按优先顺序选择，无合格入口则保留解析；恢复时间到期后自动重新判断 |
| A24 | 同组使用 443 和另一个入口端口，其中一个应运行的分流器停止，另一个正常 | 不能凭正常端口放行整个成员；当前入口按故障时间处理，备用必须全部应运行端口都准备好；不新增端口网络检测 |
| A25 | 分流恢复观察期间再次故障或确认过期，随后重新确认正常 | 不能拼接两段正常时间；从再次有效确认起重新完成分流恢复观察，其他来源已完成的有效观察不重复等待 |

实现阶段还需核对现有中英文说明和旧测试中的“每个 SNI 落地目标都必须正常”要求，将相关当前说明更新为本规格。历史发布和验收记录保留原文，不伪造过去已经采用新规则。

## 九、与旧规格的关系

本规格拟调整 [2026-10-10 转发组承载 SNI 分流规格](../2026-10-10_转发组承载SNI分流/spec.md) 中要求“入口能连接每条启用 SNI 规则的落地机”的条件，以及对应的目标失败触发整组切换验收。

旧规格中的共享端口、完整配置生效确认、权限、用量统计、热更新、成员管理、故障切换优先顺序等约定继续保留。本文件经确认并实施前，线上仍是原有逻辑。

## 十、后续阶段与完成边界

本轮只交付规格。用户确认规格后，再按要求拆分本地工单；每张工单应写明范围、前置条件和可独立检查的完成标准。实施必须得到明确授权，不能把“同意方案”或“规格确认”当成实施授权。

此次功能范围较小，但健康来源与观察时间相互影响，不能把“跳过一条检查”直接当成完整交付。后续开单必须覆盖健康判断、计时边界和完整验收，不能只覆盖最初的 DDNS 阻塞复现。

生产部署、版本发布及推送不包含在本规格编写授权内。后续如需发布，遵守仓库既有 `sni-panel` 远端约定；原生客户端继续按长期约定排除。
