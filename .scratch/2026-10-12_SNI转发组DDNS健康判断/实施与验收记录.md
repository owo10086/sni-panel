# SNI 转发组 DDNS 健康判断：实施与验收记录

**日期：** 2026-10-12。

**实施授权：** 用户调用 `implement` 并指定本需求目录。本轮在当前 `main` 分支实施，不创建工作树。规格与工单中原来的“尚未实施”授权说明是开单时的历史记录。

**实施起点：** `d2d1ebee9948ba3fb6b889aeeff454bee2daface`。

**范围：** 主机型故障转移组的 SNI 入口资格、故障及恢复观察、DDNS 再次核对、网页状态、中英文指南和对应检查。

## 实际交付行为

入口是否可选取决于 Agent 在线、全部应运行端口与域名的当前分流配置已经生效、已开启的国内检测通过，以及必要的恢复等待已经结束。SNI 落地目标检测缺失、失败或过期不再单独阻止 DDNS，也不再单独触发整组切换。混合组中的普通规则继续要求原有目标检测。

例如 A、B 各承载 12 个域名，共用入口端口：即使只收到一条业务目标检测，只要 A 的完整分流与已开启的 Bing 检测正常，就能选择 A。A 的分流停止后按组内故障时间切换到合格 B；A 恢复时重新观察，不能借用 Bing 之前一直正常的时间。

本轮没有增加数据库表、依赖、检测开关或外部入口探测。Agent 继续使用既有完整报告、内容签名和配置接收回执；不要求发布新 Agent。原生 Android、Apple 客户端按长期约定排除。

## 检查环境与证据

- 每个新场景使用独立临时 SQLite 数据库、真实规则和转发组操作入口、真实 Agent 报告处理及加密解密流程、本机 HTTP DDNS 替身。
- 检查成员状态、是否具备选择资格、实际 DDNS 请求的域名与地址、最终当前成员及事件。涉及等待时受控推进时钟并运行真实到期调度，不直接写入最终健康结论。
- 默认故障时间为 **17 秒**，恢复时间为 **23 秒**，并额外测试 13、19、41、43、61、71、89、401 秒等设置。每轮还会推进短暂的队列处理时间，因此表中的“推进 N 秒”代表至少经过 N 秒，不是对生产耗时的承诺。
- 面板重启场景使用两个真正独立的进程，共享同一临时数据库；没有用清空一个变量冒充进程重启。
- 通知采用测试收件人和本地截获的 Telegram 请求；未向真实收件人发送消息。
- 新检查入口为 [sniForwardGroupHealth.test.ts](../../server/sniForwardGroupHealth.test.ts)，场景执行文件为 [sniForwardGroupHealthHarness.mjs](../../server/test-support/sniForwardGroupHealthHarness.mjs)。24 个单场景加 2 个跨进程检查，共 **26 项**，已纳入标准 `test:server` 命令。

## 附加边界复验

- **删除完成后旧表再来：** 真实删除域名，报告正确剩余 11 条，确认数据库中对应成员副本已实际清除，再报告旧 12 条并等过恢复时间。旧域名仍使该成员无资格。`deleted-domain` 同时覆盖等待删除与清理完成两个阶段；允许其他资源合法共用分流端口。
- **缺报告的固定期限：** 普通和国内检测都不发结果，持续确认分流并反复评估，推进 330 秒后组进入不可用，不能用每次评估时间无限推迟等待。`pending-normal`、`pending-china`。
- **通知、手动同步及排序：** 切换时 DDNS 失败无成功通知；重试成功只产生对应通知，内容含实际域名、旧/新地址；记录失败与成功事件。手动同步确实请求服务；手动调换成员顺序选择新的合格优先成员，沿用不发自动切换通知的含义。`notifications`。
- **未知时钟与退休身份：** 标准审查另用两个独立面板进程，第一进程保存 PID 2001 并留存 PID 1001 的旧包；第二进程先接收旧包，再接收真正 2001 的本次回执及完整表。真正当前进程未被旧包错误退休，能重新确认。该额外复验脚本位于临时目录，不计入上述 26 项标准检查数。
- **系统 DDNS 未启用、没有可用地址和没有旧解析：** 保留原流程，通过共享流程代码核对及既有故障转移检查确认未增加放宽入口的分支；本轮没有针对所有 DNS 提供商逐一接网验收。网页“建议入口”和已完成远端解析继续区分。
