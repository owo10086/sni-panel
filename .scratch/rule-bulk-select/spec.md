# 转发规则列表行内多选批量编辑

Status: resolved

## Problem Statement

批量改一批规则的链路，今天只有一条路：工具栏的「批量管理」。它是一个四页签的总管理弹窗（批量复制 / 批量编辑 / 批量导出 / 批量导入），左半边是一份**与主列表无关的规则清单**，带自己的类别筛选和搜索框。

代价落在三个地方：

**选择要做两遍。** 主列表上已经用类别页签、资源筛选、搜索词把目标规则筛出来了，进了弹窗这些全部作废，得在弹窗自己的筛选器里重新找一遍、重新勾一遍。规则一多，两套筛选条件对不齐时还得反复核对到底勾没勾全。

**看不见上下文。** 弹窗里每条规则只有一行 `:443 -> chka.332323.xyz:1103 / nftables / TCP`。主列表上能看到的状态点、已用流量、延迟、所属资源、转发出口，在这里全没了。改一批规则的链路时，恰恰要靠这些判断该不该改。

**动作和对象隔了一层弹窗。** 「这几条改到另一条转发链」是一个当场就能说清的意图，却要先开一个占满屏幕的总管理界面，再在里面重建一次选择。

## Solution

**把多选放回列表本身。**

每行规则、每张规则卡最前面加一个常驻勾选框。选中数大于 0 时，列表上方展开一条操作栏：

```
已选 14 条（本页）  清空 │ 批量编辑   删除所选   更多批量操作
```

「批量编辑」打开一个只有两块的小对话框，与大弹窗「批量编辑」页签的两块替换项一一对应，但没有规则清单、没有页签、没有复制目标：

```
批量编辑 14 条规则
──────────────────────────────────
替换入口资源                      保持原入口
  入口类型    [转发链 ▾]
  使用转发链  [● 台湾hinet-日本gcore 1x ▾]

替换转发出口                      保持原目标
  目标地址    [留空则保持原目标地址]
  目标端口    [留空则保持原目标端口]

端口冲突处理  [保持原端口，冲突则该条失败 ▾]
                          [取消]  [应用]
```

两块各自独立，未填写的项保留每条规则原来的值——与今天的批量编辑语义完全一致。

**执行层复用现成的。** 内联入口走 `buildBatchEditRulePayload` / `updateBatchRuleTarget` / `runBatchOperations`（`client/src/pages/Rules.tsx`），并发 6 逐条调 `rules.update`；批量删除复用 `rules.deleteBatch`。不新增任何服务端接口，不新增任何数据库字段。前两个函数需要加一个可选的覆盖参数，见下文「执行层的状态隔离」。

**大弹窗原样保留。** 它继续承担内联覆盖不到的事：批量复制到其他资源、批量导出、批量导入，以及跨页和全量范围的选择。操作栏的「更多批量操作」带着当前选择把它打开。

## User Stories

1. 作为管理员，我想在规则列表里直接勾选多条规则，从而不必进总管理弹窗再把已经筛好的规则重新找一遍。
2. 作为管理员，我想在勾选时仍然看得到每条规则的状态、流量、延迟和所属资源，从而当场判断该不该把它一起改掉。
3. 作为管理员，我想一次把选中的多条规则换到另一条转发链，从而不必逐条打开编辑弹窗改同一个下拉。
4. 作为管理员，我想在同一个对话框里同时改入口资源和转发出口，从而「换链路顺便换落地机」是一次操作而不是两次。
5. 作为管理员，我想在只改其中一项时把另一项留空，从而不必担心没填的那项被清掉。
6. 作为管理员，我想在 SNI 规则组的组头上一键选中整组，从而「这一组域名整体换一条链」不需要逐条点。
7. 作为管理员，我想在组折叠着的时候也能勾组头，从而不必为了选中而先展开。
8. 作为管理员，我想一键选中本页全部规则，并且在卡片视图和手机上同样能做到，从而不必因为当前视图没有表头就逐条去点。
9. 作为管理员，我想在「全部」页签下一键选中某一类规则（比如只选转发链），从而不必全选整页再逐条取消掉不想动的那些。
10. 作为管理员，我想让不支持批量修改的规则勾选框直接置灰并写明原因，从而不会选完才发现有几条没生效。
11. 作为管理员，我想在批量修改入口资源时默认不自动改端口，从而一组共用 443 的 SNI 分流规则不会被静默打散到十几个不同端口上。
12. 作为管理员，我想在部分规则失败时让失败的那几条保持勾选，从而直接再点一次就能重试，不必回头重新找。
13. 作为管理员，我想在选中若干规则后一键删除它们，从而不必逐条点删除并逐条确认。
14. 作为管理员，我想带着已经勾好的选择跳进大弹窗，从而需要复制或导出时不必重勾一遍。
15. 作为管理员，我想在手机上也能用这个多选，从而不是只有切到桌面列表视图才用得上。

## Decisions

### 选择范围只算当前页

表头和操作栏的全选 = 全选**本页可选规则**。翻页、切类别页签、改资源筛选、改用户筛选、改搜索词 → 一律清空选择。切换卡片/表格视图、改卡片密度 → 保留选择（同一页同一批规则）。轮询刷新后已不存在的规则自动从选择里剔除。

理由是数据：主列表走 `rules.listPage`（服务端分页，每页 12/24/36/48），**全量列表 `rules.list` 只在批量弹窗打开时才拉**。批量编辑需要逐条读规则自身的 `sourcePort`、`forwardType` 才能拼 payload，所以跨页选择意味着给普通页面常驻一份带轮询的全量查询——规则多的实例上这是一份持续的大响应。

代价是跨页改几百条仍要走大弹窗。这是有意的分工：内联解决「看着列表顺手改一批」，大弹窗解决「按条件圈定全量」。

全选的数据源是 `pagedRules`（`client/src/pages/Rules.tsx`），它已经把本页展示项摊平成真实规则，**包含折叠 SNI 组内部的规则**，与「组折叠着也能勾」保持一致。

### 两类规则不可选，置灰并写明原因

可选性判定沿用批量弹窗已有的口径：`!rule.forwardGroupRuleId && !rule.forwardGroupMemberId && isRuleSupported(rule)`。

- 转发组派生规则（模板规则的成员副本）：它们由模板规则推导，直接改会和推导结果打架。
- 当前运行时不支持的协议：它本来就不能正常工作，批量改链路没有意义。

这两类的勾选框置灰，悬停写明原因。全选和组头三态**只统计可选集合**——一个整组都不可选的组，组头也置灰。

不选「可以勾、执行时静默跳过」：那样用户要到结果 toast 才知道有几条没改成，而这个功能存在的理由就是当场看得见。

### 端口冲突默认「保持原端口」，与大弹窗不同

大弹窗的端口冲突处理默认是 `auto`（自动分配新端口）。**内联对话框默认 `error`（保持原端口，冲突则该条失败）。**

按 ADR-0002，SNI 分流规则的全部意义就是同一入口主机、同一入口端口上并存多条规则，靠域名互相区分。把一组 14 条共用 443 的 SNI 规则整体换链时若撞上端口冲突，`auto` 会给每条各分一个新端口，**把这一组打散到 14 个互不相同的端口上，而且全程无声**。这正是内联入口最主要的使用场景。

三个选项仍然都给（跳过 / 自动分配新端口 / 保持原端口），只是默认值不同，并在下方写明原因。失败只是没改成，可以重来；端口被打散要逐条排查才能发现。

### 失败项保留勾选

执行结束后成功的规则取消勾选，失败和跳过的**保留勾选**，toast 汇总「成功 N 条，失败 M 条：<第一条错误>」。直接再点一次「批量编辑」就是重试剩下的，不必回头重新找。

### 混合入口类型允许，但要看得见

选中的规则入口类型一致时（比如全是转发链），对话框预选那个类型并直接展开对应下拉——你图 3 那个转发链下拉，一步到位。类型不一致时不预选，并在「替换入口资源」块里显式写「所选包含 2 种入口类型，应用后会全部改为转发链」。

不禁止混选：「把一批隧道规则改成转发链」是真实需求，大弹窗支持，内联也应该支持。

### 转发出口就是目标地址和目标端口

规则层面没有可选的「出口资源」对象。按 `CONTEXT.md`，**出口组**是隧道的属性、**落地机**就是规则的目标地址。列表里「转发出口」列渲染的正是 `targetAddress`（`renderTableTransferExit`）。

所以对话框第二块标题用「替换转发出口」（对齐列表列名和用户说法），字段仍是「目标地址」「目标端口」（对齐数据模型和大弹窗），两边都不制造新词。

替换语义与大弹窗一致：**全部设为同一个值**，留空保持原值。

### 全选要覆盖到卡片，不能只挂在表头上

「列表视图」在窄屏下并不渲染表格：它是 `<RuleCardModeTransition className="sm:hidden">` 出卡片、`<Card className="hidden sm:block">` 出表格，按屏宽二选一。加上卡片视图本身是默认视图（`getStoredRuleViewMode` 兜底 `"card"`），只把全选放进 `<TableHeader>` 会让三种情形里有两种没有全选：

| 视图 | 屏宽 | 实际渲染 | 全选入口 |
|---|---|---|---|
| 列表视图 | ≥640px | 表格 | 表头勾选框 |
| 列表视图 | <640px | 卡片 | 列表上方的「全选本页」 |
| 卡片视图 | 任何宽度 | 卡片 | 列表上方的「全选本页」 |

因此全选做成**三层**，粒度由粗到细：

1. **页级** —— 表格视图在表头；卡片视图和列表视图的手机布局在列表上方一行「全选本页」（`effectiveViewMode === "table"` 时带 `sm:hidden`，避免和表头重复）
2. **类别级** —— 类别组头（端口转发 / 隧道转发 / 转发链 / 转发组）带三态勾选框，只在 `ruleCategory === "all"` 时存在。它对表格和卡片两个视图同时生效，因为 `renderRuleGroupHeader` 是共用的
3. **SNI 组级** —— SNI 组头带三态勾选框，同样两个视图共用 `renderSniRuleGroupHeader`

类别级不是可有可无的重复：在具体类别页签下没有类别组头，页级全选是唯一入口；而在「全部」页签下，「只选转发链这一类」比「全选整页再取消一堆」更贴近实际操作。

`desktopRuleGroups` 由 `pagedRules` 构建，所以类别组头的勾选范围天然就是本页，与页级作用域一致。

代价：`renderRuleGroupHeader` 原本整体是一个 `<button>`，勾选框不能嵌在按钮里（HTML 非法，且点击会连带折叠分组），所以外面包了一层 flex，按钮退化成其中一个子元素。这是本功能在上游文件里结构改动最大的一处。

### 勾选框常驻，不做「多选模式」开关

表格最左固定一列勾选（排序拖拽列排在它右边），卡片在状态点左侧、同一行；紧凑卡片用小一号尺寸。选中数为 0 时操作栏不出现。

不加进入开关：这个功能的存在理由就是「原来那个藏得太深」，再加一层开关是把它重新藏起来。代价是卡片布局永久左移约 24px，以及手机滑动时可能误触——勾选是可逆的，误触的成本低于多一次点击乘以每次使用。

### 操作栏贴在列表上方，不做底部浮条

选中数大于 0 时，在筛选工具栏与列表之间展开一条，普通文档流。

项目里目前没有任何底部浮条或固定条的先例（只有 `HostMonitor.tsx` 有一个 `sticky top-0`）。底部浮条要自己处理 z-index、分页器遮挡、移动端安全区内边距（`--forwardx-safe-area-*`），为一个功能引入一套新的定位模式不划算。代价是列表很长时往下滚会看不到操作栏。

### 执行层的状态隔离

`buildBatchEditRulePayload` 和 `updateBatchRuleTarget` 今天是闭包读大弹窗的组件状态（`batchEditForm`、`selectedBatchEdit*`、`batchEditTargetIp/Port`、`copyConflictStrategy`），签名里只有 `rule` 和 `sourcePort`。内联对话框有自己的表单、自己的冲突策略默认值，直接复用会读到大弹窗的状态。

**给两个函数加一个可选的覆盖参数**：不传时从组件状态读取，行为与今天逐字节一致，大弹窗路径不受任何影响；内联路径把表单打成快照显式传入，完全不依赖组件状态。

选它而不是「内联自己重写一份 payload 构造」：后者让上游改 payload 形状时内联这份**静默漂移**——少传一个字段就是规则被改坏且不报错。加参数的代价是重放上游时多两处可能冲突，但那是**显式冲突**，人看一眼就能调解。也不选「把 payload 逻辑整段抽到新文件、上游函数改为一行调用」：那样上游一旦改动 payload 逻辑，调解成本比加参数高得多。

顺带的好处：内联在点「应用」时传的是表单快照，不经过 React state，天然不存在「setState 之后立即提交读到上一轮渲染值」的问题——大弹窗当年为此专门加了 `copyTargetSelectionRef` 这类补丁。

### 代码落点与上游冲突面

这是一个 fork：`origin`（`poouo/Forwardx`）是上游参考源，代码只推 `sni-panel` 远端（见 `AGENTS.md`）。历史里没有 merge，但按「作者 + 时间戳 + 标题」比对，**上游分叉后 459 个提交里有 458 个原样存在于本仓库历史中**——本仓库是在用重放/变基的方式跟上游。上游几乎每个 release 都改 `client/src/pages/Rules.tsx`（9514 行，列表和批量弹窗全在里面）。

表格列顺序统一为 **选择列 → 排序列（仅排序开启时存在）→ 状态列 → …**，`<colgroup>`、`<TableHeader>`、`renderRuleTableRow` 三处必须同序。两列都是 44px，顺序写反了列宽会整体错配到相邻列上，而肉眼看不出来。

表格的列定义散在四处（`colgroup`、`Table` 的 min-width、`ruleTableColumnCount`、类别组头 `colSpan`），加一列必须四处同改，且管理员与普通账号两种列数都要验证。类别组头原本不含排序列是正确的（它只在 `ruleCategory === "all"` 时渲染，与 `ruleSortingEnabled` 互斥），不要顺手"修"它；勾选列与它不互斥，所以必须加。

### 数据未落地时禁止勾选

`rules.listPage` 配了 `placeholderData: (previousData) => previousData`。翻页或改筛选后、新数据回来之前，列表上显示的是**上一页的规则**。仅仅「翻页时清空集合」不够：清空之后用户照样能在这份旧数据上勾选，把上一页的规则选进来再交给批量编辑或删除。

因此 `rulePageQuery.isPlaceholderData` 为真时，所有勾选框与批量执行按钮一律禁用。这与排序功能已有的做法一致（`ruleSortingReady = ruleSortingEnabled && !rulePageQuery.isPlaceholderData`）。

### 成功、跳过、失败分开统计

`updateBatchRuleTarget` 在冲突策略为「跳过」时返回 `{ updated: false, skipped: true }`——这在 `runBatchOperations` 里是正常返回，**不带错误对象**。把它并进失败统计会让 toast 的「第一条错误」无数据可取。三个计数必须分开，「全部跳过」时对话框不关闭，让用户当场改策略重试。跳过只在用户主动选了「跳过冲突规则」时才可能非零。

不新建 `client/src/components/ui/checkbox.tsx`：项目里没有这个组件，全仓库用的都是原生 `<input type="checkbox">`；三态框放进 `components/rules/` 下我们自己的文件，用 `indeterminate` ref 实现。

### 不加新的权限门

与单条规则的编辑/删除按钮一致——它们今天也没有前端权限判断，由服务端兜底。

## Testing Decisions

### 唯一的缝：`client/src/lib/ruleBulkSelection.ts`

本仓库已有的模式是把表单和列表的判断逻辑抽成 `client/src/lib/` 下的纯模块单测（`sniRuleForm.ts`、`ruleTransfer.ts`、`forwardRuleStatus.ts` 等十余个）。这个功能里真正容易出错、且与 React 无关的部分全部放进这一个模块：

- **可选性判定** —— 转发组派生规则、不支持的协议各自返回不可选与原因文案
- **三态计算** —— 空集合、全不可选的组、部分选中、全选，四种输入各自的组头与表头状态
- **选择集合的增删与剪枝** —— 勾组头选中整组、取消整组、刷新后剔除已消失的规则 ID
- **混合入口类型预选** —— 全同类型返回该类型、混类型返回不预选并给出类型数
- **执行结果归纳** —— 输入**逐条结果**（`{ ruleId, outcome: "updated" | "skipped" | "failed", error? }` 的数组），输出三个计数、提示语气与文案、保留勾选的 ID 集合、对话框关不关。那张五格矩阵在这里变成可枚举的测试用例

  输入必须是逐条结果而非三个计数：计数里没有规则编号，算不出该保留哪几条勾选——「A 成功 B 失败」与「B 成功 A 失败」的计数完全相同，要保留的编号却相反。把 `runBatchOperations` 的返回映射成这个数组的那一步留在 `Rules.tsx`，它是薄的，不含任何判断。测试要断言 ID 集合本身，只断言数量会漏掉这类错误。

新测试文件**必须加进 `package.json` 的 `test:server` 脚本的文件列表**。仓库没有裸的 `test` 脚本；测试是 `node --import tsx --test` 显式列文件跑的，CI 执行的是 `pnpm test:server`（`.github/workflows/ci.yml`）。`client/src/lib/sniRuleForm.test.ts` 和 `batchOperations.test.ts` 都在这个列表里，新文件挨着它们加。不登记就永远不会被执行。

### 不另开的缝

- **React 组件与勾选交互**：项目里只有两个 `.test.tsx`，没有为页面级组件建测试的先例，`Rules.tsx` 也无法在测试环境里装载。勾选框位置、列宽对齐、组头跨度这些靠人工过一遍管理员与普通账号两种视图。
- **执行层**：`buildBatchEditRulePayload` 与 `updateBatchRuleTarget` 仍是 `Rules.tsx` 里的闭包（把它们抽出来就是被否掉的方案 C），只加可选参数不动逻辑。它们依赖的 `runBatchOperations` 一字不改，`client/src/lib/batchOperations.test.ts` 现有 3 项必须保持全绿。
- **服务端**：不新增任何接口，`rules.update` 与 `rules.deleteBatch` 的现有测试覆盖不变。

## Out of Scope

- **跨页选择、全选当前筛选下的全部。** 需要给普通页面常驻一份带轮询的全量规则查询。走大弹窗。
- **目标地址的查找替换**（把所有目标里的 `332323.xyz` 换成别的域名、每条保留各自前缀）。内联只做「全部设为同一个值」，与今天的批量编辑一致。
- **批量启用/停用、批量复制、批量导出、批量导入。** 仍在大弹窗里，操作栏的「更多批量操作」带着选择跳过去。
- **Shift + 点击范围选择。** 每页最多 48 条，组头全选已覆盖主场景；分组列表里「范围」的定义（要不要跨过折叠的组、卡片网格里按什么顺序）容易做出反直觉行为。
- **底部浮动操作栏。**
- **3D 流量转发图视图里的多选。**
- **批量修改故障转移目标、限速、最大连接数等其余规则字段。**
