# 版本方案切换、仓库迁移与 amd64 单架构发布

**Status:** ready-for-agent

## Problem Statement

项目要从上游 `poouo/Forwardx` 独立出来，以 `owo10086/sni-panel` 的身份对外发布。当前有三件事挡在前面：

**版本号还在上游的线上。** 面板 `2.3.281`、Agent `2.2.195`、分流器 `2.2.118` 三条版本线各走各的，彼此没有可推断的关系。管理员看到「面板 2.3.281 + Agent 2.2.195」无法判断两者是否配套，运维在升级时也无从判断「这次改动要不要同时升 Agent」。

**在线安装与升级仍然指向上游仓库。** 面板下发的 Agent 安装脚本、面板自身的安装脚本、版本检查、升级入口、GitHub 加速器，全部从 `poouo/Forwardx` 的 release 拉取。这意味着新仓库发布的修复**根本不会被装上**——这不是理论风险：上游 release 里的 Agent 是 `2.2.194`，而本地构建的是 `2.2.195`，曾经一条升级命令把两台生产机从 `2.2.195` 降级到 `2.2.194`，恰好低于 SNI 分流要求的下限。

**CI 同时产出 amd64 与 arm64，但当前只需要 amd64。** 双架构让每次构建的时间和体积翻倍；本地构建面板镜像时曾因 arm64 链接阶段耗尽磁盘而失败。

## Solution

**三条版本线收敛成一条可推断的关系，并由工具强制。**

版本号重置为 `3.0.0`，此后按改动范围递增：

| 本次改动 | 面板 | Agent | 分流器 fxp | APK Release |
| --- | --- | --- | --- | --- |
| 只改面板 | 补丁位 +1（`3.0.1`） | 不动 | 不动 | 跟随面板 |
| 改了 Agent（面板是否改都算） | 小版本位 +1、补丁位归零（`3.1.0`） | 同面板 | 同 Agent | 跟随面板 |

三条不变式：

1. **面板与 Agent 的 `major.minor` 恒等。** 看到面板 `3.2.x` 就知道要配 Agent `3.2.0`。
2. **Agent 与分流器版本恒等。** 两者是同一批资产、同一条升级命令装上去的，版本错开只会制造混乱。
3. **APK Release 版本恒等于面板版本。** 它表示 APK 挂在哪个 release 上，不是 APK 自身的版本。

「只改 Agent 不改面板」也按第二行处理，因为面板镜像内置 Agent 资产，改 Agent 必然要重新发布面板。

**在线安装与升级链路整体切到新仓库**，并收敛到单一来源，杜绝再次出现「改了一处、漏了四处」。

**CI 与本地构建都只产出 amd64。**

## User Stories

1. 作为管理员，我想从面板版本号直接推断出该配哪个 Agent 版本，从而不必查表或试错。
2. 作为管理员，我想让面板与 Agent 的版本号在同一条线上，从而一眼看出两者是否配套。
3. 作为管理员，我想让分流器版本与 Agent 版本一致，从而不必记忆第三条版本线。
4. 作为管理员，我想让只改面板的发布只动补丁位，从而知道这次升级不需要动 Agent。
5. 作为管理员，我想让涉及 Agent 的发布同时推进两边的小版本位，从而知道这次必须连 Agent 一起升。
6. 作为运维，我想让版本规则由脚本强制而不是靠人记住，从而不会在某次发版时被违反。
7. 作为运维，我想让违反版本规则的提交在构建阶段就失败，从而错误不会流到发布产物里。
8. 作为管理员，我想让在线安装命令从新仓库拉取，从而装到的是本项目的版本而不是上游的。
9. 作为管理员，我想让 Agent 升级从新仓库或面板资产取得二进制，从而不会被上游的旧版本覆盖。
10. 作为管理员，我想让面板的版本检查指向新仓库的 release，从而「有新版本」的提示是准确的。
11. 作为管理员，我想让面板升级入口跳转到新仓库，从而不会误入上游项目页面。
12. 作为管理员，我想让 GitHub 加速器改写的地址也指向新仓库，从而使用加速器时同样装到正确版本。
13. 作为管理员，我想让文档里的安装命令与实际仓库一致，从而照文档操作不会装错。
14. 作为管理员，我想让卸载命令同样指向新仓库，从而卸载流程不依赖上游仓库可用。
15. 作为开发者，我想让仓库地址只有一个来源，从而下次迁移只改一处。
16. 作为开发者，我想让既有测试覆盖仓库地址断言，从而漏改会被测试立刻发现。
17. 作为运维，我想让 CI 只构建 amd64，从而发布时间与产物体积减半。
18. 作为运维，我想让本地构建脚本也只编 amd64，从而面板镜像构建不再因 arm64 阶段耗尽磁盘。
19. 作为运维，我想让镜像清单校验与实际架构一致，从而不会因为断言 arm64 存在而必然失败。
20. 作为管理员，我想在文档中明确看到「当前不支持 arm64 主机」，从而不会在 arm64 机器上白装一遍。
21. 作为开发者，我想让这次的版本规则与迁移范围写成规格，从而后续发版有据可依。

## Implementation Decisions

### 版本常量与它们的校验关系

版本号分布在五处，彼此由版本校验脚本强制对齐：面板版本常量、`package.json`、Agent 源码内的版本变量、分流器源码内的运行时版本常量，以及变更日志中声明的分流器版本。变更日志里必须有对应版本的章节并声明分流器运行时版本，否则校验失败。

面板与 Agent 的兼容表由两个版本常量推导，不需要手工维护。

### 必须改写既有的版本校验规则

**当前校验脚本里有一条规则与本方案直接冲突**：它在面板版本与 Agent 版本相同时报错，要求「两条版本线分开」。本方案恰恰要求两者相同，因此这条规则必须删除，并反向改写为强制上面三条不变式。

保留既有的版本步长校验——它允许「大版本 +1、小版本与补丁归零」的跳跃，因此从旧版本跳到 `3.0.0` 无需额外放宽。

### 仓库地址收敛为单一来源

新增一个共享模块，导出仓库归属标识与由它派生的各类地址（release 下载、原始文件、发布页）。所有安装升级链路上的位置改为引用它，不再各自硬编码。

需要改的位置分三类：

- **面板侧常量**：版本检查与 APK 下载地址、Agent 资产下载、面板升级入口、GitHub 加速器中的面板安装脚本地址
- **面板下发的 Agent 安装脚本**：生成脚本时内嵌的 release 下载地址
- **独立 shell 安装脚本**：Agent 安装脚本、面板 Docker 安装脚本、面板本地安装脚本

文档中的安装、升级、卸载命令同步更新，包括加速器用法示例。

### 明确不在迁移范围内

- **Go module 路径**。改它要动两个 Go 包的全部 import，与安装升级链路无关，风险与收益不成比例。
- **插件商店元数据**。属于插件分发体系，与本项目的安装升级无关。

这两类保留上游标识不影响功能，但应在后续单独评估。

### 单架构发布及其后果

镜像构建矩阵、Agent 发布产物清单、本地资产构建脚本三处都只保留 amd64。镜像清单校验中断言 arm64 存在的部分必须一并删除，否则构建必然失败。

**后果必须在用户文档中写明：面板镜像不再内置 arm64 资产，arm64 主机无法安装 Agent。** 这是一个能力收窄，不能只在提交信息里提一句。

### 一处已知的语义过时

SNI 分流对出口 Agent 有最低版本要求，当前值是旧版本线上的 `2.2.195`。Agent 升到 `3.0.0` 后该下限仍然成立（大版本更高），功能不受影响，但它引用的是一条已经废弃的版本线。本次不改，留待下次触及该逻辑时一并处理。

## Testing Decisions

好的测试只验证外部可观察的行为：脚本是否通过、生成的安装脚本里的地址指向哪里、构建产物包含哪些架构。不测常量本身长什么样。

**版本规则用版本校验脚本自身验证。** 它已经是这个规则的唯一执行者，改写后直接运行即可确认：符合不变式的组合通过，违反的组合失败。这是最高的缝——规则的唯一消费者就是它。

**仓库地址用既有测试验证。** 安装脚本生成、加速器改写、资产下载、面板升级入口都已有测试断言了地址，它们会在漏改时直接失败。这些测试需要同步更新为新地址，**更新它们本身就是覆盖的证明**：如果某处漏改而测试仍然通过，说明该处缺测试，需要补。

**单架构用构建产物验证。** 本地资产构建脚本执行后，产物目录应只含 amd64 文件。CI 侧的镜像清单校验改为只断言 amd64。

**Prior art**：仓库地址相关的断言散布在安装脚本生成、加速器、资产服务、面板升级四组既有测试里，照其现有写法更新即可，不需要新建测试文件。

## Out of Scope

- **Go module 路径迁移**。
- **插件商店元数据的仓库标识**。
- **arm64 支持的恢复**。本次是有意收窄，后续需要时另行评估。
- **历史版本号的追溯修改**。变更日志中既有章节保持原样，`3.0.0` 作为新起点。
- **上游仓库的同步策略**。本项目与 `poouo/Forwardx` 之后如何取舍上游改动，不在本规格范围内。
- **SNI 分流最低 Agent 版本常量的更新**。见上文说明。

## Further Notes

**版本规则必须由工具强制，这一点是有教训的。** 本项目此前依赖「发版时记得改版本号」的约定，结果是三条版本线互不相关、且出现过生产环境被降级到低于功能下限的情况。规则写进文档只能提醒，写进校验脚本才能拦住。

**仓库地址散落是这次迁移最大的风险点。** 迁移前它分布在五个独立常量、三个 shell 脚本和一段生成代码里，没有任何一处是权威来源。这类分散在一次迁移中必然漏改，而漏改的表现是「装上了上游的版本」——它不会报错，只会让修复看起来没生效。收敛为单一来源不是锦上添花，是这次迁移能否可靠完成的前提。

**arm64 的收窄是有代价的决定。** 它换来构建时间与体积减半，代价是 arm64 主机彻底装不上。这个取舍在当前只有 amd64 主机的前提下成立；一旦引入 arm64 主机，需要先恢复双架构再部署，而不是临时手工编译。
