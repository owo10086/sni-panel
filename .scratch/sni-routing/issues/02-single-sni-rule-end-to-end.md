# 02 — 单条 SNI 分流规则端到端打通

**What to build:** 管理员在一条走转发链的转发规则上填一个 SNI 域名并保存，客户端用该域名连入口端口，流量就能到达对应的落地机。这是整个功能最细的一条完整路径：只有一条规则，因此不触碰入口端口共用，也不需要分组概念。

打通之后，**分流器**这个受管运行时角色在出口主机上跑起来，面板能把**分流表**推给它，入口不再把流量发往落地机而是发往分流器，四种未匹配情况全部断开。

架构依据见 ADR-0001（分流器为何是独立角色而非内嵌隧道出口、nginx 或 HAProxy）。

**Blocked by:** None — can start immediately

**Status:** resolved

- [x] 管理员能在转发规则表单填写 SNI 域名并保存；域名在保存前被规范化（转小写、去尾点）
- [x] 非管理员账号看不到 SNI 域名输入，也无法通过接口创建带 SNI 的规则
- [x] 填了 SNI 域名的规则协议被锁定为 TCP
- [x] 客户端用正确域名连入口端口，连接到达该规则的落地机
- [x] 落地机收到的 TLS 握手与客户端发出的**逐字节一致**，未被改写或截断
- [x] 四种未匹配情况各自断开连接：域名不在分流表里、连接不带 SNI、非 TLS 流量、握手未在读取窗口内收完
- [x] 带 ECH 扩展但明文 SNI 可读的连接正常分流，不被当作「无 SNI」断开；内层域名不解密
- [x] 入口侧的转发目标是分流器；落地机地址不出现在入口主机的任何配置里
- [x] 分流器监听端口由面板分配，不与该主机上其它受管运行时冲突
- [x] 推导出的出口主机多于一台时明确拒绝创建并说明原因，不静默只下发给第一台
- [x] 出口主机的 Agent 版本不足时拒绝创建，并告知所需最低版本
- [x] ClientHello 跨多个 TCP 段到达时能正确拼接；畸形长度字段与超长扩展不 panic、不越界、不无限等待

## Comments

**2026-09-12** — 实现于 `87ca5b5`，并已在生产链路验证：韩国入口 → 香港分流器 → 落地机，三处连接与计数器同时核对通过。

**其中一条验收标准在上线后被推翻。** 原「带 ECH 的连接按无 SNI 处理并断开」是错的——它把「扩展存在」当成了「明文 SNI 不可得」的证据，导致所有 Chrome 指纹客户端（GREASE ECH）被静默丢弃。该条已改写为正确表述，**其实现另行跟踪，见 `.scratch/sni-routing-ech/spec.md`，不要从本工单重复实现。**
