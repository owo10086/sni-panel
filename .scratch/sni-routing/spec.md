# SNI 分流

Status: resolved

> 十张实施工单均已完成并部署到生产（见 `issues/`）。两项后续工作另有规格：
> ECH 判定更正见 `.scratch/sni-routing-ech/`，端口占用检测见 `.scratch/sni-port/`。
> 工单 07 的 Comments 里记录了两个尚未开单的遗留缺陷。

## Problem Statement

一条转发规则只能指向一个目标地址，所以每多一台落地机就要多占一个业务端口。落地机到了几十上百台之后，这个模型的成本集中体现在三处：

客户端必须知道自己该连哪个端口。管理员发出去的不是一个地址，而是一张端口对照表，客户端配错端口的表现是连不上，但错误信息里没有任何线索指向"你端口选错了"。

每加一台落地机要在两台机器上各改一次配置——入口开一个新端口，出口加一条新转发。两处只改了一处，症状是新客户能连上但流量去了别人的落地机。

批量录入只能缓解打字量，缓解不了端口消耗。现有的批量导入可以一次粘贴上百行 `地址:端口` 建出上百条规则，但那依然是上百个端口。端口段是主机上的有限资源，还要和隧道出口端口池竞争。

## Solution

把区分落地机的维度从**端口**挪到**域名**。

所有客户端连同一个入口端口。出口主机上的**分流器**读取客户端 TLS 握手里的 SNI 域名，据此决定把连接交给哪一台**落地机**。落地机从 3 台加到 100 台，客户端连的还是那一个端口，入口侧的配置一个字都不用改。

管理员在转发规则上多填一个 SNI 域名，这条规则就成为一条 **SNI 分流规则**。同一个入口端口上可以并存任意多条 SNI 分流规则，靠域名互相区分。粘贴一批 `规则名#SNI域名#目标地址#目标端口`，一次建好全部规则。

分流器是**独立的受管运行时角色**，不绑定链路类型。隧道、转发链、端口转发的最后一跳都可以把流量交给它，因此换掉入口到出口那一段的实现，不需要重配任何分流规则。

## Implementation Decisions

### 数据模型

**SNI 分流规则就是转发规则，不新建资源。** `forward_rules` 增加一个可空的 `sni` 字段，承载规范化后的域名；为空即普通转发规则。这一决定源于：分流表在概念上是"域名到落地机"的映射，但它可以完全从规则集推导出来，把它做成用户可创建的资源会引入一个与规则重复的管理面。参见 CONTEXT.md 对**分流表**的定义——它是运行时派生物，不是资源。

**规则的目标仍然是落地机。** `targetIp:targetPort` 语义不变，改变的只是**谁消费它**：普通规则由入口消费，SNI 分流规则由出口的分流器消费。

**新增索引覆盖 (入口主机, 入口端口, 域名)**，服务于域名唯一性校验和分流表推导两条路径。

**域名规范化在写入前完成**，库里存的就是规范化后的值，唯一性直接比对该列，不在查询时做函数变换。

### 放开源端口唯一性

面板一直强制同主机源端口唯一。本功能为带 `sni` 的规则放开这条约束：同主机同端口可并存多条 SNI 分流规则，只要域名互不相同。同时新增反向约束——某端口一旦被 SNI 分流规则占用就不接受普通规则，反之亦然。完整理由与连带后果见 ADR-0002。

### 分流器作为独立运行时角色

分流器是 `forwardx-fxp` 的一个新角色，部署在链路出口主机上，不内嵌进隧道出口进程，也不借用 nginx 或 HAProxy。完整的备选方案与否决理由见 ADR-0001。

**连接处理契约**：读取直到能判定 SNI → 查分流表 → 连接落地机 → **把已读取的握手字节原样先发给落地机** → 双向转发。握手字节的缓存与重放是这个角色最容易写错的地方，也是"落地机一直等握手"类故障的唯一来源。

**四种未匹配情况统一断开**：取不到明文 SNI、域名不在表里、非 TLS、窗口内未收全。不存在默认落地机。

**ECH 扩展的存在不等于取不到 SNI。** 只要 ClientHello 里能解析出明文 SNI 就按它路由，带 ECH 扩展与否不参与判定；只有真正解析不出明文 SNI 才算「无 SNI」。GREASE ECH（Chrome 指纹的诱饵扩展）的明文 SNI 完全真实可读，真 ECH 的外层明文 SNI 同样可读，两者都应正常分流。内层真实域名不解密、不尝试获取。修正缘由与证据见 `.scratch/sni-routing-ech/spec.md`。

### 分流表热更新

分流器持有的分流表通过原子换指针更新，不重建监听 socket、不重启进程。配置携带单调递增的版本号，进程持有"当前生效版本"。校验不通过的配置不替换正在生效的那份。

按规则维护活跃连接集合以支持定向关闭，变更语义为：

| 变更 | 动作 |
| --- | --- |
| 新增规则 | 换表，不关任何连接 |
| 改落地机地址或端口 | 换表 + 关闭该规则的既有连接 |
| 停用或删除 | 换表 + 关闭该规则的既有连接 |
| 改其它规则 | 不影响本规则 |

**配置投递不能走 Agent 现有的"配置 hash 变了就重启服务"路径**，否则热更新的全部意义会被抵消。

### 期望状态与下发

面板按「出口主机 + 入口端口」聚合该组的全部 SNI 分流规则，推导出分流表，随分流器配置一起下发到出口主机。出口主机由规则引用的链路资源的最后一跳推导。分流器监听端口由面板分配并持久化，沿用现有主机端口预留机制。

v1 只支持单出口；推导出多于一台出口主机时明确拒绝，不静默只下发给第一台。

### 入口侧转发命令

SNI 分流规则的入口转发目标一律替换为「出口主机地址 + 分流器端口」，落地机地址在入口侧任何配置里都不出现。同组规则在入口侧只产生**一份**监听与转发配置。

**不为 SNI 分流规则生成按目标的计数链。** 计数链按 (监听端口, 目标 IP, 目标端口) 建条目，而同组 SNI 分流规则这三项完全相同，照常生成会得到互相覆盖的重复条目，并把整组流量重复记到某一条规则头上。

**隧道路径下同组规则共用一个出口端口**，不逐条预留，否则上百条规则会耗尽出口 Agent 的隧道端口池。

### 计量、限速与连接数

三者全部由分流器按匹配到的规则执行。这不是选择而是必然：入口不解析 SNI，对同组全部规则的转发行为完全一致，在入口侧物理上无法分账。流量上报以规则为键，一个分流器进程在一次批次里上报多个规则的数值。

### 运行状态语义

单条 SNI 分流规则的「运行中」定义为：**该域名已出现在出口主机当前生效的配置版本里**。不能沿用「端口已监听」——那对同组全部规则永远是同一个答案，等于没有状态。

分流器额外上报：当前生效配置版本、上次配置错误原因、未匹配连接计数。

### 分流器端口的来源限制

随分流器配置一起下发防火墙规则，只放行链路上游主机地址，其余丢弃；上游主机地址变更时自动更新；规则带可识别标记以便对账清理；分流器停用或删除时一并清理。上游引用入口组时覆盖全部成员地址。

这一项不是可选加固。入口到出口那一段若是内核 NAT 一类的纯 L3/L4 搬运，不携带任何身份，分流器无法区分上游转来的连接和外部直连。若落地机把出口主机地址加入了信任白名单（常见做法），未设防的分流器端口等于把落地机暴露在一个被信任的位置上。

### 批量导入契约

```
规则名#SNI域名#目标地址#目标端口
```

每行一条，先选链路资源、入口端口在导入面板填一次。沿用现有批量导入的上限与失败保留策略：单次上限 500 条，失败行留在输入框供修正重试，成功行不重复创建。IPv6 落地地址沿用 `[地址]` 形式。

**必须关闭现有的端口冲突自动回退。** 现有手动导入在遇到端口冲突时会把源端口改成自动分配再重试；SNI 分流规则的端口是整组共享的，这个回退会把规则从组里踢出去，变成一条监听随机端口、永远收不到流量的孤儿规则。

### 前端

规则表单的 SNI 输入仅对管理员、且在选中支持分流的链路资源时出现；填写后协议锁定为 TCP，目标地址标注为落地机。列表增加域名列与域名搜索，同一入口端口上的规则归组展示，出口主机离线时在组上提示整组不可达。

## Testing Decisions

好的测试只断言外部可观察的行为：给定一批规则，Agent 应该被告知做什么；给定一段字节流，哪台落地机收到了连接；给定一行文本，解析出什么或报什么错。不断言内部函数被调用了几次，也不断言中间数据结构的形状。

### 缝 1 — 转发规则 router，配临时 SQLite

覆盖全部面向用户的规则行为：同端口共存、域名重复被拒并指出冲突对象、端口独占的双向拒绝、协议锁定、管理员限定、Agent 版本门槛、域名规范化。

在子进程里连接临时 SQLite、建表、用裸 SQL 铺设主机与链路资源，然后调用真实的 tRPC router。断言点是 router 的返回值与库中最终状态。

**Prior art**：`server/rulesPortAvailability.test.ts`（同样是端口冲突语义 + 真实 router）、`server/ruleQuotaReservations.test.ts`、`server/portReservations.test.ts`。

### 缝 2 — 心跳期望状态，配同一套 SQLite 夹具

这是唯一能一次性验证"从库中的规则行到 Agent 实际行为"的地方。用缝 1 建出规则后，向心跳路由索取期望状态，断言：

- 入口主机对整组只得到**一个**监听
- 入口的转发目标是分流器，落地机地址**不出现**在入口侧任何配置里
- SNI 分流规则**不产生**计数链条目
- 同组规则**不逐条**预留隧道出口端口
- 出口主机拿到推导出的分流表、配置版本号与来源白名单
- 推导出多台出口主机时被拒绝，而不是静默取第一台

这道缝是新开的：目前没有测试这样驱动过心跳路由。但它由两种既有风格接合而成，不引入新的测试基础设施。

**Prior art**：`server/agentTrafficRoute.test.ts`（DB 夹具 + Agent 面向路由）与 `server/agentHeartbeatGate.test.ts`（断言生成出来的配置内容）；命令生成的断言风格参考 `server/agentActionCommands.test.ts`。

### 缝 3 — 分流器监听器，真实 socket

在 `forwardx-fxp` 包内起真实监听器，往里灌构造好的字节，断言：

- 命中时哪台落地机收到连接，且**握手字节逐字节原样**到达
- 四种未匹配情况各自被断开
- 带 ECH 扩展但明文 SNI 可读时正常路由，且握手字节原样到达（GREASE ECH 在真实流量中极其普遍）
- ClientHello 跨多段到达时能正确拼接
- 畸形长度字段、超长扩展、非 TLS 字节不 panic、不越界、不无限等待
- 热换表时爆炸半径精确到单条规则：持续跑连接的前提下改其中一条，只有该条被断
- 流量按规则分账，一次批次带多个规则且数值与实际字节一致
- 限速与连接数上限按规则各自生效

**字节解析器不单独开缝**，畸形与分片输入也从监听器灌入。

## Out of Scope

- **每条规则的多落地机、故障转移与负载均衡。** v1 每条 SNI 分流规则只有一个落地机。
- **同一入口主机上的多组分流。** v1 只支持一个入口端口一组；分流表的存储与校验按「主机 + 端口」分组设计，以便后续放开时不动数据结构。
- **出口容灾。** 转发链不支持出口组，因此出口主机是单点，宕机则该端口上全部落地机不可达且无自动切换。这是一个独立的正交需求，不塞进本次范围。
- **用户自助创建 SNI 分流规则。** 管理员专用，因此套餐额度（端口数与规则数）如何计算的问题在本次不需要回答。
- **通配符域名匹配。** 只做精确匹配。通配会引入优先级规则、重叠检测和"这条连接为什么走了那台机器"的可解释性问题。
- **UDP 与 QUIC。** QUIC 的 SNI 位于加密的 Initial 包内，是另一个量级的工作。SNI 分流规则的协议锁定为 TCP，入口端口的 UDP 不监听。
- **保留客户端真实 IP。** 落地机看到的来源是出口主机。

## Further Notes

**入口到出口那一段的选择是部署决策，不是代码决策。** 分流器与链路类型解耦，因此可以按场景权衡：

| | CPU（每 Gbps，估算） | 新连接额外 RTT | 该段的 SNI | 端口自带认证 |
| --- | --- | --- | --- | --- |
| nftables 转发链 | < 1% 核 | +0 | 明文 | 无，依赖来源白名单 |
| realm 转发链 | 5–15% 核 | +0 | 明文 | 无，依赖来源白名单 |
| ForwardX 隧道 | 拷贝 5–15% + 加解密 2–10% 核 | +1 × 上下游 RTT | 加密隐藏 | 有，每连接握手认证 |

当前部署采用 **nftables 转发链**：大流量长连接下省掉一次用户态拷贝与加解密，海量短连接下省掉一个往返。代价是该段 SNI 明文，且分流器端口的防护完全依赖来源白名单——这正是把白名单列为必需项而非可选加固的原因。

**已知风险**（需在界面与文档中明示）：

- **出口单点**：出口主机宕机则该端口上全部落地机不可达，无自动切换。
- **端口指纹**：入口端口只对特定域名有反应，这是可观测的特征。由于入口是原样透传，对外公开的入口地址表现相同。
- **客户端 IP 不保留**：落地侧无法做基于客户端 IP 的限制或审计。

**ECH 判定已于上线后更正。** 本规格最初写的是「带 ECH 的连接按无 SNI 处理」，实现照此丢弃了一切带 `encrypted_client_hello` 扩展的连接。这条规则把「扩展存在」当成了「信息不可得」的证据，而 Chrome 指纹的 GREASE ECH 明文 SNI 完全真实可读，结果是所有伪装成 Chrome 的客户端被静默丢弃。现行规则见上文连接处理契约一节，完整证据与修复方案见 `.scratch/sni-routing-ech/spec.md`。

**验证方式的教训**：用 `openssl s_client` 之类手工 TLS 工具测通，**不构成 SNI 分流可用的证据**——它们不发送 GREASE ECH，走的是与真实客户端不同的代码路径。验收必须用携带 Chrome 指纹的真实客户端。

**术语纪律**：面板与文档中，用户管理的始终是**SNI 分流规则**；**分流表**是分流器运行时持有的派生物，不出现为可创建的对象。这个区分一旦模糊，就会出现"分流表在哪个页面建"这类问题。词汇定义见 CONTEXT.md。
