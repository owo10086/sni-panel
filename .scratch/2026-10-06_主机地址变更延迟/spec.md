# 取消 SNI 分流端口的来源 IP 限制

**Status:** ready-for-human（已就地上线并完成现有链路验收，真实公网换 IP 等剩余验收待补齐）

**Decision date:** 2026-10-06

**决策：** 删除 SNI 分流自动维护的来源 IP 放行名单，并清理已下发到主机的对应防火墙规则。入口从旧 IP A 换成新 IP B 后，出口分流器不再因为只允许 A 而拒绝 B。本规格替代此前“根据存活请求来源纠正主机地址”的方案；目录沿用原名，任务以本文和当前 `工单/` 为准。

## 问题与目标

当前 SNI 转发链出口按上游主机地址生成放行名单。入口换 IP 后，即使客户端已能访问新入口、入口也已能到达出口，出口仍可能只允许旧地址。面板等待 Agent 上报新 IP，再刷新名单，导致实际分流持续中断。

2026-09-22 的历史实验记录中，中断约 5 分 56 秒，其中面板尚未获得新地址约 5 分 42 秒，随后约 16 秒恢复。这是旧实现的一次实测，不是新方案的时限保证。

本轮目标是消除“入口来源 IP 改变 → 必须等待面板更新出口名单”这一依赖。完成升级清理后，只要客户端已经到达新入口、入口到下一跳的网络恢复、链路目标和 SNI 路由仍有效，新连接就不应因来源地址变化而被本功能拒绝。

客户端仍访问旧 IP、DNS 缓存尚未更新、出口或中继自身换 IP、操作系统或云安全组另有来源限制，都可能继续造成中断。本轮不能承诺这些场景也因删除名单而恢复。

## 删除范围与直接影响

本轮删除的是 **SNI 分流功能自动生成的来源 IP 限制**，覆盖转发链出口按上游地址生成的名单，以及隧道 SNI 出口只允许 `127.0.0.1` / `::1` 的名单。入口分流器和单机端口转发原本就不限制来源，继续采用相同行为。

主机防火墙的其他规则、云安全组、中国区域白名单插件、普通隧道认证、端口占用校验中的允许复用规则，不属于本次删除范围。

**直接影响：** 在网络和其他防火墙允许访问的前提下，任意来源都可以直连出口分流端口，并使用已配置的 SNI 域名访问对应目标。删除 IP 名单不会给 SNI 转发链增加账号或密钥认证；知道正确域名不等于获得了身份认证。若目标服务仅信任出口主机 IP，这种直连同样会以出口身份访问目标。以上是本次功能删除必须明确说明的行为变化。

无 SNI、未匹配域名或无效握手仍按现有规则拒绝；来源限制删除不会变成可指定任意目标的通用代理。按规则限速、连接数限制和出口流量计量继续生效。出口“未匹配连接”还可能来自外部直连探测，不能再把它直接解释为入口与出口配置未同步。

## 实施决策

### 1. 以面板改动完成，兼容现有 Agent

当前拦截由 `server/agentActionCommands.ts` 生成的 nftables / iptables 命令执行。`forwardx-fxp` 中的 `SourceAllowIPs` 只参与配置解析和规范化，连接接入逻辑没有使用它进行来源判断。现有 Agent 已支持空名单与清理命令，入口分流器已有相同下发方式。

因此本轮以面板修改完成，不要求升级 Agent 或 FXP runtime。保留必要的兼容字段，下发 `sourceAllowIps: []`；不为删除字段而更改协议。移除面板收集上游 IP、按地址族生成名单及安装来源拦截规则的业务路径。

旧 Agent 会拒绝 `commands` 为空的 `sni-splitter` 应用动作。应用动作必须携带实际的旧规则清理命令，不能直接改成空命令，也不能用无意义的成功命令替代清理。

### 2. 升级必须清理已存在的规则

仅停止生成新名单不能解决旧主机仍被拦截的问题。升级时要删除本项目为 SNI 来源限制生成的允许项和兜底丢弃项，覆盖 nftables、iptables、ip6tables；主机上两套后端都留有规则时均须处理。

清理按 `fwx-sni-splitter-<port>:` 等现有明确归属标记定位，不清空整张防火墙表，不删除普通转发、计数、插件或管理员自行设置的规则。清理须可重复执行，重复应用、Agent 重连和主机重启后都不能重新安装来源名单。

既要清理仍在使用的分流端口，也要检查并清理本项目标记下已停用、删除或退役端口的来源限制残留。清理名单不意味着重新开放或启动这些退役端口的监听器；孤立的旧分流进程属于另一个问题。

现有清理命令会忽略部分删除错误，不能以命令最终返回成功直接证明迁移完成。实施时应补齐可观察的清理结果：明确不存在的规则视为成功；发现目标规则仍然残留或无法核实时，报告失败并允许后续下发再次清理。

### 3. 区分旧状态迁移与清理后的稳定状态

已有 Agent 可能上报非空 `sourceAllowIps`，即使路由和监听均一致，也必须得到清理动作，不能提前被判为“无需更新”。同时要覆盖未上报来源元数据或本地元数据为空、实际防火墙仍留有旧规则的升级场景；不能仅凭空字段推定已清理。

当前 `localSniRuntimeMatches` 会把“期望名单为空”直接判为不匹配。该判断需要一起修正：成功清理并确认路由状态后，空名单应能稳定匹配，后续相同心跳不因空名单永久重复应用。

保留旧名单的识别与清理兼容能力，但退出按主机 IP 维护名单的日常逻辑。入口地址变化不能仅因为已删除的名单而触发额外防火墙改写。主机地址变更原有的 DDNS、连接目标迁移和配置处理仍按现有机制执行。

清理失败、应用失败或升级过程中重启时，恢复执行条件后要由正常心跳或配置重试自动继续迁移，无需人工刷新或修改规则，且不能把尚未成功的动作记成完成。使用现有配置下发和失败重试机制解决清理的生命周期；这不需要此前为主机地址迁移设计的来源保护期限、旧地址快照或持久待办方案。

### 4. 保留原有主机地址上报机制

本轮不修改存活上报、心跳和注册接口的地址写入策略，不增加按连接来源纠正地址的功能，不增加按 IPv4 / IPv6 保存的保护状态，也不增加用于主机地址迁移的持久待办。

此前讨论的“有效来源与旧自报冲突”“双栈自报兜底”“主机地址已经提交但旧连接地址迁移失败”等问题不作为本轮实施任务。现有主机地址迁移在中途失败后可能不自动恢复的缺口仍然存在，删除名单并没有修复它；如继续优化通用地址同步，应另立方案。

### 5. 同步使用说明

实施时更新 `docs/guide/sni-routing.md`：说明出口分流端口不再由面板限制来源，已匹配域名的请求仍按路由转发；修正出口未匹配计数的解释。发布说明记录旧规则清理、现有 Agent 兼容性以及直接访问出口的行为变化。

旧 SNI 规格中的“来源限制必须存在”“出口仅允许上一跳”“未匹配主要代表双端未同步”属于原决策。本轮为这些文档添加替代说明，保留历史实施记录；实际用户指南在功能实施时更新，不能提前声称线上已经取消限制。

## 验证与验收

核心通过条件是：**迁移完成后，面板仍保存旧入口地址 A，来自新地址 B 的有效 SNI 请求也能通过；无需等待地址上报、名单更新或额外刷新。**

- 面板真实心跳接口生成的 SNI 期望状态不再安装按来源地址允许或丢弃的规则，兼容名单为空，并包含必要清理动作。
- 带旧非空名单、本地状态缺少名单、空元数据但仍有旧防火墙规则等升级场景，都能清理后收敛；重复心跳不因空名单一直重发。
- 在 Linux 上预置真实旧规则，分别覆盖 nftables 与 iptables / ip6tables；应用新配置后确认对应标记的规则消失，其他规则保留。清理失败后能够重试，重启后不复活。
- 来源变化必须用真实 TCP / TLS 连接验证，例如两台测试主机或网络命名空间提供 A、B 两个来源。向 HTTP 请求添加转发头不能证明 SNI 数据流已恢复。
- 面板数据库保持 A，现有 SNI 路由和下一跳不变，从 B 发出匹配域名的新连接应到达正确目标；再以数据库未登记的来源 C 验证直连行为，明确这是删除来源限制后的预期结果。
- 覆盖转发链两跳、多跳与入口组、隧道 SNI、单机端口转发，以及 IPv4 / IPv6 可用环境。多跳中最后一跳来源发生变化时也不再受旧名单阻挡。
- 保留未匹配域名拒绝、路由热更新、限速、连接数限制和出口计量的相关回归。普通隧道和其他防火墙功能不受清理影响。
- 面板期望状态测试不能替代实际 Linux 防火墙和网络验证。任务 02 负责自动验证，任务 03 负责部署升级与真实换 IP 验收。

不再使用“5 秒发现 + 16 秒收敛 ≈ 20 秒”作为本轮通过标准。分别记录网络恢复、首次从 B 发起请求、首次请求成功、面板记录更新的时间，并记录相关事件通道状态。受控验证应证明面板记录尚未更新时已经可以转发；真实换 IP 则报告实际中断时间，并将客户端地址、DNS 和网络不可用的等待说明清楚。事件通道是否在线不应在迁移完成后成为新来源获准访问的条件。

## 上线、回退与发布

沿用先就地验证再正规发版的顺序。就地验证替换运行容器中的 `dist/index.js` 构建产物并重启加载，不能只复制 TypeScript 源文件。验证前记录实际运行镜像 ID / digest，回退按该标识重建容器，不能仅重启或依赖可能已变动的 `latest` 标签。

**回退还涉及主机防火墙状态。** 回退面板镜像不会自动把已经清掉的名单重新装回主机。若要恢复旧行为，需让旧面板重新下发旧版 SNI 配置并核对防火墙规则；版本回退与来源限制恢复必须分别验收。

验证通过后：按改动范围更新版本并提交 → 创建版本标签 → 将 `main` 与该版本标签一并推送到 `sni-panel` → 等待发布与镜像构建成功 → 拉取对应版本镜像并重建容器 → 核对版本、清理结果和实际转发。`origin` 仅作为上游参考，不推送代码、标签或发布内容。

## 历史依据

上游普通 GOST / ForwardX 隧道使用凭据识别连接方。只更换入口来源 IP、出口目标不变时，原有凭据仍有效；客户端能访问新入口且网络恢复后，通常可以重新连接。当前 SNI 转发链按上游 IP 设置名单，额外引入了等待面板获知新来源的依赖。本轮移除的就是这层依赖，不声称给 SNI 转发链增加与普通加密隧道相同的认证。

2026-09-22 受控实验的原始时间线（UTC）保留如下，仅作为旧行为依据：

| 时刻 | 事件 |
| --- | --- |
| 15:24:04 | 触发换 IP |
| 约 15:24:2x | IP 实际变化，入口到出口分流端口开始被拒 |
| 15:25:03 | 入口主机自己已能查到新地址 |
| 15:25:22 | Agent 事件通道重连 |
| 15:25:22–15:30:08 | 心跳可达，面板仍保存旧地址 |
| 15:30:08 | 面板从完整心跳获得新地址 |
| 15:30:10 | 入口组 DDNS 更新 |
| 15:30:12 | 出口收到刷新通知 |
| 15:30:17 | 出口防火墙放行值更新 |
| 15:30:24 | 分流恢复 |

原方案及其评审讨论中的来源判定、单写者、按族保护、持久地址迁移重试等路线均由本次决策替代，尚未进入实现。发版必须创建并推送标签这一修正继续适用；双栈验收改为两族均不再由 SNI 自动来源名单拦截，不再要求生成新 IPv6 放行项。


## 2026-10-06 实施记录

面板已停止生成 SNI 自动来源名单，所有分流角色下发空兼容名单及实际清理命令。升级迁移通过现有 runtime 动作清理全主机 SNI 标记，包括退役端口；同时核实原生 nftables、iptables/ip6tables 的当前入口及 nft/legacy 显式入口。仅本轮成功回报完成迁移，失败正常重试，Agent 会话变化或面板重启后重新核实。

本地类型检查、面板 690 项测试、Agent 全套回归、Linux FXP 全套回归及真实防火墙/TLS 验证通过。受控验证中，面板数据库入口地址始终为 A，旧规则阻挡 B，清理后 IPv4/IPv6 的 B 与未登记来源 C 均能完成匹配域名的 TLS 请求；未知域名和无 SNI 仍拒绝，分流器重启不恢复旧名单。

完整本地证据和复现命令见[验证记录](验证记录.md)。2026-10-07 已从本机 SSH 配置找到目标环境，完成就地上线、三个在线 Agent 的旧规则清理、真实公网来源 A/B/C 对照、正常心跳失败重试和事件通道断开验收，详见[线上验收记录](线上验收记录.md)。真实入口公网换 IP、真实账号登录及生产环境暂不具备的拓扑验收仍待补齐。发布说明暂留 CHANGELOG 的“未发布”，版本递增、标签和推送须按原定顺序在验收通过后执行。
