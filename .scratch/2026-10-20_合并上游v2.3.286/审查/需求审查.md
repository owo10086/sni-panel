# 286 需求审查报告

**结论：目前不建议直接拆单。** 有两处范围未闭合，另有一项自动换 IP 后的 DNS 行为需要主代理按默认模式进一步确认。审查以固定本地提交 `563b1c691827f7ca13d3e8a687663b65f99f6b53` 对照目标 `aca5d5dfb645393b6925f155ff7258006f46204e`；没有把 285 当作本地起点。

## 必须先处理

### 1. 自动换 IP 后的 DNS 更新与 SNI 确认顺序未说清

**严重程度：高；拆单前阻塞。位置：** [规格 D04](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-20_合并上游v2.3.286/spec.md:82)、[验收 A10](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-20_合并上游v2.3.286/spec.md:131)。

**证据：** 讨论记录已指出上游换 IP 流程“没有直接调组 DDNS，也没有直接令 SNI 完整确认失效”，并要求重新核对。[目标源码](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-20_合并上游v2.3.286/证据/上游原文/server/hostProbeHealth.ts:124)更新 `entryIp`／`tunnelEntryIp` 后调用运行时刷新；本地的 `refreshHostAddressRuntime` 与调度主机、组 DDNS 的 `handleHostAddressChanged` 是不同入口。[本地组 DDNS](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/server/repositories/forwardGroupRepository.ts:666)会用主机入口地址作为组记录值，另有专门的地址变更调度入口。

**用户后果：** 按上游路径合入后，自动换 IP 是否会刷新主机或组 DNS、何时刷新，以及 SNI 配置未确认时如何保留旧解析，没有唯一的验收预期。可能出现解析仍指向旧地址，也可能在新配置未确认前发布新地址。

**建议：** 在拆单前明确 `entry` 与 `entry_and_tunnel` 两种模式分别触发哪些 DNS 更新；若更新涉及 SNI，应明确当前完整配置、入口检测、观察等待和发布前复核如何共同决定新地址何时可发布。讨论记录已标出这一边界，属于新增行为取舍，交主代理按默认模式处理，不能由实施者自行假定。

### 2. 337 项上游变化中仍有 174 项未确定处理归属

**严重程度：高；拆单前阻塞。位置：** [范围决策 D01](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-20_合并上游v2.3.286/spec.md:60)、[逐文件清单](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-20_合并上游v2.3.286/本地对照清单.md:18)。

**证据：** 固定变化清单有337项；其中174项的处理标记仍是“待逐段核对”。例如自动换 IP、主机 DDNS 和 MCP 源码条目均尚未标为纳入、拆分、保留或排除。D01 又要求逐文件记录处理方式和指纹，A01 将此列为验收条件。

**用户后果：** 现在开工单时无法确认每项上游变更归属哪个需求或工单，容易漏掉网页／服务端功能，或把原生客户端内容带进混合文件。

**建议：** 拆单前补全变化清单的处理结果，并将需要实施的变更对应到工单和验收项；明确排除的内容按长期约定标记，不能留作待办。

### 3. 混合 CI 与依赖文件会带入 iOS 专属检查

**严重程度：高；拆单前阻塞。位置：** [清单中的 CI 与 package.json 条目](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-20_合并上游v2.3.286/本地对照清单.md:21)、[客户端排除约定](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/AGENTS.md:11)。

**证据：** 固定起点到目标的 `git diff` 显示，目标新增 `test:ios` 脚本，运行 `scripts/ios-build.test.mjs` 和 `client/src/lib/mobileAppUpdate.test.ts`；目标 CI 也新增 `pnpm test:ios`（[上游补丁中的 CI 变化](/Users/macmini/Documents/Aixiaoji/haproxy-sni/Forwardx/.scratch/2026-10-20_合并上游v2.3.286/证据/上游285到286.patch:40)，脚本变化见 `aca5d5d:package.json`）。而长期约定要求跳过原生应用代码、专属内容及发布相关流程。规格要求拆分混合文件，但没有点名排除该脚本及 CI 调用。

**用户后果：** 若按“CI 共用内容”整体合入，网页／服务端 CI 会开始运行原生 iOS 构建与应用更新相关检查，使已排除的客户端内容进入本轮验证和交付范围。

**建议：** 在文件处理清单中明确排除 `test:ios` 脚本和 CI 调用，同时保留确属网页构建的客户端交付检查；不要把网页客户端目录整体排除。

## 普通建议

验收结果整体可观察，但 A04、A21、A22 等条目把多种场景放在一起。拆票时建议将权限、计费、导入、三类数据库迁移、网页构建等分别写成可执行场景，并在验证记录中注明实际使用的检查入口和未覆盖项，避免把“仍需核查”写成“已通过”。
