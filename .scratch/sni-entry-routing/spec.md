# SNI 分流：入口按域名选链路

**Status:** claimed

**Extends:** `.scratch/sni-routing/spec.md`。那份规格把「区分落地机的维度从端口挪到域名」做完了；本规格把同一件事再往前挪一跳——让域名也能决定**走哪条线**。不改动出口分流器的任何既有行为。

**Requires ADR revision:** ADR-0001 的理由段、ADR-0002 的运行状态定义。见「文档」。

## Problem Statement

一个入口端口只能交给一个下一跳，所以同一个入口端口上的所有域名必然走同一条线路。

管理员想让 a.com 从入口主机走线路 A、b.com 从**同一台入口主机的同一个端口**走线路 B——两条线常常是不同 ISP、不同价格、不同质量——今天做不到。在第二条转发链上建规则时，面板拒绝：

```
入口端口 443 已被其它转发链的 SNI 分流规则「sni香港1」（ID 9） 占用
```

这不是校验过严，是架构使然：**入口不解析 SNI**。入口端口上跑的是 gost 或 nginx 的哑转发，它拿不到任何可用来区分的信息，配置里也只有一个下一跳的位置。ADR-0001 当初把分流器放在出口，这条限制就是那个决定的直接后果。

绕过去有三条路，每条都要付代价：

**换一个入口端口。** 客户端必须知道自己该连 443 还是 8443，管理员发出去的又变成一张端口对照表——正是 SNI 分流当初要消灭的东西。

**串联。** 把线路 B 的出口当作线路 A 出口分流器的一个落地机，在那里再分一层。b.com 的流量要先绕道线路 A 的出口，带宽和延迟双重浪费；而且线路 A 一挂，b.com 跟着挂——本该并联的两条线变成了串联。

**多一台入口主机。** 为了区分线路而多买一台机器，两个域名的解析还要分开维护。

## Solution

**在入口也放一个分流器。**

入口分流器读客户端握手里的域名，据此决定把连接交给哪条转发链的下一跳；出口分流器照旧决定交给哪台落地机。同一个入口端口上因此可以并存任意多条转发链。

```
                      ┌─ a.com ─→ 线路A 出口分流器 ─→ 落地A
入口主机:443 分流器 ──┼─ b.com ─→ 线路B 出口分流器 ─→ 落地A
                      └─ c.com ─↗                  ↘ 落地C
```

转发链上每一跳本来就是纯 TCP 转发，所以入口分流器可以**直接拨远端的下一跳**，不需要任何回环端口，跳数与今天完全相同。

入口端口上的分流表由面板从所有指向该「入口主机 + 入口端口」的 SNI 分流规则自动聚合得出。**不引入新的链路资源**——分流表仍然是派生物，与既有领域词汇一致。

管理员的录入方式一个字不变：选转发链 A、填 a.com、入口端口 443；再选转发链 B、填 b.com、入口端口 443。只是不再报错。

## User Stories

### 分流与选路

1. 作为管理员，我想让同一个入口端口上的不同域名走不同的转发链，从而按线路质量或成本区分客户，而不必给他们不同的端口。
2. 作为管理员，我想让两条以上的转发链共用同一台入口主机的同一个入口端口，从而一个对外端口就能覆盖多条线路。
3. 作为管理员，我想让同一条转发链上依旧能挂多台落地机，从而选路能力是叠加在既有分流能力之上，而不是取代它。
4. 作为管理员，我想让录入方式与今天完全一致（选一条链路资源、填域名、填入口端口），从而不必为这个能力学一套新模型。
5. 作为管理员，我想让这个能力不要求我新建任何资源，从而我的资源列表不会因为它多出一层。
6. 作为终端用户，我想连同一个入口端口、用自己的域名握手就能到达对应线路和落地机，从而不必知道自己走的是哪条线。
7. 作为管理员，我想让入口分流对转发链的转发方式不再敏感，从而内核转发的转发链也能承载 SNI 分流规则。
8. 作为管理员，我想让三跳以上的转发链同样适用，入口分流器拨向下一个中转成员，从而这个能力不限于两跳链。

### 校验与防错

9. 作为管理员，我想在同一个入口端口上建属于不同转发链的 SNI 分流规则时不再被拒绝，从而上面那件事真的做得成。
10. 作为管理员，我想在同一台入口主机上录入重复域名时仍然被拒绝，并被告知与哪一条规则冲突，从而不会建出一条永远收不到流量的规则。
11. 作为管理员，我想在入口端口已被普通转发规则占用时仍然无法建 SNI 分流规则，反之亦然，从而不会出现两套语义争抢同一个端口。
12. 作为管理员，我想在入口主机的 Agent 版本不足以运行分流器时被直接拒绝创建，并被告知所需的最低版本，从而不会建出一条静默不生效的规则。
13. 作为管理员，我想让入口主机的版本门槛与出口主机是同一个，从而不必记两个版本号。
14. 作为管理员，我想在修改规则、启用此前停用的规则、批量导入时都受到同样的入口版本检查，从而各个入口的行为一致。
15. 作为管理员，我想让表单的实时预检结论与保存时的结论一致，从而不会出现界面说可用、提交却报占用。

### 入口组

16. 作为管理员，我想让引用了入口组的转发链继续能建 SNI 分流规则，从而现有生产规则不被这次改动打掉。
17. 作为管理员，我想让每台入口主机的分流表只包含真正指向它的规则，从而分流表如实反映配置，不凭空多出它根本到不了的线路。
18. 作为管理员，我想在某个入口端口于不同入口主机上域名集合不一致时得到明确提示，从而「客户端有时通有时不通」不会成为一个只能靠猜的故障。
19. 作为管理员，我想让入口主机集合不一致本身不被拒绝，从而「小客户单入口、大客户双入口」这种配置仍然做得出来。

### 运行行为

20. 作为管理员，我想让入口分流器对域名不在表里的连接立即断开，从而配错一个字母会立刻暴露，而不是把流量安静地送到别处。
21. 作为管理员，我想让不带 SNI、非 TLS、握手未在读取窗口内收完的连接在入口就被断开，从而这个端口不会成为一个无差别的通用跳板。
22. 作为管理员，我想让「兜底转发」在入口这一层也根本不存在，从而入口与出口的未匹配语义一致。
23. 作为终端用户，我想让我的 TLS 握手逐字节原样穿过入口分流器到达落地机，从而对握手完整性敏感的后端能够正常工作。
24. 作为管理员，我想让入口分流器不限制来源 IP，从而它能正常接收来自公网的客户端连接。
25. 作为管理员，我想让出口分流器的来源 IP 限制保持不变，从而出口仍然只接受来自上一跳的连接。

### 变更与运维

26. 作为管理员，我想在某个入口端口上新增一条 SNI 分流规则时不断开该端口上任何既有连接，从而扩容对在线客户完全无感——**包括属于其它转发链的域名**。
27. 作为管理员，我想在删除某条 SNI 分流规则时只断开这一条的连接，从而同一端口上其它线路的客户不受牵连。
28. 作为管理员，我想让入口分流器的身份不取自任何一条具体规则，从而删掉编号最小的那条规则不会让整个入口配置改名重启、把该端口上所有线路的连接一起踢掉。
29. 作为管理员，我想在一条规则的落地机地址变更时只影响这一条，入口侧完全不受影响。
30. 作为管理员，我想在入口分流器下发的配置校验失败时，正在生效的那份保持不变、业务不受影响，并能看到失败原因。

### 限速与计量

31. 作为管理员，我想让每条 SNI 分流规则的限速与连接数上限仍然只在出口分流器执行，从而一个数字只在一个地方生效。
32. 作为管理员，我想让限速与流量统计取自同一个点，从而「限了 100、统计出来对不上」这种困惑不会发生。
33. 作为管理员，我想让入口分流器即使开始按域名产生流量数字也不会被计入账单，从而不会重复计费。

### 可观测

34. 作为管理员，我想在入口分流器和出口分流器都确认某个域名已生效之后，这条规则才显示为运行中，从而「运行中」意味着这条规则真的能通。
35. 作为管理员，我想在某条规则未运行时看出是入口没生效还是出口没生效，从而知道该去哪台机器排查。
36. 作为管理员，我想分别看到入口与出口的未匹配连接数，从而区分「客户端域名对不上」和「入口与出口配置不同步」。
37. 作为管理员，我想在未匹配计数旁看到一句说明它代表什么，从而不必记住两个数字的差别。

39. 作为管理员，我想看到入口分流器最近一次配置下发失败的原因，从而不必登上机器翻日志。

## Implementation Decisions

### 入口分流器

入口端口上的受管运行时，从 gost / nginx 的哑转发监听器改为 `sni-splitter` 角色的受管运行时。这与出口分流器是**同一个角色、同一套下发格式、同一个 Agent 版本门槛**——Agent 侧对该角色的处理只看「角色名、监听端口、路由表」三样，没有任何出口专属假设，因此 Agent 无需新增能力。

入口分流表的每条路由，目标是**该规则所属转发链的下一跳地址与端口**：两跳链（入口 + 出口）下即出口主机的分流器端口；更长的链下即下一个中转成员的监听端口。这两个值今天已经按规则存着，聚合不需要新增字段。

入口分流器**不设来源 IP 限制**——它面向公网。出口分流器的来源限制原样不动。

入口分流表的路由**不携带**限速、连接数上限、最大 IP 数、访问范围。

### 聚合与身份

入口期望状态的分组键，从「转发方式 + 入口端口 + 目标地址 + 目标端口」收敛为**「入口端口」一个维度**。出口分流器已经是这么做的（只按分流器端口聚合，把多条规则的路由聚成一张表，且不看规则记的转发方式），入口照同一形状写。

聚合逻辑**不看规则属于哪类链路资源**。这不是为将来做的抽象——不看资源类型本身就是更短的写法，写死资源类型反而要多加判断。

**入口分流器的身份必须取自「入口主机 + 入口端口」，不得取自组内任何一条具体规则。** 取自规则会让删除该规则触发配置节点改名与受管运行时重启，把该端口上**所有转发链**的连接一并踢掉。出口侧已经因为同一个原因改成按分流组取身份（ADR-0002），跨链之后这个爆炸半径比当初更大。

分流表变更走分流器已有的热更新通道：换表不动监听 socket，只断开本次确实改变了的那几条规则的连接。

### 校验

**撤除**「同一入口端口上的 SNI 分流规则必须属于同一条链路资源」这条判定，以及它在表单实时预检里的对应分支。转发链与隧道各有一条，本期只撤转发链那条。

**保留**：同一台入口主机上域名唯一（跨端口、跨承载资源）；入口端口被普通转发规则占用则不能建 SNI 分流规则，反之亦然；端口范围与套餐策略。

转发链同步时的入口端口占用白名单，从「同一条链的 SNI 规则」扩大到「同一入口主机同一入口端口上的所有 SNI 分流规则」。**这个白名单与上面那条判定必须同源**，否则会出现校验放行、同步报错。

新增入口主机的 Agent 版本检查，门槛沿用出口使用的同一个常量。检查覆盖创建、修改、启用与批量导入四条路径。

### 未匹配计数

入口与出口的未匹配连接数**分别呈现，不合并**。

入口未匹配的含义是「客户端用了这台入口主机上没有配置的域名」——域名拼错、DNS 指到了错的入口主机、或有人在扫这个端口。

出口未匹配在新模型下基本只剩一种成因：**入口与出口配置不同步**。因为入口只会把它表里有的域名送往对应出口，而出口分流器的来源限制挡住了绕过入口的直连。这个数字非零是一个强信号，值得单独呈现。

两者各配一句说明。

### 入口端口全貌

新增一个**只读**查询，按「入口主机 + 入口端口」返回：该端口上的域名、各自所属的转发链、各自的落地机，以及该入口主机的 Agent 版本是否满足分流器门槛。

同一入口端口在不同入口主机上域名集合不一致时，在结果中**标出差异但不拒绝**这种配置——不一致有合法用途（小客户单入口、大客户双入口），而治静默的手段是让它看得见，不是禁止它。

**升级前预检复用同一个查询**，不另开一条遍历路径。它本来就要遍历所有入口主机与端口，版本检查是顺手的。

### 计量

**不改动。** 现有的流量归属判定已经为 SNI 分流链专门分支：只接受出口那条子规则报上来的流量，入口报的一律丢弃。入口分流器开始按域名产生流量数字后，这道判定会继续把它丢掉，不会重复计费。

### 迁移

面板升级后，所有 SNI 分流规则的入口**一律**改用分流器。不保留 gost / nginx 老路，不提供按需切换或长期开关——两种入口形态并存会让「这个端口上到底什么在监听」变成一个得先查才能回答的问题。

入口主机 Agent 版本不足时，该规则**明确报错停摆**，不静默降级。

回滚即面板回滚，接受再断一次连；不提供细粒度回滚开关（那等于把双形态又请回来）。

### 文档

**ADR-0001**：结论（计量、限速、连接数上限由出口分流器承担）保留，但它给出的理由——「入口不解析 SNI，对所有 SNI 规则的转发行为完全一致，在入口侧物理上无法分账」——**已被本次改动推翻**，须替换为新理由：入口可能有多台（入口组），在入口限速会随入口台数放大，而出口是唯一必经点。同时补记分流器角色现在同时部署在入口与出口。

**ADR-0002**：更新「单条规则的运行中需要重新定义」一节，改为两端都生效；并补记入口端口共用的范围已从「同一条链路资源内」扩大到「跨链路资源」，以及随之扩大的爆炸半径。

**领域词汇表**：「分流器」的定义不再限定为出口主机上的角色；补充「入口分流器」与「出口分流器」的区分，以及入口分流表的派生规则。

**CHANGELOG**：记录入口形态的切换与升级时的一次性断连。

## Testing Decisions

好的测试只断言外部可观察的行为：心跳返回的期望状态、路由返回值、落库结果。不断言内部函数被怎么调用，也不断言配置字符串长什么样——除非那串配置本身就是下发内容。

两条缝，**都是现成的，不新增**。

### 缝 1 — Agent 心跳接口，配临时 SQLite

沿用 `server/sniDesiredState.test.ts` 的做法：用原始 SQL 播种主机、转发链、成员与规则，POST 一次心跳，断言返回的期望状态。

覆盖：

- 两条转发链共用同一台入口主机的同一个入口端口时，入口只生成**一个** `sni-splitter` 受管运行时，而不是两个抢同一端口的监听器
- 入口分流表同时包含两条链的域名，每条域名的目标是**它自己那条链**的下一跳
- 入口分流表的路由不带限速、连接数上限、最大 IP 数；不下发来源 IP 限制
- 出口分流器的路由与来源 IP 限制不受影响
- 删除入口端口上编号最小的那条规则后，入口的受管运行时配置**不被重写**（该文件里已有一条针对出口的同形断言，照抄到入口）
- 新增一条域名后，入口分流表新增一条路由，其余路由与运行时身份不变
- 入口或出口任一未确认该域名时，规则不被标记为运行中；两端都确认后才标记
- 转发方式为内核转发的转发链，其入口同样生成分流器
- 三跳链下，入口分流器的目标是中转成员的监听端口而非出口的分流器端口

### 缝 2 — rules 的 tRPC 路由，配同一套 SQLite 夹具

沿用 `server/sniRuleRouter.test.ts` 的做法：用 caller context 调用路由，断言返回值与落库结果。建规则会触发转发链同步，所以这一层**同时验证校验与同步**。

覆盖：

- 在同一台入口主机的同一个入口端口上，为**另一条**转发链创建 SNI 分流规则成功，且两条链的子规则都被建出来。现有的 `forward-chain SNI rules share one entry port and reject duplicate or mixed ports` 用例需要改写——它今天断言的正是要撤除的那条拒绝
- 同一台入口主机上域名重复仍被拒绝，并点名冲突规则
- 入口端口已被普通转发规则占用时仍拒绝建 SNI 分流规则，反之亦然
- 入口主机 Agent 版本不足时拒绝创建，错误信息带最低版本；修改、启用、批量导入三条路径同样拒绝

- **Agent 端口占用上报**：入口端口的占用者从 gost 变为分流器，归类走的是既有的受管运行时识别路径；端口占用重做规格已明确占用警告只对内核转发呈现，SNI 入口本就不产生警告。

## Out of Scope

**隧道。** 隧道的入口进程本身就监听着入口端口，要在该端口放分流器，必须先把隧道入口挪到一个回环端口，并为此新增一套回环端口的分配与回收，还要处理它与隧道出口端口池的竞争。这是独立的一块工作。聚合逻辑按资源无关写，以后加隧道只需放开校验并补上回环端口，不必回头重构。隧道路径上「同一入口端口必须属于同一条链路资源」的拒绝**本期保持不变**。

**端口转发资源。** 它的分流器本来就直接监听入口端口（分流器端口即源端口），只有一台主机、没有「下一跳」可选，不存在本规格要解决的问题。本期不改动它。

**显式的「分流入口」资源。** 分流表仍是派生物，不引入可写的入口资源。它唯一多买到的是可见性，而可见性由只读全貌视图买到，代价低一个数量级。

**入口限速。**

**放开「同一台入口主机上域名跨端口唯一」。** 同一台机器上两个入口端口各持一张分流表，同名域名在技术上不冲突，但本期不放开这条约束，避免把改动面扩大。

**细粒度回滚开关。**

**转发组承载 SNI 分流。**

**通配符域名匹配。**

## Further Notes

### 顺带修好的一个坑

转发方式选了内核转发（iptables / nftables）的 SNI 转发链，**今天是坏的**：生成入口监听器的代码只认 gost 和 nginx，那种链压根不会产生任何监听，而规则表单对转发方式没有任何限制，可以建出这种注定跑不通的组合。改完之后入口一律是分流器、不再看转发方式，这个坑自动填上。转发方式从此只作用于中间跳；两跳链下它完全不起作用。

### 爆炸半径扩大了，这是代价不是缺陷

今天一个入口端口上只有一条链，入口进程挂了只影响这条链；改完之后该端口上有几条链就一起挂。这在物理上无法避免——共用一个端口就是共用一个监听。热更新已经把**日常变更**（加域名、改落地机）的影响压到单条规则，进程挂掉是另一回事。

这也是「入口分流器身份必须取自主机与端口」那条决定之所以是硬性要求的原因：身份一旦跟着某条规则走，一次普通的删除就会把整个端口的连接清空，等于把一个罕见的故障变成日常操作。

### 与姊妹项目的对照

相邻的 relay-panel 用 HAProxy 做同一件事：一个 frontend 绑定入口端口，若干条 `use_backend ... if { req.ssl_sni -i ... }`，每个 backend 指向任意地址；没有 `default_backend`，未匹配一律 `tcp-request content reject`。

两边在未匹配语义、热更新粒度（它用 `-sf` 平滑重载加 runtime socket 只关变化的 route）、精确域名匹配上的结论一致。真正的差别只有一个：**HAProxy 的 frontend 天生是一个以「绑定地址 + 端口」为身份的独立对象，不从属于任何链路**；而 ForwardX 的分流器身份此前是从链路资源派生的。本规格要引进的就是前者那个性质——而且只引进性质，不引进资源。

ForwardX 保留了 relay-panel 没有的两样东西：按域名内建的限速与计量，以及多跳链路编排。它做不了 `入口-出口-落地`，这也是当初迁过来的原因；本规格补上它唯一比 HAProxy 弱的那一处，不让另外两样有任何损失。
