# 分流器不得因 ECH 扩展丢弃带明文 SNI 的连接

**Status:** ready-for-agent

## Problem Statement

管理员为一条链路配好 SNI 分流规则后,真实客户端连不上——**同一条链路在不加 SNI 域名时完全正常**。现场表现是节点建立连接后立刻断开,而且:

- 分流器**不记录任何错误日志**,看不到连接被拒的痕迹
- 面板显示一切正常:分组「全部生效」、规则运行中、延迟正常
- 用 `openssl s_client` 手工测同一个域名,握手完全成功

根因是分流器只要在 ClientHello 里看到 ECH 扩展(`encrypted_client_hello`),就把这条连接当作「拿不到 SNI」直接丢弃。问题在于 **ECH 扩展的存在不等于 SNI 不可读**:

- **GREASE ECH**:Chrome 从 117 起在普通 ClientHello 里发送的诱饵扩展,内容是随机数,**明文 SNI 百分之百真实可读**。任何把客户端指纹伪装成 Chrome 的客户端都会带上它。
- **真 ECH**:真实域名被加密,外层承载一个伪装域名——但**外层的明文 SNI 同样可读**,它正是网络路径上唯一能看到、也是所有 SNI 分流实现据以路由的那个名字。

两种情况下明文 SNI 都在,分流器却一概丢弃。

现场证据(在真实链路上构造两个 ClientHello,唯一差别是带不带 ECH 扩展):

| ClientHello | 结果 |
| --- | --- |
| 不带 ECH 扩展 | 转发成功,收到落地机回应 |
| 带 ECH 扩展 | 连接被立即关闭,零字节 |

管理员侧的独立验证:把客户端指纹从 `chrome` 换成 `ios` 后,同一条规则立刻可用——iOS/Safari 指纹不发送 GREASE ECH。

**这不是实现偏离了规格,而是规格本身写错了。** 现有规格写的是「带 ECH 的连接按『无 SNI』处理,不尝试解密」,实现忠实照做。这句话把 GREASE ECH 和真 ECH 混为一谈,而前者在真实流量里极其普遍。用户文档里「加密客户端问候等无法取得明文 SNI 的连接无法匹配」这句同样把两者混同。

## Solution

**明文 SNI 可读就按它路由,ECH 扩展的存在与否不参与判定。**

判定规则简化为一句话:ClientHello 里能解析出明文 SNI,就查分流表并转发;解析不出任何明文 SNI,才按未匹配处理、断开连接。

对两类 ECH 的实际效果:

- **GREASE ECH**:完全正常工作。Chrome 指纹的客户端不再被误杀,这是本次修复要解决的现场问题。
- **真 ECH**:按外层明文域名路由。这是分流器唯一能做的事,也是所有基于 SNI 的分流实现的一致行为。内层真实域名仍然不解密、不尝试获取。

「未匹配一律断开、不设回落」这条不变(见 ADR-0001 与既有规格),变的只是「什么算未匹配」:**只有真正取不到明文 SNI 才算**。

## User Stories

1. 作为管理员,我想让使用 Chrome 客户端指纹的连接能正常通过 SNI 分流,从而不必为了绕开这个问题去改客户端指纹。
2. 作为管理员,我想让 ClientHello 里带 ECH 扩展但明文 SNI 可读的连接被正常路由,从而伪装扩展不影响分流判定。
3. 作为管理员,我想让真 ECH 连接按外层明文域名路由,从而这类连接不被静默丢弃。
4. 作为管理员,我想让「未匹配」只在真正取不到明文 SNI 时成立,从而这个判定与它的字面含义一致。
5. 作为管理员,我想让完全不带 SNI 的连接继续被断开,从而这次放宽不会削弱既有的拒绝语义。
6. 作为管理员,我想让非 TLS 流量继续被断开,从而分流器仍然只接受 TLS 握手。
7. 作为管理员,我想让握手未在读取窗口内收完的连接继续被断开,从而慢速探测不会长期占用连接。
8. 作为管理员,我想让域名不在分流表里的连接继续被断开,从而配错域名仍会立刻暴露。
9. 作为管理员,我想让带 ECH 扩展的握手字节原样转发给落地机,从而对握手字节敏感的协议不被破坏。
10. 作为管理员,我想让 REALITY 这类依赖 ClientHello 字节完整性的协议在分流器之后正常工作,从而分流不限制可承载的协议种类。
11. 作为管理员,我想让 ClientHello 被 TCP 分片送达时仍能正确重组,从而带 ECH 的大握手不会因分片被误判。
12. 作为管理员,我想让 ECH 扩展出现在扩展列表的任意位置都不影响 SNI 解析,从而不依赖客户端的扩展排列顺序。
13. 作为管理员,我想让同时带 ECH 与 SNI 的握手在多域名分流表下匹配到正确的那条规则,从而放宽判定不会引入错配。
14. 作为管理员,我想让这类连接的流量正常计入所属规则,从而计量不因 ECH 而缺口。
15. 作为管理员,我想让这类连接同样受所属规则的限速约束,从而限速不被带 ECH 的客户端绕过。
16. 作为管理员,我想让这类连接同样计入所属规则的连接数上限,从而上限不被绕过。
17. 作为管理员,我想让这类连接在来源白名单生效时同样受限,从而放宽 ECH 判定不削弱来源限制。
18. 作为管理员,我想让分流表热更新对这类连接的行为与普通连接一致,从而改规则时的影响范围不变。
19. 作为管理员,我想让「未匹配连接数」只统计真正未匹配的连接,从而这个数字恢复为可信的排查依据。
20. 作为管理员,我想让规格与用户文档不再说「带 ECH 的连接按无 SNI 处理」,从而文档与实际行为一致。
21. 作为管理员,我想让用户文档说清楚「带 ECH 扩展但明文 SNI 可读的连接可以正常分流」,从而遇到同类问题时能自查。
22. 作为管理员,我想让修复后的分流器通过常规的 Agent 升级流程装到出口主机上,从而不需要手工替换二进制。
23. 作为管理员,我想在升级分流器后不需要改动任何 SNI 分流规则,从而修复不带来配置迁移成本。
24. 作为管理员,我想让升级分流器时的连接中断范围与既有的分流器重启一致,从而升级影响可预期。
25. 作为运维,我想让这条判定变更有真实套接字测试兜底,从而它不会在后续改动中被无意改回。

## Implementation Decisions

### ECH 扩展不再是丢弃条件

分流器解析 ClientHello 后的判定,从「有 ECH 扩展**或**无明文 SNI ⇒ 丢弃」改为「无明文 SNI ⇒ 丢弃」。ECH 扩展的存在不再进入判定。

### 不尝试区分 GREASE ECH 与真 ECH

两者使用**同一个扩展类型**,且在网络上都以 outer 形态出现,内容都是不可读的字节。**没有可靠的办法把它们区分开**,任何基于长度或内容启发式的判别都会误判。因此不做区分——判定只依据「明文 SNI 是否可读」这一个事实。

这也意味着真 ECH 连接会按外层伪装域名路由。这是可接受的:外层域名是网络路径上唯一可见的名字,而 ADR-0001 已经确立分流器不解密任何内容。

### 握手字节仍然原样转发

分流器读取到的握手字节必须原封不动先发给落地机,这条要求不变,但现在要在**带 ECH 扩展的握手**上同样成立。这一点对 REALITY 之类把认证信息编码进 ClientHello 的协议是硬要求:任何重新序列化都会破坏认证,表现为协议回落到伪装站点、客户端连不上。

### 其余拒绝语义保持不变

「未匹配一律断开、不提供回落」不变(ADR-0001、ADR-0002)。四类未匹配中的三类原样保留:非 TLS 流量、握手未在读取窗口内收完、域名不在分流表里。第四类「无 SNI」的定义收窄为**真正解析不出明文 SNI**。

### 不涉及面板

分流表的推导、版本号、热更新、限速、连接数上限、来源白名单、流量计量全部不变。本次改动完全落在分流器内部,面板侧一行不动。

### 文档与规格更正

三处需要同步更正,否则文档会继续把人引向错误结论:

- SNI 分流规格中「带 ECH 的连接按『无 SNI』处理」一句
- 对应实施工单里「带 ECH 的连接按『无 SNI』处理并断开」这条验收标准
- 用户文档中「加密客户端问候等无法取得明文 SNI 的连接无法匹配」一句

更正后的表述要把「有 ECH 扩展」与「取不到明文 SNI」明确分开。

### 部署路径

修复后的分流器二进制随面板镜像的 Agent 资产一起分发。出口主机执行常规 Agent 升级、并让安装脚本优先从面板取资产时,即可拿到修复版本。**不需要手工替换二进制,也不需要改任何 SNI 分流规则。**

需要注意的是:安装脚本默认优先从公开发布渠道下载,那里的版本不含本次修复;必须让它优先使用面板自带资产,否则会装回旧版本。

## Testing Decisions

好的测试只验证外部可观察的行为:给定一个 ClientHello,连接是被转发到落地机还是被断开,以及落地机收到的握手字节是否与客户端发出的完全一致。不测解析函数的内部结构。

**只用一道缝:分流器的真实套接字测试。** 本次行为完全发生在分流器内部,面板不参与,没有第二道缝的必要。

要覆盖的行为:

- **带 ECH 扩展 + 明文 SNI 命中分流表 ⇒ 路由成功**,这是本次修复的核心断言
- **带 ECH 扩展时握手字节原样到达落地机**,逐字节比对,守住 REALITY 这类协议的前提
- **ECH 扩展位于扩展列表不同位置**时结果一致
- **多域名分流表下带 ECH 的握手匹配到正确规则**,确认放宽判定没有引入错配
- **完全无 SNI 的 ClientHello 仍被断开**,确认拒绝语义没有被削弱
- 非 TLS 流量、握手超窗、域名未命中三类拒绝**保持原样**

**必须改掉的既有断言**:现有「拒绝未匹配流量」的表驱动用例里,有一条 `ech extension` 把带 ECH 的握手当作应被拒绝来断言。它编码的正是本次要推翻的错误规则,必须从拒绝表里移出,改写为路由成功的用例。**如果只加新用例而不改它,测试会自相矛盾。**

**Prior art**:同一文件里已有多个真实套接字用例可直接沿用其套路——「握手原样转发」用例提供了字节比对的做法,「多域名分流并按规则统计流量」用例提供了多条分流表路由的搭建方式,「拒绝未匹配流量」用例提供了表驱动的拒绝断言结构。

## Out of Scope

- **解密 ECH、获取内层真实域名**。分流器不解密任何内容,这是 ADR-0001 的既定边界。
- **按内层域名分流**。
- **区分 GREASE ECH 与真 ECH 并分别处理**。上面已说明无法可靠区分。
- **丢弃连接的可观测性改进**。分流器丢弃连接时不记日志、不区分原因,这确实让本次排查付出了很大代价,但管理员明确要求本次只修 ECH 判定,可观测性另行处理。
- **面板侧的任何改动**,包括「未匹配连接数」的呈现方式。
- **QUIC / UDP 上的 SNI 分流**。
- **为未匹配连接提供回落目标**。ADR-0002 已明确否决。

## Further Notes

**这个缺陷是在真实环境中暴露的,且有两条独立证据。** 一是在真实链路上构造的对照 ClientHello——只差一个 ECH 扩展,一个被转发、一个被丢弃。二是管理员把客户端指纹从 `chrome` 换成 `ios` 后规则立刻可用,而 iOS/Safari 指纹不发送 GREASE ECH。两条证据指向同一个结论。

**排查代价远超修复代价。** 真正的修复只是判定条件去掉一个分支,但定位它花了很久,原因是三重静默:分流器丢弃连接不记日志;面板显示一切正常;用 `openssl` 手工验证会成功,因为 openssl 不发送 GREASE ECH。**能重现问题的唯一方式是用带 Chrome 指纹的客户端**,而这恰恰不是排查时最先想到的工具。这一点值得记住:验证 SNI 分流是否可用,手工 TLS 工具的成功不构成证据。

**规格的教训。** 「带 ECH 的连接按无 SNI 处理」这句话在写下时看起来是个保守、安全的决定,但它把一个**扩展的存在**当成了**信息不可得**的证据。这两者在 GREASE 广泛使用的今天已经完全脱钩。往后凡是基于「某个扩展存在」做拒绝判定的规则,都要先问一句:这个扩展的存在,是否真的意味着我要的信息拿不到?
