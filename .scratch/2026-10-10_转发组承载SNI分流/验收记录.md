## 实施结果

主机型转发组现在可以承载 SNI 规则。每个启用入口直接在保存的业务端口把完整域名送到对应落地机；主入口与备用入口提前取得相同规则，继续沿用原有整组主备调度。规则保存成功与机器真正准备好分别展示，旧目标、旧限制或历史运行标记不能代替最新配置确认。

例如 A、B 都准备 `a.example.com`、`b.example.com`，共用 `18443`。A 到服务甲断连而 B 能访问全部落地机时，经过原故障观察时间才把组入口切到 B。A 恢复后，是否切回取决于原有开关。修改或正常删除 a 的规则时，b 的长连接继续工作。

## 验收入口与环境

新增 [生命周期验收](../../server/sniForwardGroup.test.ts) 已纳入 `pnpm test:server`。它使用隔离 SQLite 数据库，通过现有规则与转发组管理接口、Agent 心跳、流量和连接检查报告入口验证业务结果。直接写数据库仅用于初始化样例、注入写入失败以及模拟迟到状态，不增加测试专用业务接口。

真实网络部分使用隔离 Linux 容器、临时 TLS 服务、真实 FXP 二进制和原 Agent 执行流程。[主备连接脚本](../../scripts/verify-sni-forward-group.mjs) 执行 A、B 的真实连接、正常撤除与撤除失败；[新增成员连接脚本](../../scripts/verify-sni-forward-group-member.mjs) 执行 C 的两个端口新增与停用。[Agent 集成检查](../../agent/sni_forward_group_integration_test.go) 读取面板真实导出的动作和检查任务。

容器中的入口监听 `127.0.0.1:18443`，C 另有 `18444`。使用预置验收镜像 `forwardx-sni-test:20261006`，并在容器内给予 `NET_ADMIN`，让 Agent 真正执行防火墙清理。未使用主机网络，不改生产 DNS；DDNS 成功、失败和响应期间并发保存均采用本地可控服务。

常规测试中的可选 Go 网络用例会跳过；上述真实网络命令已实际执行落地机检查、正常撤除、失败保护和新增／停用成员场景。

## 审查与失败路径修复

两名只读审查分别检查仓库规范和规格要求，基准为实施前提交 `eeee3fb66897059d86d68fbf86f4912118fdbdc4`。本轮修复后均已复查。

| 审查方向 | 最终结论 |
| --- | --- |
| Standards／仓库规范 | 0 项明文违规；1 项 P3 非阻塞维护建议：下发配置与就绪核对重复计算限制值，后续可共用生成函数。合法输入下两处结果一致 |
| Spec／规格要求 | 最终未发现明确规格缺口或阻塞问题；此前提出的三处失败路径已修复，新增成员真实连接发现的撤除遗漏也已补齐 |

修复均以可观察结果验证：

1. **撤除更新失败仍放行旧域名。** 让真实分流器拒绝更新，旧域名随即不可再连接，并清理运行配置和恢复文件。保护通过原 Agent 命令通道执行，最低版本保持 `2.2.195`，不要求先升级 Agent 生产代码。
2. **等待 DDNS 时另存新配置。** DDNS 返回前保存新的连接上限，旧的备用判断不会提交为当前入口；下次继续校对真实解析记录。
3. **新目标借用了旧健康记录。** 修改地址或端口后，旧测量保留作历史但失去健康资格，迟到的旧目标报告被拒绝，新目标取得自己的结果后才恢复健康。该严格匹配只用于主机型主备组，原转发链报告仍被接受。
4. **删除第一条规则遗留旧恢复文件。** 真实 Agent 执行正常撤除，保护只删危险旧文件，b 的持续连接仍能回显，不误停已经安全的分流表。
5. **停用新增成员仍有旧监听。** 原撤除退回普通转发工具，真实 C 连接验收先失败。改为按实际分流器撤除两个闲置端口；整个端口撤除不依赖某条代表规则，避免旧 Agent 的端口重分配保护误跳过。再次执行后两端口均拒绝业务连接，同批不再重复清理。

## 已确认的使用边界

- 切换仍受 DNS 缓存影响，已有连接不能迁移；断开的连接需要重连。
- 带宽和连接数按每台入口分别执行，多台入口同时服务时不是全组严格总上限；流量额度仍汇总实际用量。
- 正常域名变化只影响对应域名。撤除失败且旧表继续放行禁用域名时，会暂时停掉该入口的整个共享端口；其他已就绪入口继续按原组策略工作。
- 公共落地服务自身失效且所有入口都连接失败时，换入口不能恢复服务，状态按无健康成员处理。
- 本轮已验证本地代码、接口、真实容器网络及构建；生产机器部署和生产面板人工点选另行处理。
