# 转发组／入口组删减成员后释放主机：需求约定

> **实施授权更新（2026-10-16）：** 用户已明确要求“执行计划后，完成提交并发布新版”。以下“仅方案”属于前期边界；本轮已授权实施、检查、提交并向 `sni-panel` 发布，不包含直接修改生产数据库或删除 dmit6。

**日期：** 2026-10-16。

**状态：** 五项业务实现和最终审查已完成，面板 v3.3.8 已正式发布；最终服务端 1091/1091，四项正式流程、公开安装包、镜像和文档核对通过。正式证据见同目录 `发布记录.md`。没有执行生产处理或人工验收。

**用户要求：** “在转发组或入口组，删减了成员主机，就应该释放主机”。

## 一、要解决什么

从组里移除一台主机并保存后，这个组不能再因为旧的内部记录占着它。若没有其他真实用途，用户应该能正常删除该主机；不需要删除整个组或原有业务规则。

例如，入口组原来有 A、B，改成只保留 B：

- 组和它所生成的规则都应停止使用 A，并通知 A 清理旧配置。
- 原有业务规则继续存在，新入口沿用原来的规则编号、业务端口、目标和用量记录。
- 如果 A 还被另一条独立隧道或其他组使用，系统应继续保留那项真实引用，并提示仍有何种资源在使用。
- “从组中释放”不等于自动删除主机、注销 Agent、卸载服务或强行终止所有业务。

## 二、已确认的原因

主备转发组现场：dmit6 已从所有组的成员名单中移除，但 `v4x美国cn2` 的 44 条主规则仍保存 dmit6 的旧主机编号，删除检查因此返回 44 条引用。

入口组本地复现：入口组 30 从主机 4、5 改为只保留 5；引用它的转发链 40 已生成主机 1、2、5 的新路径，但主规则 400 仍保存 `hostId=4`，删除检查继续返回 1 条有效引用及 1 条待清理副本。

现有“修正主规则所属主机”的处理仅覆盖普通端口转发，遗漏主备转发组，以及入口组所影响的转发链。诊断原始记录保存在本地同目录的 `排查记录.md` 和 `远程只读证据.json`，未纳入公开提交；此处保留确认问题所需的数量和关系。

入口组引用的隧道还有独立的主入口设置。现有程序确实把 `tunnels.entryHostId` 当作独立入口使用；不能只因该主机从入口组移除就擅自更改这一设置。入口组产生的附加入口应释放，独立主入口、隧道中继、出口等真实用途仍受保护。

## 三、逐项要求

| 编号 | 要求 |
| --- | --- |
| R01 | 成员保存成功后，移除的主机不再被该组的主规则或有效成员副本占用；没有其他真实用途时允许正常删除。 |
| R02 | 覆盖普通规则和 SNI 规则、主机型和隧道型主备转发组，以及入口组影响的一条或多条转发链、入口组产生的隧道附加入口。 |
| R03 | 主规则编号、名称、归属用户、端口、目标、域名、限制、累计用量和计费关系全部保留；保留成员的有效规则继续存在。 |
| R04 | 旧成员副本沿用现有停用、待清理、用量处理和配置刷新过程；旧主机离线不应让逻辑引用无限期残留，实际清理是否完成单独记录。 |
| R05 | 归属修正按最新保存的成员配置决定，不等待健康检查、在线状态或 DNS 服务；组被禁用、成员全离线或全被禁用时仍可释放已经移除的成员。 |
| R06 | 没有成员移除、只修改名称、未改变归属或重复同步时，归属修正本身不得重复写入主规则或刷新其时间；已被移除的活动成员编号不得悬空。 |
| R07 | 保存失败时，相关成员、主规则归属和成员副本一起撤回；保存成功后再通知主机刷新，避免看到一半新、一半旧的配置。 |
| R08 | 历史遗留引用在正常组同步或删除检查时得到修正；数据库修正完成后才检查能否删除，不能通过删掉主规则或放松检查来消除报错。 |
| R09 | 仍被其他有效规则、组成员、独立隧道入口／中继／出口使用的主机继续受到保护；删除主机与删除其 Token 使用一致的判断。 |
| R10 | 入口组变更应刷新所有引用它的转发链和隧道；一条链处理失败，不能把入口组和其他受影响链的数据库配置留下部分成功。DNS 失败不能恢复旧成员关系或阻止已提交配置的清理通知。 |
| R11 | 主机释放不等于 DNS 或业务切换完成；保留既有健康判断、DNS 失败和全不健康时的处理政策，不伪造健康或切换成功。 |
| R12 | 沿用现有数据库字段、接口、依赖及 Agent 协议；本次修复不要求升级 Agent。 |

## 五、怎样算完成

实施阶段需要同时提供：实际保存接口的检查结果、删除接口的检查结果、规则和用量保留证据、配置撤除通知证据，以及与本次修复有关的现有检查结果。历史场景至少覆盖 1 条和现场同规模的 44 条规则。

本地检查通过、生产业务切换、用户人工验收分别记录。未运行的项目保持未完成；没有用户明确确认，不记录人工验收通过。

## 六、计划审查补充的验收细节

以下内容细化 R03、R07、R09、R10，现已纳入本轮实施与验证：

- **保存与历史修正分别验证。** 保存后先直接读取主规则和有效副本，再调用会自动修正历史数据的删除检查。不能靠删除检查替保存流程补好记录。
- **最后删除前再核对。** 不能在检查通过后先删权限或 Token，再发现主机重新被使用。失败时，待清理记录、主机权限、Token 绑定和在线标记一起恢复。
- **Token 查全受影响主机。** 同时检查 Token 记录里的主机编号，以及所有实际使用这枚 Token 的主机；其中任何一台仍在使用，就不执行删除和解绑。
- **局部编辑不能带回旧名单。** 与底层成员保存同时发生时，只修改名称也必须基于最新成员配置。新建引用链与入口组成员保存分别交换先后顺序检查。
- **失败撤回包含通知和运行状态。** 除了数据库记录恢复，还要证明没有提前发出撤除通知、没有提前清掉隧道状态。已提交后的单项刷新失败要如实提示，并继续尝试其他受影响资源。
- **计费与真实配置有独立证据。** 检查主规则对应账单、用量明细、余额；入口组引用链和隧道附加入口分别检查真实心跳配置。保留独立入口和其他实际用途。
- **额外保护继续保留。** Token 删除后的自动主机清理仍保留套餐绑定、其他 Token 等原有保护；孤立的组／隧道记录不能与现存关系混算。
- **数据库运行范围写清楚。** SQLite 检查不能代表 MySQL／PostgreSQL 已运行；真实跨库检查只使用专用空测试库，未运行的项目明确记录。

审查详情见 [计划审查记录](计划审查记录.md)。
