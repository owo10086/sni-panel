# 端口占用检测：面板必须知道主机上真实监听了什么

**Status:** ready-for-agent

## Problem Statement

管理员在面板上建转发规则时，源端口输入框会给出「✓ 可用」的判定。这个判定只查了面板自己的数据库——有没有别的转发规则或隧道占着这个端口——**从不问主机上真实监听了什么**。于是界面上写着「可用」，实际那个端口可能正被一个和 ForwardX 无关的进程占着。

后果按链路类型分成两种，都很难排查：

**内核转发（nftables / iptables）不 bind 端口。** 规则以 PREROUTING DNAT 的形式落到内核，数据包在到达本机 socket 之前就被改写了目的地址。原来监听该端口的进程还在跑、还在 listen，但一个包也收不到。两个系统都认为自己工作正常，**没有任何一方报错**。管理员要等到有人反馈「另一个服务不转发了」才会发现，而症状和原因隔得极远。

**用户态转发（gost / forwardx / nginx）必须 bind。** 受管运行时启动时会拿到 EADDRINUSE，规则起不来。但转发规则这条路径上没有对「地址已被占用」的识别，失败只表现为规则长期不生效、延迟探测超时，真正原因埋在 Agent 日志里。

讽刺的是，Agent 每次心跳都已经在采集主机的监听快照（用 `ss` 取，连占用进程名都有），只是它把这份数据留在本地用于判断规则是否就绪，从不上报给面板，面板也没有接口能在建规则前问一句。

## Solution

**「✓ 可用」必须成为对主机的判断，而不只是对数据库的判断。**

Agent 把它本来就在采集的端口占用情况随心跳带给面板。面板据此把端口校验的结论分成三档：

| 主机上的占用者 | 面板结论 |
| --- | --- |
| 无人占用 | 可用 |
| ForwardX 自己的受管运行时 | 可用——本来就是自己的 |
| **与 ForwardX 无关的进程** | **明确告知占用者是谁** |

第三档的处理按链路类型区分，因为两者的失败方式根本不同：

- **用户态链路**必定 bind 失败，直接拒绝创建，并在错误里点名占用进程。建一条注定起不来的规则没有意义。
- **内核转发**技术上能建，规则也会正常运行，但该端口的入站流量归属发生了变化。所以不拦截，而是显式警告并要求管理员确认——警告只陈述可核实的事实：「该端口上存在监听（绑定地址 / 协议 / 进程名），建立后入站流量将由本规则接管」。保留这条路是因为存在合法场景：对方只绑在 `127.0.0.1`、或绑在另一张网卡上，此时接管公网入站流量未必造成影响；面板无从判断，把决定权交给管理员。

**但创建时的这一次判断远远不够。** 端口占用是时变的：外部进程完全可能在规则建好之后才启动，而此时创建校验早已过去。所以本方案同时要求一条**持续占用检测**——面板拿每次心跳的快照与现有规则比对，占用出现或变化时在规则卡片上打出独立的警告标记。它同时覆盖**存量规则**，不需要任何人重建。

同时，受管运行时真的因为端口被占而起不来时，Agent 要把这个原因回报面板，让规则卡片直接显示「端口 443 已被 relay-node 占用」，而不是让人去翻日志。

**这三件事的失败形态不同，呈现方式也必须不同**：创建校验是**拦截或确认**，持续检测是**独立警告**（规则仍在正常运行），bind 失败回报才是**运行失败**。绝不能因为看到一条外部监听就把仍在工作的内核规则标成失败。

## User Stories

1. 作为管理员，我想在填写源端口时就知道这个端口在主机上是否真的空闲，从而不必等到规则建完才发现问题。
2. 作为管理员，我想在端口被外部进程占用时看到**占用者的进程名**，从而知道该去停哪个服务。
3. 作为管理员，我想让「可用」这两个字代表主机的真实状态，从而不再需要自己 SSH 上去 `ss -tlnp` 复核。
4. 作为管理员，我想在用户态链路上创建被占端口的规则时被直接拒绝，从而不会建出一条注定起不来的规则。
5. 作为管理员，我想在内核转发链路上遇到端口被占时收到警告而不是硬拦截，从而在对方只绑回环地址这类合法场景下仍能继续。
6. 作为管理员，我想让那条警告写清「该端口存在监听、建立后入站流量将由本规则接管」并附上绑定地址，从而在不被替我下结论的前提下自己判断后果。
7. 作为管理员，我想在确认警告后规则能正常建立，从而不被一个我已经想清楚的判断反复阻挡。
8. 作为管理员，我想知道这份占用信息是多久以前采集的，从而在它明显过期时自己判断可信度。
9. 作为管理员，我想在 Agent 离线、拿不到占用信息时得到明确提示，从而不把「没有警告」误解成「端口空闲」。
10. 作为管理员，我想让端口被 ForwardX 自己的受管运行时占用时仍判定为可用，从而不会被自己的进程挡住。
11. 作为管理员，我想让同一入口端口上的多条 SNI 分流规则继续正常创建，从而不因为这个新检查破坏共用端口的能力。
12. 作为管理员，我想让分流器占用的出口端口不被误判为外部占用，从而不会在扩容分流规则时被拦下。
13. 作为管理员，我想让隧道监听端口被自己的受管运行时占用时不触发警告，从而隧道的正常复用不受影响。
14. 作为管理员，我想在规则因端口被占而起不来时，从规则卡片上直接看到原因，从而不必去服务器翻 Agent 日志。
15. 作为管理员，我想让这个原因里也带上占用进程名，从而一眼定位到要处理的对象。
16. 作为管理员，我想在占用进程消失后规则能自动恢复运行，从而不需要手动重建规则。
17. 作为管理员，我想在内核转发遇到只绑 `127.0.0.1` 的进程时收到告知了绑定地址的警告、确认后仍能建立规则，从而既不被本机自用服务挡住、也不会对它的存在一无所知。
18. 作为管理员，我想让绑在某张具体网卡上的进程被正确判断，从而多网卡机器上的端口复用不被误报。
19. 作为管理员，我想让 IPv6 与 IPv4 分别监听的情况被正确识别，从而双栈主机上的判断不出错。

24. 作为管理员，我想让启用一条此前停用的规则时也走同样的检查，从而停用期间被别人占走的端口能被发现。
25. 作为管理员，我想让修改规则源端口时也走同样的检查，从而改端口和建端口的安全性一致。

29. 作为普通用户，我想在自己无权查看主机细节时仍得到「端口不可用」的结论，从而不因权限差异拿到误导性的「可用」。
30. 作为普通用户，我不想看到主机上其它进程的名字，从而不越权获知与我无关的主机信息。
31. 作为管理员，我想让这项检查在主机首次接入、还没上报过占用信息时降级为原有行为，从而新主机不会被卡住。
32. 作为管理员，我想让降级时界面说清楚「尚未取得主机端口信息」，从而知道当前判断的依据是什么。
33. 作为管理员，我想让占用检测的结论在规则创建和端口输入框两处完全一致，从而不出现「输入框说可用、提交说占用」的矛盾。
34. 作为管理员，我想让确认过的警告不在每次编辑规则时重复弹出，从而不被已经决策过的事情反复打断。
35. 作为运维，我想让整套判断在 Agent 版本较老、不上报占用信息时静默降级，从而升级节奏不被强制绑定。
36. 作为管理员，我想在规则建好之后才出现的端口占用也被发现，从而不必假设创建那一刻的判断永远成立。
37. 作为管理员，我想让这项持续检测同样覆盖此前已经建好的规则，从而不需要为了得到保护而重建它们。
38. 作为管理员，我想让内核转发规则在被外部监听占用时仍显示为运行中、同时带一个独立的占用警告，从而不把一条正常工作的规则误读成故障。
39. 作为管理员，我想让这个占用警告不被绿色的运行状态或一次成功的延迟探测掩盖，从而不会因为卡片是绿的就忽略它。
40. 作为管理员，我想只在占用出现或占用者发生变化时收到提醒，从而不会为同一个一直存在的占用被反复打扰。
41. 作为管理员，我想在占用消失后收到一条解除提醒，从而知道这件事已经可以收工。

## Implementation Decisions

### 端口占用快照由 Agent 随心跳上报

Agent 已经在构建主机监听快照（`ss -H -ltnup`，带进程名，有缓存）。本方案**复用这份既有数据**，不新增采集动作：把它整理成一份**端口占用快照**，随心跳的本地运行时状态一起上报。

每个条目至少包含：端口、协议、绑定地址、占用进程名。**绑定地址必须带上**——只绑 `127.0.0.1` 的进程和绑 `0.0.0.0` 的进程对入站规则的影响完全不同，丢掉这个信息就只能一刀切误报。

快照的体积要有上限。一台主机可能监听几百个端口，上报应只包含**必要信息**，不夹带完整 `ss` 输出行。

**上限一旦生效，就必须能区分「这个端口没人监听」和「这个端口不在快照里」。** 否则截断会悄悄把被裁掉的端口全部呈现为空闲——一个比没有检查更糟的结果，因为它带着「已核实」的语气。快照要能表达自身是否完整；不完整时，落在截断范围外的端口按**未经核实**处理，走降级路径，而不是按空闲处理。

截断策略上，被裁掉的应当是**最不可能被问到的**那些条目，而不是任意截断。

**快照必须是心跳里的独立字段，并有自己的签名。** 现有的本地运行时状态是按**整包内容**算一个签名、只在变化时才整包上传的。如果把快照并进同一个包，主机上任何一个与 ForwardX 无关的服务起停都会翻转整包签名，触发规则状态的整包重传——为一个校验功能付出与它无关的心跳开销。

拆签名之后**强制上报通道也要跟着拆**。现有的「请求上报本地运行时状态」做了两件事：置上传标志、失效采集缓存。一旦快照有了自己的签名，就必须明确**谁来触发快照的上报**，否则会出现「占用变了、但因为规则状态没变所以不上报」——这恰好是本方案要防的那个洞。

**但「只在变化时重传」和「用采集时间判断过期」放在一起会产生一个洞。** 如果主机的监听几小时没变化，快照就几小时不重传，面板保存的采集时间也就跟着一起变老——哪怕 Agent 每次心跳都在成功采集。到头来面板会把一份**每分钟都在被重新核实**的数据判定为过期，然后降级。这是本方案里最容易被忽略的自伤。

所以心跳要**始终携带两样轻量的东西**：本次快照的签名，以及本次采集是否成功。完整快照只在两种情况下传——内容变化，或面板明说自己没有缓存。面板据此更新**最近核实时间**，而更新的前提是**本次采集成功且签名与缓存一致**：

- 采集成功 + 签名一致 ⇒ 刷新最近核实时间，缓存内容不变。
- 采集成功 + 签名不一致 ⇒ 面板缓存已过时，要求补传完整快照。
- **采集失败 ⇒ 什么都不刷新。** 心跳到达本身不构成核实，否则一台 `ss` 已经坏掉的主机会靠心跳把一份陈年快照永久保鲜。

「最近核实时间」和「采集时刻」是两个不同的东西：前者回答「这份判断还新鲜吗」，后者回答「这份内容是什么时候取的」。降级判断用前者。

### 面板侧缓存与陈旧度

面板按主机缓存这份快照，沿用现有的有界缓存约定（注意：在遍历缓存的同时写入，必须使用不改变键位置的那个写入函数）。每份缓存记录两个时间：**采集时刻**（这份内容取自何时）与**最近核实时间**（这份判断上次被确认仍然成立是何时），按上一节的规则分别更新。

**Agent 未上报过快照时**（老版本 Agent、主机刚接入、Agent 离线），端口校验降级为现有的「只查数据库」行为，并在结论里标明依据不足，绝不把「没有占用信息」呈现为「端口空闲」。

**陈旧度算的是最近核实时间，不是采集时刻**，否则一份长期没有变化、但每分钟都在被成功核实的快照会被误判为过期。

**时间基准要沿用仓库既有约定，不要新造。** 两个时间都来自 Agent 本机时钟，判断陈旧的是面板，跨机时钟偏移会直接决定降级行为对不对。仓库里已经有一套成熟做法：一个「新鲜期」加一个「未来偏移容忍值」，链路探测与隧道规则延迟都用它。快照照搬即可，并明确一点：**时间戳落在未来且超过容忍值时按不可信处理**，否则时钟快的主机会永远显示「刚刚核实」，降级永远不触发。

### 占用者归类：受管 vs 外部

判定的核心是把占用者分成两类：

- **受管占用**：占用者是 ForwardX 自己安装并托管的受管运行时（Agent 本身、分流器、各类转发运行时）。
- **外部占用**：其它一切进程。

**「受管」是占用者的身份，不是端口可用的充分条件。** 这两件事必须分开：一个端口被 ForwardX 自己的另一个运行时占着，新规则照样绑不上去——内核给的还是 EADDRINUSE，不会因为两个进程都姓 ForwardX 就网开一面。

真正让端口可用的条件只有一个：**新规则要用的，确实就是那个已经存在的监听本身**（同一入口端口上的多条 SNI 分流规则共用分流器的同一个监听，就是这种情况）。凡是达不到这个条件的受管占用，一律按绑定冲突处理。进程名相同、甚至运行时类型相同，都不足以证明监听可复用。

归类只看进程名是不够的，进程名相同不足以证明那个监听可以复用——必须确认它**确实就是**本规则要用的那个受管监听。

**归类只陈述客观事实，不下「算不算冲突」的结论。** 它回答的是：这个端口上有谁在监听、绑在哪个地址、什么协议、是不是我们自己的受管运行时。至于「这算不算冲突」，交给按 `forwardType` 分流的那一层去判断。

这条分工是有原因的。同一个绑定地址，对两种执行方式的含义完全相反：一个只绑 `127.0.0.1` 的进程，对用户态转发是**硬冲突**（受管运行时要绑 `0.0.0.0`，内核会直接给 EADDRINUSE），对内核转发则是**另一回事**（DNAT 不 bind，两者能共存，但该端口的入站流量归属发生了变化）。如果让归类层自己判断「回环占用不影响入站」，同一个函数就要对两种执行方式给出相反答案——这是整个实现里最容易搞错的地方。让它只报事实，冲突判断单点收敛，才不会两头打架。

### 校验结论的形状

现有端口校验返回 `{ used, reason }`。新增的是**警告**，它和 `used` 是不同的东西——警告不等于不可用，**绝不能把警告塞进 `used`**，否则界面会把可以继续的情况显示成不可用。

结论扩展为三种状态：可用 / 警告（附占用者与后果说明）/ 不可用（附原因）。警告态还需携带占用者信息和采集时刻，供界面呈现。

**创建校验与持续检测必须调用同一套占用判定**，否则两个位置会对同一个端口给出不同结论。这里有个容易实现成两份的陷阱：现有的端口校验走的是一个**纯数据库查询**，持续检测根本不会经过那条路径。所以「共用」只能落在**新增的这一层**上——一个只依赖 `(快照, 主机, 端口, 协议, forwardType, 受管端口集合)` 的判定，不碰请求上下文、不碰数据库连接。指望把它塞进现有的数据库查询里复用，最后一定会变成两份实现。

### 拦截策略按 forwardType 分流

**注意 `forwardType` 是转发规则的执行方式标签，不等于传输协议**（见 `CONTEXT.md`）。策略按运行时是否需要 bind 端口来分：

- **需要 bind 的执行方式**（gost、forwardx、nginx 系）：外部占用 ⇒ **不可用**，拒绝创建，错误信息点名占用进程。
- **内核转发**（nftables、iptables）：外部占用 ⇒ **警告**，需要调用方显式确认后才放行。确认以一个显式入参表达，默认不确认。

**内核转发下即使对方只绑回环地址，也要警告。** 保留「确认后放行」这条路不是因为回环占用无害，而是因为面板**没有能力断言它有害还是无害**：DNAT 只装在 `PREROUTING`，本机自己发起的连接走 `OUTPUT`、不受影响，所以那个进程的流量会怎样，取决于它的客户端从哪来——面板不知道。

这决定了警告的**措辞边界**：只陈述可核实的事实（这个端口上存在监听、绑在哪个地址、什么协议、管理员可见进程名），并说明该端口的入站流量归属会发生变化。**不要断言「原监听进程将收不到数据」**——对一个只绑 `127.0.0.1`、只服务本机客户端的进程来说，这句话是错的。把判断权交给看得见上下文的管理员，比替他下一个可能错的结论更有用。

### 必须不破坏共用端口的既有能力

ADR-0002 放开了 SNI 分流规则的源端口唯一性——同一入口端口上可以并存多条 SNI 分流规则。这些规则在主机上表现为**同一个受管运行时的同一个监听**，属于受管占用，必须继续判定为可用。**这是本方案最容易踩坏的地方**：一旦把自己的分流器监听误判成外部占用，第二条起的 SNI 分流规则就全建不出来。

同理，隧道监听端口、分流器出口端口被自己的受管运行时占用，都不得触发警告。

### 持续占用检测：警告是独立标记，不是运行状态

创建校验只保护「新建那一刻」。规则建好之后外部进程才启动，是同样常见、且创建校验完全无能为力的情形。因此面板要用每次心跳的快照与**现有启用中的规则**比对，发现不可复用的外部监听时给出警告。这条路径的附带收益是它**天然覆盖存量规则**——不需要任何人重建。

**警告必须是一个独立的标记，不能翻译成运行状态。** 具体说：不得仅凭一条监听记录就把 `isRunning` 置假、或把规则标成运行失败。内核转发规则在这种情况下**确实还在正常运行**，DNAT 规则好端端地待在内核里，转发也在进行。把它标成失败是在报告一件没有发生的事。

这一点不只是偏好，现有类型已经替我们做了决定：规则卡片的视觉状态是一个**单值枚举**（停用 / 运行中 / 等待中 / 错误），没有位置表达「运行中 + 有警告」。更关键的是，状态解析函数在**探测新鲜且可达时会提前返回「运行中」**，根本走不到后面的分支——也就是说，如果把警告塞进同一个返回值，它在「绿色、延迟 1ms」这个恰恰最需要它的场景里是**不可达代码**。所以警告必须走另一条通道，与状态并列呈现。

**实现落点有现成样板**：SNI 分流规则的运行时状态就是从内存缓存**派生式地**挂在规则行上的——不加数据库列、不写迁移、快照一变结论自动跟着变、占用消失警告自动消失。端口占用警告照此办理。它外层的权限装饰已经按管理员 / 普通用户分支，进程名的脱敏直接落在那条缝上，不必新开。

### Telegram 提醒：需要新的触发点，不能复用现有条件

发送能力可以复用，**触发条件不能**。现有的规则错误提醒挂在「运行状态由真变假」这个边沿上，而仍在工作的内核转发规则 `isRunning` 一直是真——这个条件永远不会命中。

触发点挂在上一节说的**变化检测**上（收到有效快照时、规则集变动后），不挂在规则列表的读取上。

新的触发点按**状态变化**驱动，需要定清四件事：

- **状态键必须包含占用者身份**，不只是「有没有占用」：规则 + 入口主机 + 端口 + 协议 + 进程名 + 绑定地址。占用者从 A 换成 B 也必须算一次变化，否则让位会被静默吞掉。
- **必须有恢复边**。占用消失时要发一条解除提醒，否则管理员永远不知道这件事可以收工。注意这与「受管运行时恢复运行」不是一回事——内核转发规则压根没有停过。
- **「未经核实」不是「占用已解除」。** 快照缺失、采集失败、过期、被截断——这些情况下面板**不知道**占用还在不在，绝不能据此发出解除提醒。Agent 一掉线就收到一批「占用已解除」的好消息，是这套提醒最糟糕的失败方式：它把一个观测中断说成了一个问题被解决。解除提醒只能由**一份明确显示占用已经不在的有效快照**触发。
- **状态记在内存则面板重启会重发一次**。可以接受，但要写明，否则会被当成缺陷报回来。
- **现有的冷却窗口要保留，而不是被替换**。变化触发负责「该不该发」，冷却负责「占用者反复起停时别刷屏」，两层各司其职。

消息内容要与「运行异常」明确区分：这是一条**警告**，不是故障通知，措辞上不得暗示规则已经停止工作。提醒沿用规则上既有的那个开关，不新增开关。

### 运行时 bind 失败要回报原因

受管运行时因端口被占而启动失败时，Agent 要识别出「地址已被占用」这一类错误，并作为规则级错误回报面板，使规则卡片能直接显示占用者。目前代码里只有 iperf3 诊断工具做了这个识别，转发规则路径上没有。

占用消失后，规则应在后续心跳中自动恢复运行，不需要人工重建。

**这一节只覆盖用户态执行方式。** 内核转发没有 bind 这个动作，也就没有 bind 失败，它的占用问题完全由上一节的持续检测负责。两者在卡片上的呈现也不同：bind 失败是**运行失败**（规则确实没在工作），持续占用是**独立警告**（规则仍在工作）。不要试图用同一个字段表达。

### 权限边界

占用进程名属于主机信息。普通用户能得到「端口不可用」「该端口存在占用」的结论，但**不应看到进程名**；管理员才看到完整信息。

**脱敏必须发生在服务端构造返回值的那一刻，不能依赖任何形式的事后删除或页面隐藏。** 现有的规则权限装饰是**只加不减**的：非管理员分支把原规则整个展开、再补一个授权结果字段，没有任何白名单或字段剔除。这意味着上游一旦把带进程名的占用信息挂到规则上，它会原样流到普通用户手里，而页面隐藏拦不住 API 响应。

同一处还有第二个坑：那个非管理员分支**完全跳过了派生信息的挂载**。照搬这个结构会得到一个相反的错误——普通用户一条占用警告都收不到，而规格要求他们仍然应当知道「这个端口有占用」。

所以正确的做法是**按角色分别构造**警告内容：管理员那份含进程名，普通用户那份从一开始就不含，两份都要有。不是先构造一份完整的再想办法删干净。

### 覆盖面

这项检查要覆盖所有产生端口占用判断的入口：端口输入框的实时校验、规则创建、规则更新、规则启用、批量导入、随机端口分配。批量导入的冲突要能精确到行号。随机端口分配要主动避开主机上已被占用的端口。

除了这些**表单入口**，持续检测还有两个各司其职的位置，**不能混为一谈**：

- **变化检测**发生在面板**收到一份有效快照**的时候（心跳路径），另外在规则创建、启用、修改之后也要重算一次——因为规则集变了，同一份快照的结论也就变了。它负责发现占用的出现、变更与消失，并驱动提醒。
- **规则列表的读取路径**只负责**展示**已经算出来的结论。

这个分工是必须的：**没有人打开规则列表的时候，占用照样要被发现、提醒照样要发出去**。把变化检测挂在列表读取上，等于让告警的有无取决于有没有人正在看页面——服务器上那个占用可能已经存在了一整夜。

两个位置用的必须是同一套占用判定（见「校验结论的形状」）。

## Testing Decisions

好的测试只验证外部可观察的行为：给定的输入下，管理员看到什么结论、规则能不能建出来、期望状态里有没有那条规则。不测内部函数怎么拆、缓存长什么样。

四道缝，全部沿用现有缝，不新增：

### 缝一：tRPC 规则路由（用户看到的判定）

覆盖端口校验与规则创建/更新/启用的最终结论，以及规则列表里的持续占用警告。这是本功能绝大多数用户可见的输出：受管占用判定为可用、外部占用在用户态链路被拒、内核转发得到警告、确认后放行、同端口多条 SNI 分流规则不受影响、普通用户看不到进程名、无快照时降级。

持续检测的行为也在这道缝上验证，其中有两条必须显式断言，因为它们正是最容易被实现错的地方：

- 内核转发规则在入口端口存在外部监听时，**运行状态保持为运行中**，同时规则行上带出占用警告——断言「运行状态没有被改成失败」和「警告确实出现了」这两件事，缺一不可。
- 探测新鲜且可达（卡片会显示绿色低延迟）时，警告**依然出现**。这条用例防的是把警告塞进单值状态枚举后被提前返回吞掉。

**Prior art**：`server/rulesPortAvailability.test.ts`——以真实数据库跑 tRPC 路由的 spawnSync 子进程测试，已覆盖转发组端口校验与套餐端口范围。新用例照此扩展。

### 缝二：心跳（占用数据的上报与消费）

覆盖 Agent 上报的端口占用快照被面板正确接收、缓存、并在后续判定中生效，以及快照缺失时的降级。另外要断言：只有快照变化时才重新上报快照，**规则状态未变化时监听变化仍能更新面板缓存**——这是独立字段独立签名的外部可观察表现。陈旧与未来时间戳的降级行为也在这里验证。

**Prior art**：`server/sniDesiredState.test.ts`——起真实 express + 心跳路由，POST 心跳并断言返回的期望状态。同一套路可以断言「上报占用后再查端口，结论改变」。

### 缝三：Agent Go（采集与归类）

覆盖监听快照被正确整理成上报结构：绑定地址保留、进程名保留、TCP/UDP 分开、IPv6 与 IPv4 分别识别、体积有上限、采集时刻带上。以及受管运行时 bind 失败时「地址已被占用」被识别为规则级错误。

签名拆分也在这里验证：**只有监听发生变化时快照签名才翻转，规则状态变化不影响它**，反之亦然。

**Prior art**：`agent/fxp_spec_test.go`——以构造的运行时状态驱动 `readLocalRuntimeStatePayload` 并断言上报内容。

### 缝四：规则错误提醒的触发判定（提醒发不发、发几次）

覆盖变化触发的四条语义：同一占用持续存在只发一次、占用者换人算一次新变化、占用消失发出解除提醒、冷却窗口仍在最外层生效。

**Prior art**：`server/forwardRuleErrorNotifier.test.ts`——纯函数地驱动提醒判定并断言真假，不发真实消息。新的变化触发判定照此扩展。

### 明确不为此单开缝

占用者归类（受管 vs 外部）是纯逻辑，但它**没有独立的用户可见行为**，其正确性完全体现在缝一的结论上。因此不为它单开纯函数缝，除非归类规则在实现中复杂到光靠缝一定位不了问题——那时再拆，并在 spec 上补记。

## Out of Scope

- **提交时向 Agent 实时探测端口**。心跳快照最多陈旧一个心跳周期，对本问题已经够用。实时探测需要新的往返、Agent 在线依赖和降级策略，留待确有需要时再评估。
- **自动停止占用端口的外部进程**。面板不代管不属于它的进程。
- **自动推荐替代端口**。现有随机端口分配避开已占用端口即可，不做「猜你想用哪个」。
- **把主机上所有监听端口做成一个可浏览的页面**。本方案只在端口判定这一个场景用这份数据。
- **历史占用记录与趋势**。只保留最近一次快照。
- **非 Linux 主机**。占用采集依赖 `ss`。
- **容器内端口占用的穿透判断**。Agent 看到的是宿主机视角。
- **为端口占用警告单独设一个提醒开关**。沿用规则上既有的那个开关，不增加配置面。
- **凭占用信息自动停用或修改已有规则**。持续检测只告知，不代替管理员做处置决定。

## Further Notes

**这个缺陷是在真实环境中暴露的。** 韩国入口主机的 443 端口被另一套系统的节点进程占着，面板照样显示「✓ 可用」并成功建出规则；实际落地的是一条 PREROUTING DNAT，把 443 的入站流量整个接管了，而原进程仍在监听、毫无察觉。两个系统同时「正常工作」的假象，比任何一方报错都更难发现。

**术语缺口。** `CONTEXT.md` 目前没有描述「主机上某个端口被谁占着」这件事的词。本规格用了**端口占用快照**（Agent 采集、随心跳上报的派生数据，不是用户创建的资源）、**受管占用**、**外部占用**与**端口占用警告**（规则卡片上与运行状态并列的独立标记，出现时规则仍在运行）。这四个词在实现落地时应补进 `CONTEXT.md` 的词汇表；**受管占用**可以直接挂在既有的**受管运行时**词条下。

**一处已裁决的内部矛盾，记录在此以免回退。** 本规格早先一版在「占用者归类」里写过「绑在回环地址的占用不影响公网入站规则」，而创建校验工单（现编号 03）要求回环占用在内核转发下也必须警告——两处会导出相反的产品行为。现已裁决为**后者**：归类层只陈述事实，冲突判断交给按 `forwardType` 分流的那一层；内核转发遇到回环占用照样警告，但措辞不得断言原进程会失去流量。裁决理由见「拦截策略按 forwardType 分流」。这个矛盾是在一个真实案例上暴露的：一台入口主机的某端口被 `127.0.0.1` 上的编辑器进程占着，按旧措辞面板会完全沉默，管理员对「这个端口在本机另有归属」一无所知。

**与 ADR 的关系。** 本规格不与 ADR-0001、ADR-0002 冲突，但 ADR-0002 放开的「SNI 分流规则共用入口端口」是最容易被这项检查误伤的能力，实现时必须有针对性的回归用例，而不是等人工发现。

**一个容易忽略的收益。** 受管运行时 bind 失败的原因回报（本规格的最后一项）单独看是个小改动，但它把一类「规则显示已生效、实际不通」的问题从「翻日志」降级成「看卡片」。这类问题的排查成本远高于它的实现成本。

**工单顺序是一个刻意的决定，不是任意编号。** 数据地基（01）之后先做**持续检测**（02），再做**创建表单的警告与确认**（03）。理由是持续检测覆盖存量规则、不依赖任何人重建、工作量也小得多；而创建校验要贯穿六个表单入口、要给校验结论加第三态和确认入参，成本高出一个数量级。先做 02，服务器上已经存在的占用当天就能被看见；先做 03，则只有此后新建的规则受保护，存量规则继续沉默。

**这也意味着 02 不能等 03。** 如果实现时发现两者有共享代码想合并推进，要合并的是**判定层**（那本来就在 01 里），而不是把警告的呈现推迟到创建表单做完。
