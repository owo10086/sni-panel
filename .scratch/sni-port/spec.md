# 端口占用检测：面板必须知道主机上真实监听了什么

**Status:** ready-for-agent

## Problem Statement

管理员在面板上建转发规则时，源端口输入框会给出「✓ 可用」的判定。这个判定只查了面板自己的数据库——有没有别的转发规则或隧道占着这个端口——**从不问主机上真实监听了什么**。于是界面上写着「可用」，实际那个端口可能正被一个和 ForwardX 无关的进程占着。

后果按链路类型分成两种，都很难排查：

**内核转发（nftables / iptables）不 bind 端口。** 规则以 PREROUTING DNAT 的形式落到内核，数据包在到达本机 socket 之前就被改写了目的地址。原来监听该端口的进程还在跑、还在 listen，但一个包也收不到。两个系统都认为自己工作正常，**没有任何一方报错**。管理员要等到有人反馈「另一个服务不转发了」才会发现，而症状和原因隔得极远。

**用户态转发（gost / forwardx / nginx）必须 bind。** 受管运行时启动时会拿到 EADDRINUSE，规则起不来。但转发规则这条路径上没有对「地址已被占用」的识别，失败只表现为规则长期不生效、延迟探测超时，真正原因埋在 Agent 日志里。

讽刺的是，Agent 每次心跳都已经在采集主机的监听快照（用 `ss` 取，连占用进程名都有），只是它把这份数据留在本地用于判断规则是否就绪，从不上报给面板，面板也没有接口能在建规则前问一句。

## Solution

**「✓ 可用」必须成为对主机的判断，而不只是对数据库的判断。**

Agent 把它本来就在采集的端口占用情况随心跳带给面板。面板据此把端口校验的结论分成三档：

| 主机上的占用者 | 面板结论 |
| --- | --- |
| 无人占用 | 可用 |
| ForwardX 自己的受管运行时 | 可用——本来就是自己的 |
| **与 ForwardX 无关的进程** | **明确告知占用者是谁** |

第三档的处理按链路类型区分，因为两者的失败方式根本不同：

- **用户态链路**必定 bind 失败，直接拒绝创建，并在错误里点名占用进程。建一条注定起不来的规则没有意义。
- **内核转发**技术上能建，但会静默接管该端口的入站流量。所以不拦截，而是显式警告并要求管理员确认——警告里把后果说清楚：「建立后将接管该端口的入站流量，原监听进程 XXX 将收不到数据」。保留这条路是因为存在合法场景：对方只绑在 `127.0.0.1`、或绑在另一张网卡上，此时接管公网入站流量并不冲突。

同时，受管运行时真的因为端口被占而起不来时，Agent 要把这个原因回报面板，让规则卡片直接显示「端口 443 已被 relay-node 占用」，而不是让人去翻日志。

## User Stories

1. 作为管理员，我想在填写源端口时就知道这个端口在主机上是否真的空闲，从而不必等到规则建完才发现问题。
2. 作为管理员，我想在端口被外部进程占用时看到**占用者的进程名**，从而知道该去停哪个服务。
3. 作为管理员，我想让「可用」这两个字代表主机的真实状态，从而不再需要自己 SSH 上去 `ss -tlnp` 复核。
4. 作为管理员，我想在用户态链路上创建被占端口的规则时被直接拒绝，从而不会建出一条注定起不来的规则。
5. 作为管理员，我想在内核转发链路上遇到端口被占时收到警告而不是硬拦截，从而在对方只绑回环地址这类合法场景下仍能继续。
6. 作为管理员，我想让那条警告明确写出「原监听进程将收不到数据」，从而理解我确认的到底是什么后果。
7. 作为管理员，我想在确认警告后规则能正常建立，从而不被一个我已经想清楚的判断反复阻挡。
8. 作为管理员，我想知道这份占用信息是多久以前采集的，从而在它明显过期时自己判断可信度。
9. 作为管理员，我想在 Agent 离线、拿不到占用信息时得到明确提示，从而不把「没有警告」误解成「端口空闲」。
10. 作为管理员，我想让端口被 ForwardX 自己的受管运行时占用时仍判定为可用，从而不会被自己的进程挡住。
11. 作为管理员，我想让同一入口端口上的多条 SNI 分流规则继续正常创建，从而不因为这个新检查破坏共用端口的能力。
12. 作为管理员，我想让分流器占用的出口端口不被误判为外部占用，从而不会在扩容分流规则时被拦下。
13. 作为管理员，我想让隧道监听端口被自己的受管运行时占用时不触发警告，从而隧道的正常复用不受影响。
14. 作为管理员，我想在规则因端口被占而起不来时，从规则卡片上直接看到原因，从而不必去服务器翻 Agent 日志。
15. 作为管理员，我想让这个原因里也带上占用进程名，从而一眼定位到要处理的对象。
16. 作为管理员，我想在占用进程消失后规则能自动恢复运行，从而不需要手动重建规则。
17. 作为管理员，我想让只绑在 `127.0.0.1` 的进程不阻止我建公网入站规则，从而本机自用服务不会误伤业务配置。
18. 作为管理员，我想让绑在某张具体网卡上的进程被正确判断，从而多网卡机器上的端口复用不被误报。
19. 作为管理员，我想让 IPv6 与 IPv4 分别监听的情况被正确识别，从而双栈主机上的判断不出错。
20. 作为管理员，我想让 TCP 和 UDP 的占用分开判断，从而一个协议的占用不会挡住另一个协议的规则。
21. 作为管理员，我想在批量导入规则时同样得到端口占用的判断，从而不会一次性建出一批起不来的规则。
22. 作为管理员，我想让批量导入时的占用冲突精确到行号，从而能直接定位到要改的那一行。
23. 作为管理员，我想让随机端口分配自动避开主机上已被占用的端口，从而系统分配的端口一次就能用。
24. 作为管理员，我想让启用一条此前停用的规则时也走同样的检查，从而停用期间被别人占走的端口能被发现。
25. 作为管理员，我想让修改规则源端口时也走同样的检查，从而改端口和建端口的安全性一致。
26. 作为管理员，我想让这项检查不显著拖慢端口输入框的响应，从而填表体验不退步。
27. 作为管理员，我想让占用信息的采集不明显增加 Agent 的负担，从而不为一个校验功能付出运行时代价。
28. 作为管理员，我想让占用信息随心跳自然更新，从而不需要手动刷新就能看到最新状态。
29. 作为普通用户，我想在自己无权查看主机细节时仍得到「端口不可用」的结论，从而不因权限差异拿到误导性的「可用」。
30. 作为普通用户，我不想看到主机上其它进程的名字，从而不越权获知与我无关的主机信息。
31. 作为管理员，我想让这项检查在主机首次接入、还没上报过占用信息时降级为原有行为，从而新主机不会被卡住。
32. 作为管理员，我想让降级时界面说清楚「尚未取得主机端口信息」，从而知道当前判断的依据是什么。
33. 作为管理员，我想让占用检测的结论在规则创建和端口输入框两处完全一致，从而不出现「输入框说可用、提交说占用」的矛盾。
34. 作为管理员，我想让确认过的警告不在每次编辑规则时重复弹出，从而不被已经决策过的事情反复打断。
35. 作为运维，我想让整套判断在 Agent 版本较老、不上报占用信息时静默降级，从而升级节奏不被强制绑定。

## Implementation Decisions

### 端口占用快照由 Agent 随心跳上报

Agent 已经在构建主机监听快照（`ss -H -ltnup`，带进程名，有缓存）。本方案**复用这份既有数据**，不新增采集动作：把它整理成一份**端口占用快照**，随心跳的本地运行时状态一起上报。

每个条目至少包含：端口、协议、绑定地址、占用进程名。**绑定地址必须带上**——只绑 `127.0.0.1` 的进程和绑 `0.0.0.0` 的进程对入站规则的影响完全不同，丢掉这个信息就只能一刀切误报。

快照的体积要有上限。一台主机可能监听几百个端口，上报应只包含**必要信息**，不夹带完整 `ss` 输出行。

### 面板侧缓存与陈旧度

面板按主机缓存这份快照，沿用现有的有界缓存约定（注意：在遍历缓存的同时写入，必须使用不改变键位置的那个写入函数）。每份快照记录采集时刻，供界面标注陈旧度。

**Agent 未上报过快照时**（老版本 Agent、主机刚接入、Agent 离线），端口校验降级为现有的「只查数据库」行为，并在结论里标明依据不足，绝不把「没有占用信息」呈现为「端口空闲」。

### 占用者归类：受管 vs 外部

判定的核心是把占用者分成两类：

- **受管占用**：占用者是 ForwardX 自己安装并托管的受管运行时（Agent 本身、分流器、各类转发运行时）。这类占用等同于「没被占用」，因为它本就是面板期望状态的一部分。
- **外部占用**：其它一切进程。

归类只看进程名是不够的，还要结合绑定地址判断「这个占用是否会影响本规则要接收的流量」：绑在回环地址的占用不影响公网入站规则；绑在具体网卡地址的占用只影响该地址上的流量。

### 校验结论的形状

现有端口校验返回 `{ used, reason }`。新增的是**警告**，它和 `used` 是不同的东西——警告不等于不可用，**绝不能把警告塞进 `used`**，否则界面会把可以继续的情况显示成不可用。

结论扩展为三种状态：可用 / 警告（附占用者与后果说明）/ 不可用（附原因）。警告态还需携带占用者信息和采集时刻，供界面呈现。

### 拦截策略按 forwardType 分流

**注意 `forwardType` 是转发规则的执行方式标签，不等于传输协议**（见 `CONTEXT.md`）。策略按运行时是否需要 bind 端口来分：

- **需要 bind 的执行方式**（gost、forwardx、nginx 系）：外部占用 ⇒ **不可用**，拒绝创建，错误信息点名占用进程。
- **内核转发**（nftables、iptables）：外部占用 ⇒ **警告**，需要调用方显式确认后才放行。确认以一个显式入参表达，默认不确认。

### 必须不破坏共用端口的既有能力

ADR-0002 放开了 SNI 分流规则的源端口唯一性——同一入口端口上可以并存多条 SNI 分流规则。这些规则在主机上表现为**同一个受管运行时的同一个监听**，属于受管占用，必须继续判定为可用。**这是本方案最容易踩坏的地方**：一旦把自己的分流器监听误判成外部占用，第二条起的 SNI 分流规则就全建不出来。

同理，隧道监听端口、分流器出口端口被自己的受管运行时占用，都不得触发警告。

### 运行时 bind 失败要回报原因

受管运行时因端口被占而启动失败时，Agent 要识别出「地址已被占用」这一类错误，并作为规则级错误回报面板，使规则卡片能直接显示占用者。目前代码里只有 iperf3 诊断工具做了这个识别，转发规则路径上没有。

占用消失后，规则应在后续心跳中自动恢复运行，不需要人工重建。

### 权限边界

占用进程名属于主机信息。普通用户能得到「端口不可用」的结论，但**不应看到进程名**；管理员才看到完整信息。

### 覆盖面

这项检查要覆盖所有产生端口占用判断的入口：端口输入框的实时校验、规则创建、规则更新、规则启用、批量导入、随机端口分配。批量导入的冲突要能精确到行号。随机端口分配要主动避开主机上已被占用的端口。

## Testing Decisions

好的测试只验证外部可观察的行为：给定的输入下，管理员看到什么结论、规则能不能建出来、期望状态里有没有那条规则。不测内部函数怎么拆、缓存长什么样。

三道缝，全部沿用现有缝，不新增：

### 缝一：tRPC 规则路由（用户看到的判定）

覆盖端口校验与规则创建/更新/启用的最终结论。这是本功能唯一用户可见的输出，绝大多数行为都应在这里验证：受管占用判定为可用、外部占用在用户态链路被拒、内核转发得到警告、确认后放行、同端口多条 SNI 分流规则不受影响、普通用户看不到进程名、无快照时降级。

**Prior art**：`server/rulesPortAvailability.test.ts`——以真实数据库跑 tRPC 路由的 spawnSync 子进程测试，已覆盖转发组端口校验与套餐端口范围。新用例照此扩展。

### 缝二：心跳（占用数据的上报与消费）

覆盖 Agent 上报的端口占用快照被面板正确接收、缓存、并在后续判定中生效，以及快照缺失时的降级。

**Prior art**：`server/sniDesiredState.test.ts`——起真实 express + 心跳路由，POST 心跳并断言返回的期望状态。同一套路可以断言「上报占用后再查端口，结论改变」。

### 缝三：Agent Go（采集与归类）

覆盖监听快照被正确整理成上报结构：绑定地址保留、进程名保留、TCP/UDP 分开、IPv6 与 IPv4 分别识别、体积有上限。以及受管运行时 bind 失败时「地址已被占用」被识别为规则级错误。

**Prior art**：`agent/fxp_spec_test.go`——以构造的运行时状态驱动 `readLocalRuntimeStatePayload` 并断言上报内容。

### 明确不为此单开缝

占用者归类（受管 vs 外部）是纯逻辑，但它**没有独立的用户可见行为**，其正确性完全体现在缝一的结论上。因此不为它单开纯函数缝，除非归类规则在实现中复杂到光靠缝一定位不了问题——那时再拆，并在 spec 上补记。

## Out of Scope

- **提交时向 Agent 实时探测端口**。心跳快照最多陈旧一个心跳周期，对本问题已经够用。实时探测需要新的往返、Agent 在线依赖和降级策略，留待确有需要时再评估。
- **自动停止占用端口的外部进程**。面板不代管不属于它的进程。
- **自动推荐替代端口**。现有随机端口分配避开已占用端口即可，不做「猜你想用哪个」。
- **把主机上所有监听端口做成一个可浏览的页面**。本方案只在端口判定这一个场景用这份数据。
- **历史占用记录与趋势**。只保留最近一次快照。
- **非 Linux 主机**。占用采集依赖 `ss`。
- **容器内端口占用的穿透判断**。Agent 看到的是宿主机视角。

## Further Notes

**这个缺陷是在真实环境中暴露的。** 韩国入口主机的 443 端口被另一套系统的节点进程占着，面板照样显示「✓ 可用」并成功建出规则；实际落地的是一条 PREROUTING DNAT，把 443 的入站流量整个接管了，而原进程仍在监听、毫无察觉。两个系统同时「正常工作」的假象，比任何一方报错都更难发现。

**术语缺口。** `CONTEXT.md` 目前没有描述「主机上某个端口被谁占着」这件事的词。本规格用了**端口占用快照**（Agent 采集、随心跳上报的派生数据，不是用户创建的资源）、**受管占用**与**外部占用**。这三个词在实现落地时应补进 `CONTEXT.md` 的词汇表；**受管占用**可以直接挂在既有的**受管运行时**词条下。

**与 ADR 的关系。** 本规格不与 ADR-0001、ADR-0002 冲突，但 ADR-0002 放开的「SNI 分流规则共用入口端口」是最容易被这项检查误伤的能力，实现时必须有针对性的回归用例，而不是等人工发现。

**一个容易忽略的收益。** 受管运行时 bind 失败的原因回报（本规格的最后一项）单独看是个小改动，但它把一类「规则显示已生效、实际不通」的问题从「翻日志」降级成「看卡片」。这类问题的排查成本远高于它的实现成本。
