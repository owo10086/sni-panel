## 2. 做法

- 放行装在 Docker 文档指定给管理员的 `DOCKER-USER` 链，按“规则编号—入口端口—协议—方向—目标摘要”打注释，限定转换后的目标地址／端口；回程限定返回方向。放行排在管理员规则之后、末尾 RETURN 之前。
- 重新应用就地收敛：先确保目标放行存在，再删除多余的；未变化的规则放行不会被删除重建（验收中用内核规则句柄核对）。删除按规则内容经 `<前端>-restore --noflush` 一个事务完成，不按行号。
- `iptables-nft` 与 `iptables-legacy` 分别判断：只对“FORWARD 默认 DROP 且跳转 DOCKER-USER”的前端动作；legacy 表仅在已加载时读取。
- Agent 就绪判断核实 IP 转发、masquerade、转发／回程放行、Docker 放行，并把上一版目标、已移除协议的遗留视为未收敛。
- 失败原因：内核转发类动作的失败输出进入动作状态消息；主备组子规则由既有机制保存为运行诊断。
- 自测：写入端不再无条件写 `listenOk`／`forwardOk`；读取端附带 `evidence`，旧记录按证据重新解释；网页分开展示“目标连接成功／失败”与“外部路径未验证”。

## 3. 验证与审查中发现并修复的问题

把规则协议从 TCP+UDP 改成仅 TCP 后，Agent 的接管判断只看“所需部分是否都在”，认为已就绪而不重新应用，UDP 的 DNAT、转发放行（以及新增的 Docker 放行）一直残留，退役路径仍然开放。现在就绪判断同时要求遗留物已清掉，且按规则归属判断，同端口上其他规则的状态不会被误判。

代码审查（高强度）另提出并已处理：端口按子串匹配会把 `dport 80` 当成 `dport 8080`（改为整词匹配）；先清后装在重新应用时有空窗且失败会丢失旧放行（改为就地收敛）；按行号删除可能在链被并发修改时误删他人规则（改为按内容经 `-restore` 删除）；把任何列举失败都当成“链不存在”（改为只有链不存在才视为无事可做，命令超时调到高于 `-w 5`）；入口端口检测的提示文案不准确（区分目标检测与入口监听端口检测）。审查还指出 IPv6／主机名目标不核实 Docker 放行：规格明确不扩大 IPv6 范围，保持原有语义，列为已知边界。

## 6. 已知边界

- 只处理 IPv4 与“FORWARD 默认 DROP + 跳转 DOCKER-USER”的 iptables 结构；ufw、自定义防火墙、Docker 的 nftables 原生后端不判断、不修改。IPv6 保持原有“只核实 DNAT”的含义。
- 放行结束 DOCKER-USER 的求值，受管流量不再经过其后的 Docker 隔离链；目标若是本机 Docker 容器，应继续用 Docker 端口发布。
- 普通（非主备组子规则）规则的失败原因记入面板日志，运行诊断字段沿用既有契约只保存主备组子规则。
- 范围外且未处理：美国 4、韩国、德国的 12 个目标端点自身失败；入口修复不保证它们恢复。
- 主备组面板重启后故障计时接续、移组再移回、隧道型主备等沿用 `server/forwardGroupFailover.test.ts` 等既有回归，本次未改动主备策略。
