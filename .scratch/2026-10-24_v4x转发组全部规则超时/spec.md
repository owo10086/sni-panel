# 修复 nftables 转发与 Docker FORWARD DROP 共存及运行状态误报

## Problem Statement

用户访问一个包含 44 条转发规则的主机型主备转发组时，全部入口业务端口连接超时。面板仍显示三台入口在线、规则已运行、期望状态已应用，且香港业务目标检测约 147 ms，用户无法从这些正常状态判断入口转发已经失效。

排查发现，三台入口均存在 Docker 使用的默认 DROP 的 FORWARD 基础链。ForwardX 虽已建立自身的 DNAT、转发 ACCEPT 和源地址转换，但自身基础链中的 ACCEPT 不能覆盖另一个基础链的 DROP。外部 SYN 到达入口后没有继续转发至目标，重复下发当前生成的配置也无法恢复。

Agent 当前对原生 nftables 转发的就绪判断只确认 DNAT 存在，遗漏本机转发必需条件及本次 Docker 过滤冲突；目标自测又将主动连接目标成功写为转发成功。这使实际故障同时被运行状态和目标检测结果掩盖。

## Solution

让 ForwardX 管理的原生 nftables 转发在现有 Docker FORWARD 默认 DROP 的环境中正常工作，保留 Docker 和管理员原有的防火墙策略，只对明确属于相应转发规则的业务流量建立必要放行。

Agent 应确认当前期望配置在本机具备必要转发条件，发现本次支持范围内的配置缺失或 Docker 过滤冲突时，不再仅凭 DNAT 存在报告运行正常。重复应用、Agent 重启后的配置接管、目标变更和规则删除都应保持正确收敛。

面板应明确表达业务目标检测的范围：目标连接成功与外部经入口的业务转发验证分别记录、解释。缺少外部路径验证时，目标成功不能作为该路径已验证成功的依据。

主机型主备转发组继续按入口自身运行与健康选择，并使用既有 DDNS、故障等待和恢复观察规则。单条业务目标失败、缺失或过期不得重新成为整组入口资格的门槛。

## User Stories

1. 作为转发规则的使用者，我希望通过组域名访问可达的业务目标，以便正常使用入口提供的转发服务。
2. 作为主机管理员，我希望运行 Docker 的入口也能承接原生 nftables 转发，以便两类服务在同一主机上共存。
3. 作为主机管理员，我希望 Docker 的 FORWARD 默认 DROP 策略得以保留，以便其他流量继续遵守既有过滤策略。
4. 作为主机管理员，我希望放行仅覆盖 ForwardX 管理的具体转发流量，以便非受管端口、非匹配目标及其他转发路径不被额外放行。
5. 作为 TCP 业务使用者，我希望连接握手和双向应用数据都能通过入口，以便连接成功代表业务路径确实可用。
6. 作为 UDP 业务使用者，我希望请求和响应都能通过入口，以便 UDP 转发不因只验证 TCP 而遗漏故障。
7. 作为转发规则管理员，我希望同一规则反复应用后仍正常工作，以便心跳重试和手动重试不会造成规则重复或失效。
8. 作为转发规则管理员，我希望 Agent 重启后按实际内核状态接管规则，以便旧的已应用记录不能掩盖本机转发条件缺失。
9. 作为转发规则管理员，我希望本机受管放行被删除或支持范围内的 Docker 转发配置发生冲突时，规则不再持续误报就绪，以便能够发现入口自身故障。
10. 作为转发规则管理员，我希望无法建立所需兼容规则时收到可理解的失败原因，以便定位权限、工具或过滤配置问题。
11. 作为转发规则管理员，我希望修改目标地址或端口后只保留新期望配置对应的放行，以便旧业务路径不继续开放。
12. 作为转发规则管理员，我希望目标域名解析更新后转发和兼容放行一起收敛，以便 DNS 更新不会让原本可用的规则失效。
13. 作为转发规则管理员，我希望删除或禁用规则后清理该规则拥有的转发状态，以便停用的业务不残留放行。
14. 作为转发规则管理员，我希望多个入口端口共用同一目标时仍分别受管，以便删除或变更其中一条不会影响其他规则。
15. 作为转发规则管理员，我希望 TCP、UDP 和双协议规则按各自配置生效，以便一种协议的更新和清理不会破坏另一种协议。
16. 作为转发规则管理员，我希望切换原生转发后端时清理与安装相互配合，以便清除旧规则后仍具备新后端需要的放行。
17. 作为主机管理员，我希望使用活动的防火墙后端核实转发条件，以便 legacy 后端显示 ACCEPT 时不会漏掉 nft 后端的 DROP。
18. 作为面板使用者，我希望业务目标检测成功只表达目标连接成功，以便不会把绿色延迟结果误解为外部入口转发已经验证。
19. 作为主机管理员，我希望本机转发就绪不依赖业务目标当前是否在线，以便业务目标自身故障不会被误诊为本机配置没有生效。
20. 作为转发组管理员，我希望入口自身规则未准备好时继续遵守既有故障等待和主备选择，以便真实入口故障能够参与原有故障处理。
21. 作为转发组管理员，我希望单条业务目标失败、没有记录或记录过期时，健康入口仍可维持组域名解析，以便其他正常业务继续使用。
22. 作为转发组管理员，我希望入口在线、流量政策、已开启的入口健康检测和恢复观察继续有效，以便修复不会绕过已有入口资格要求。
23. 作为 SNI 分流规则管理员，我希望当前完整分流配置确认及既有入口选择约定继续保留，以便共用代码调整不改变 SNI 行为。
24. 作为主机管理员，我希望其他 Docker 网络、管理员规则和非 nftables 转发服务保持原有行为，以便修复不扩大到无关业务。
25. 作为运维人员，我希望升级面板或 Agent 的必要条件明确，以便不会把仅升级一端误认为所有运行状态判断都已修正。
26. 作为维护者，我希望用真实 TCP／UDP 往返和对照故障验证修复，以便测试可以发现“配置存在但业务不能通过”的回归。
27. 作为维护者，我希望规则流量归属仍按入口端口和协议区分，以便兼容放行不会使共享目标的统计重复或串入其他规则。
28. 作为运维人员，我希望将入口共同故障与业务目标自身故障分别验收，以便不会把入口修复解释为所有目标服务均已恢复。

## Implementation Decisions

1. **修复范围以原生 nftables 的 Docker 共存故障为中心。** 修改期望状态命令生成、受管规则清理、Agent 内核转发就绪核实及相关检测结果展示。复用现有动作、心跳、规则状态和自测流程，不建立第二套配置下发机制。
2. **兼容必须作用于实际阻断流量的过滤路径。** 仅调整 ForwardX 自身基础链的优先级或增加 ACCEPT，不能作为解决其他基础链 DROP 的方案。应识别实际活动后端及本次支持的 Docker FORWARD 结构，在能够管理的兼容位置安装对应流量的放行。
3. **受管放行必须具备明确归属和流量范围。** 以规则身份、入口原始目标端口、协议、转换后的目标地址／端口及连接方向限定，回程只允许相应连接的返回流量。共享目标不能导致其他入口端口或无关转发被一并放行；保持现有访问限制及流量政策的实际约束。
4. **保留主机既有策略。** 不全局改为 FORWARD ACCEPT，不清空规则集，不删除 Docker 或管理员自有规则，不借兼容规则绕过现有显式拒绝。不能在已支持结构中建立必要放行时，提供失败原因，不把安装失败吞掉后报告成功。
5. **完整管理兼容规则生命周期。** 创建、重复应用、重启接管、目标地址／端口改变、域名重解析、协议变化、禁用、删除及后端过渡均按当前期望状态收敛。只清理自身拥有的规则；多个规则共存时互不清理。更新失败不得把与当前期望不一致的配置报告为已应用。
6. **就绪检查验证本机必要条件。** 除 DNAT 外，覆盖所需的 IP 转发开关、受管转发与源地址转换配置，以及本次支持的 Docker 过滤路径和兼容放行。动作完成判定、已有动作接管及本地运行状态核实使用一致的结论，避免只修正首次应用而保留后续误报。
7. **就绪结论有明确范围。** 它表达当前期望配置在本机已核实的必要转发条件，不等同于任意外部来源到任意业务目标都可达。不引入业务目标连通性作为本机配置就绪的前置条件，也不承诺静态检查可以证明所有自定义防火墙表达式及外部网络路径可达。
8. **保持检测结果的证据含义。** 业务目标连接结果只证明对应检测来源到目标的连接情况；入口健康检测继续表达入口对设置中检测地址的主动连通性。没有执行外部入口路径验证时，不将目标检测结果无条件写为“外部转发已验证成功”。沿用现有接口和存储能力表达失败或未验证；若现有成功字段语义需要调整，须同步修改结果处理、读取方及网页说明，并兼容旧记录和旧 Agent，不让未验证被显示为已验证成功。
9. **遵守 ADR-0008 与 ADR-0006。** 主机型主备转发组保留入口自身运行、在线、流量政策、已开启的入口健康检测、故障／恢复观察、优先级、自动回切及发布解析前复核；SNI 保留当前完整分流配置确认。业务目标失败、缺失或过期不得单独阻止这些组的入口选择、DDNS 或触发整组切换；其他资源类型继续各自既有判断。
10. **不预设数据库迁移或新公共接口。** 优先在现有动作和状态契约内实现；若实施中发现现有契约无法真实区分检测证据，先更新本规格中的契约决定。不得为方便诊断新增生产调试端点或常驻外部探测服务。
11. **兼容现有运行环境。** IPv4 原生 nftables 加活动 nft 后端 Docker 过滤链是本次必验场景；同时覆盖无 Docker 场景及已支持后端的非回归。不扩大 IPv6 能力范围，现有 IPv6 行为不得因共用代码修改而退化。
12. **本地开单和实施分开授权。** 本规格的保存、测试边界确认及本地工单创建均不构成代码实施、生产防火墙调整、服务重启、Agent 升级或部署授权。实施时应明确面板端与 Agent 端各自需要的版本能力。

## Testing Decisions

### 验证边界

以一套隔离 Linux 网络集成场景作为主要新增验收边界：**面板通过现有心跳生成真实期望状态 → 真实 Agent 动作处理与本地状态核实 → 独立客户端经入口完成 TCP／UDP 应用往返 → 现有状态回报入口。**

复用仓库已有的隔离数据库／面板心跳测试方式，以及将真实动作交给 Agent 执行的可选网络集成模式。新增的网络场景覆盖原生 nftables 和 Docker 过滤共存，不从源码提取函数拼装替代 Agent，也不手工重写一份应当被测的生产命令。只增加必要的测试环境组织能力，不为测试增加生产接口。

目标结果语义及主备组行为沿用现有自测结果接口测试、主机型主备转发组测试和本地 DDNS 提供方替身，作为补充回归；不另建生产测试入口。用户要求“按推荐开单”，随后明确工单应留在本地，本轮按上述推荐边界整理为本地规格与工单，代码实施及生产操作仍须另行授权。

### 测试质量

- 以客户端能收到目标应用响应、规则对外上报状态、结果页面含义、DDNS 提供方收到的更新及无关流量仍受既有策略约束为断言。
- 命令生成及快照测试用于补充覆盖后端差异和错误分支，命令字符串匹配不能替代实际网络验收。
- 故障对照必须能使测试失败：保留 DNAT、移除必要兼容放行时，客户端超时，Agent 不得持续报告对应本机条件已就绪；恢复配置后再验证往返与状态恢复。
- 测试在临时容器及网络命名空间内完成，不修改开发机或生产入口的防火墙，不访问生产业务目标和 DNS 提供方。

### 验收场景

| 场景 | 必须观察到的行为 |
| --- | --- |
| 无 Docker、无冲突默认丢弃链 | TCP 与 UDP 往返成功，原有使用方式正常 |
| 活动 nft 后端存在 Docker FORWARD 默认 DROP | 受管 TCP／UDP 双向应用往返成功，默认 DROP 保持，非匹配流量仍被拒绝 |
| legacy 显示 ACCEPT，但活动 nft 后端存在 DROP | 使用活动后端作兼容和核实，不被 legacy 状态误导 |
| DNAT 仍在，必要受管放行被删除 | 检出本机配置缺失，不凭旧修订号或 DNAT 持续报告就绪；修复后恢复 |
| IP 转发关闭，或受管源地址转换配置缺失 | 检出对应本机必要条件缺失，重建后按真实配置恢复 |
| 安装命令失败或兼容结构不满足支持条件 | 返回可理解的失败信息，不吞错后宣告成功，也不修改管理员自有拒绝规则 |
| 重复应用及 Agent 重启接管 | 转发持续可用，受管状态不无限重复，接管按实际内核状态核实 |
| 目标 IP／端口变化、域名重解析 | 新目标可用，旧受管放行清理，状态对应当前期望配置 |
| 删除、禁用及原生后端切换 | 旧受管状态清理；保留其他规则、Docker 及管理员原有规则，新后端按预期工作 |
| 两个入口端口共享目标，或同端口按协议区分 | 一条变更或删除不破坏另一条；访问范围和流量统计归属不扩大 |
| 目标直连成功、外部经入口路径失败或未测 | 目标检测保留成功及延迟，结果不声称外部路径已经验证成功 |
| 目标自身失败，但入口本机配置完整 | 本机就绪与业务目标失败分别表达；按 ADR-0008 保留健康入口选择及 DDNS |
| 入口自身条件失败、恢复、面板重启 | 保留既有故障等待、同一故障计时接续及恢复观察，不借业务目标或其他规则的时间凑数 |
| 旧 Agent 或旧检测记录缺少新核实证据 | 保持协议可用，缺失证据不被伪造为已完成的新核实或外部路径验证 |
| SNI 完整分流确认、其他资源及现有 IPv6 场景 | 既有资格边界、访问限制和运行行为保持 |

### 已有测试依据与本次复现的区别

仓库已有的命令生成／后端过渡测试覆盖规则归属和命令结构；Agent 已有本地运行状态、动作处理和可选真实网络集成测试；面板已有自测路由、主机型主备转发组、观察等待及 DDNS 提供方替身测试。本次优先复用这些组织方式和公开边界。

此前诊断只完成 TCP 隔离往返，并以原样提取的就绪函数核实误报。它是修复前的复现证据，不能替代本规格要求的真实 Agent 集成、UDP 往返及完整生命周期回归。当前规格阶段尚未实施或运行上述新增验收。

## Out of Scope

- 修复美国 4、韩国、德国的 12 个失败目标端点，或承诺所有业务目标随入口修复同时恢复。
- 改变主机型主备转发组及 SNI 的入口选择、业务目标门槛、DDNS 或观察等待策略。
- 全局关闭防火墙、将 FORWARD 策略改为 ACCEPT、清空或接管用户及 Docker 的全部网络规则。
- 自动绕过任意自定义防火墙、实现通用防火墙求值器，或证明任意外部路径均可达。
- 新建常驻公网探测服务、全面重做自测体系、提供持续的互联网可达性保证。
- 重构其他转发后端、隧道、转发链、入口组或 SNI 分流架构；共用改动只做必要适配和非回归。
- 扩展尚未支持的 IPv6／Docker 网络能力。
- 原生移动客户端变更、无关网页改版、计费改造或额外通知功能。
- 直接修改生产规则、重启服务、升级 Agent、部署、创建版本标签或发布软件。

## Further Notes

- 本规格来源于 2026-10-24 的线上只读检查、当前工作区代码定位和本地隔离复现，属于已完成诊断后的修复要求。
- 检查时面板版本为 3.7.0，三台入口 Agent 均为 3.6.0。源码行为与线上内核配置相互印证；本次没有对线上二进制与工作区源码进行逐字节一致性核验，也未确定具体引入故障的历史提交或迁移时间。
