# 03: 保证目标变化与后端切换时受管转发状态正确收敛

**What to build:** 管理员修改规则目标、协议或转发后端，以及业务目标域名重新解析时，新业务路径能够按当前期望状态生效，旧受管放行随之撤除。多个入口端口共享同一目标、同端口按协议分别受管时，单条规则的更新或删除不破坏其他规则，也不残留已经停用的路径。

本单在基本 Docker 共存路径上完成动态变更与清理行为，不另建期望状态通道。无需等待完整就绪误报工单：验收直接使用真实业务往返、当前动作结果和实际受管规则归属。

**Blocked by:** 01：恢复 Docker FORWARD DROP 环境下的原生 nftables TCP／UDP 转发

**Status:** ready-for-agent

- [x] 目标 IP 或端口改变后，新目标可经入口完成 TCP／UDP 往返，旧目标对应受管放行被清理，状态与当前期望一致。
- [x] 使用隔离 DNS 或既有解析替身触发域名重新解析，验证转发与兼容放行一起收敛，不连接生产 DNS 服务。
- [x] TCP、UDP、双协议之间变化及按协议删除，既清理过期受管状态，也保留另一协议仍需使用的状态。
- [x] 两个入口端口共用目标时，变更、禁用或删除其中一条不影响另一条；不能用仅按目标匹配的宽泛放行绕过归属隔离。
- [x] 原生 iptables 与 nftables 后端过渡后，旧后端受管状态正确清理，新后端业务真实可用；删除旧规则不能再次造成 Docker 默认 DROP 阻断。
- [x] 重复更新、重试和 Agent 重启接管不造成规则无限重复或旧放行残留；失败更新不被报告为当前期望已经应用。
- [x] 禁用及删除保留其他规则、Docker 链、管理员规则及非受管网络流量策略，现有访问限制不被兼容路径绕过。
- [x] 共享目标的流量仍按原始入口端口及协议归属；相关共用 IPv6 和非 nftables 场景通过适用的既有回归。
- [x] 上述行为在前置工单的同一隔离网络场景扩展验证，不新建生产测试端点。

## Comments

2026-10-25 已实施并验证。验证中发现并修复一个真实缺陷：协议收窄后 Agent 因“所需部分都在”而接管，遗留的 UDP DNAT、转发放行与 Docker 放行不被清理；现在就绪判断同时要求遗留物已清掉（按规则归属，不误伤同端口其他规则）。

- 域名重新解析走 Agent 自带的 DNS 监测（容器内 /etc/hosts 为隔离解析源）加面板的强制重解析（Node 的 dns/promises 换成本地表），没有访问真实 DNS。
- 共用 IPv6 及非 nftables 场景由全量回归覆盖。
