# 合并上游 v2.3.289：规格

Status: completed

确认日期：2026-10-24。用户已确认功能取舍，并调用 to-spec 保存正式规格。

授权边界：最初的“同意”仅确认并保存规格，随后用户通过 `$implement` 明确授权本地实施、验证、审查和当前分支中文提交。交付终点为本地兼容合入、验证和中文提交；推送、打标签、正式发布及生产部署不在本轮交付范围。

## Problem Statement

本地 sni-panel 已发布 v3.6.0，累计兼容上游 v2.3.288。上游 v2.3.289 新增库存与按量计费的每账号逻辑规则上限，并改进查询性能、MySQL 初始化兼容、多 IP UDP 回包和网页展示。需要兼容这些能力，同时保留本地 SNI 分流、账号配额、权限、计费收尾和入口健康判断，避免直接覆盖上游文件造成已有行为回退。

用户希望只讨论实际功能冲突和取舍，不扩大为新的产品设计或流程采访。本轮已核实的功能交叉可以兼容处理，没有尚待用户选择的功能冲突。

## Solution

以固定上游 v2.3.289 为唯一目标，在现有本地版本上兼容合入网页、服务端及 Agent 相关变化。库存和按量逻辑规则上限完整采用上游语义，默认 `0＝不限`，与本地现有账号配额共同生效。查询性能、数据库兼容、UDP 和展示改进按既有本地行为适配。

原生客户端和作者赞助内容按长期约定排除；本地 SNI 分类、完整分流配置确认、主机型主备组入口判断、DDNS、权限及费用收尾继续保留。现按 `$implement` 授权完成本地验证和中文提交；远程发布仍不在授权范围。

## User Stories

1. 作为维护者，我希望合入固定 v2.3.289 的有效变化，以便升级范围明确且可复核。
2. 作为现有用户，我希望升级后库存和按量规则上限默认不限，以便原有使用方式不会因新增配置被意外限制。
3. 作为管理员，我希望为订阅套餐设置销售库存，以便控制升级后继续销售的数量。
4. 作为管理员，我希望历史已售订阅不被追溯为新增销售库存，以便遵循上游的升级口径。
5. 作为购买者，我希望待支付订单预占库存、取消或过期时释放，以便支付过程中不发生超售或永久占额。
6. 作为订阅用户，我希望续费不重复占用销售库存，以便已有服务可以按既定规则续期。
7. 作为管理员，我希望订阅到期或取消不自动返还已售库存，以便销售总量口径保持一致。
8. 作为管理员，我希望按量资源按当前占用的用户数限制库存，以便控制可使用该资源的账号数量。
9. 作为按量用户，我希望同一账号在同一计费资源创建多条规则只占一份库存，以便库存与规则条数分别计算。
10. 作为按量用户，我希望删除最后一条有效逻辑规则后释放该资源的库存占用，以便不再使用资源时归还名额。
11. 作为管理员，我希望停用规则仍保留按量库存占用，以便停用与删除保持不同含义。
12. 作为管理员，我希望为每个按量计费资源设置每账号逻辑规则上限，以便分别限制账号占额和规则数量。
13. 作为已占用按量库存的用户，我希望库存耗尽后仍能在个人规则上限内增加规则，以便库存限制不会重复阻止已有使用者。
14. 作为现有用户，我希望管理员降低限额时保留已有规则，以便新限额只约束后续新增和需要重新校验的变更。
15. 作为 SNI 使用者，我希望每条域名根规则分别计数、自动成员副本不重复计数，以便共用监听不会把逻辑规则混为一条。
16. 作为账号所有者，我希望账号规则额度、端口额度和资源规则上限同时生效，以便新增功能不绕过既有配额。
17. 作为批量操作用户，我希望导入、复制、移组和修改所属账号时正确校验库存与上限，以便批量操作和并发操作不能超额。
18. 作为管理员，我希望迟到付款遇到库存不足时保留真实付款及发放失败状态，以便补货重试或通过支付渠道退款，而不虚报发放成功。
19. 作为计费用户，我希望规则删除继续完成费用结算、停止确认和失败重试，以便库存变化不会造成漏账或重复收费。
20. 作为规则使用者，我希望列表查询更快且账号数据相互隔离，以便性能改进不会泄露其他用户的数据。
21. 作为管理员，我希望权限撤销、余额和库存执行仍使用当前有效状态，以便展示缓存不会成为授权或扣费依据。
22. 作为 MySQL 使用者，我希望旧版 MySQL 的初始化握手正确兼容，以便继续安装和启动面板。
23. 作为多 IP UDP 使用者，我希望回包使用实际接收请求的入口 IP，以便客户端不会因源地址错误丢弃回包。
24. 作为多 IP UDP 使用者，我希望同一客户端访问不同入口 IP 时会话分别处理，以便数据不会串到另一个入口。
25. 作为链路资源使用者，我希望卡片同时展示北京时间当日流量和累计流量，以便区分当天用量与历史累计。
26. 作为转发规则使用者，我希望规则页继续展示最近连续 24 小时流量，以便它与北京时间当日流量分别解释。
27. 作为运维使用者，我希望排名默认展示前 5 项、展开后查看前 10 项，以便兼顾概览与详情。
28. 作为管理员，我希望按量资源拥有独立展示名称和富文本说明预览，以便准确介绍资源和计费方式。
29. 作为网页使用者，我希望规则文字清晰、窄卡片可操作、支付开关和悬停反馈符合上游调整，以便日常操作更顺畅。
30. 作为 SNI 使用者，我希望保留独立分类、可见域名和完整异常信息，以便网页调整后仍能识别分流规则。
31. 作为 SNI 转发组使用者，我希望落地检测缺失、过期或失败不会单独阻塞入口选择或 DDNS，以便正常入口仍能承接业务。
32. 作为主机型主备组使用者，我希望按入口自身运行与健康选择成员，并保留观察等待、重启续算和当前副本判断，以便已有故障切换行为不回退。
33. 作为维护者，我希望保留本地品牌、安装来源、升级预检、个人分组和事务修复，以便兼容合入不丢失已有能力。
34. 作为维护者，我希望跳过原生客户端和赞助入口，以便遵守长期维护范围。
35. 作为验收者，我希望看到实际验证结果及未验证项，以便区分本机验证、Linux 行为验证和人工验收。
36. 作为维护者，我希望获得按功能拆分的中文本地提交，并把本轮文档统一提交，以便后续审查和维护。

## Implementation Decisions

1. **固定比较对象**：本地确认时 HEAD 为 `4fa1c892012be90f007b11c1d7dd27a4721ced44`，面板、Agent、FXP 为 v3.6.0；已兼容上游 v2.3.288，实际提交 `d776443c024f3357477d6b8b23a24b77a5237bb0`。唯一新目标为 v2.3.289，实际提交 `e73e01b0c3e57da8190c22bbe490170184d50d2e`，标签对象 `c31d258ee51157c68b91bed1a13ad6000fcc5d8c`。调查时上游 main 与该标签一致；之后的新提交不自动扩大范围。288 至 289 共 2 个提交、77 个变化文件，这只是上游增量，不是覆盖本地完整文件的许可。
2. **兼容合入方式**：沿用本地既有的功能兼容移植方式。按固定上游增量逐项核对本地对应行为，同时核对本地与目标的直接差异，保留本地独有实现。不能以本地历史不含上游提交为理由重复覆盖旧功能，也不默认使用一次普通合并代替功能适配。
3. **涉及模块**：主要涉及产品库存、套餐与订单支付、按量计费配置、规则创建与变更、查询展示缓存、数据库连接与迁移、Agent UDP 监听和网页展示。沿用已有服务与 API 边界，纳入固定目标必要的字段、校验和返回信息，不引入无关重构。
4. **库存及迁移默认值**：按上游纳入套餐销售库存、已销售占用、按量资源库存和每账号逻辑规则上限。旧配置默认为 `0＝不限`；历史订阅销售不追溯计入新增销售库存。升级后新购即使不限库存仍累计销售占用。三种支持的数据库方言、初始化和迁移保持字段语义一致。
5. **订阅销售库存**：新购、管理员新分配和兑换每份占 1；待支付订单预占，未付款取消、过期或创建支付失败后释放。续费不额外占用；已售订阅到期或取消不返还销售库存。该值表示销售总量，不解释为当前活跃订阅数。
6. **按量库存**：同一用户在同一有效计费资源拥有至少一条有效逻辑根规则即占 1 份，停用不释放；最后一条根规则逻辑删除后释放。库存耗尽不阻止已占库存的用户在个人上限内继续新增。降低库存或规则上限不删除现有规则，后续新增及上游要求重新校验的变更按新值执行。
7. **逻辑规则与账号配额**：每条 SNI 域名根规则分别计数，受管成员副本不重复计数。两个域名共用一个入口端口仍为 2 条规则、1 个端口。资源每账号逻辑规则上限与现有账号最大规则数、最大端口数同时生效，保留本地并发配额预留与共享端口去重，不把新字段替换为旧账号配额。
8. **资源归属与写入校验**：计费资源继续按转发组、隧道、主机优先级选择首个已启用的匹配配置，一条逻辑规则只归一个有效计费资源。单次和批量创建、导入、复制、变更资源、移组、变更所属用户及恢复删除状态，均在适当的实时事务中校验库存与上限。库存检查和写入保持原子，保留本地权限、SNI 校验及跨账号隔离。
9. **订单异常与幂等**：订单关闭后迟到付款须重新核对库存；库存不足时保留真实已付款和发放失败状态，供管理员补货重试或通过支付渠道退款，不虚报成功、不超售。不将上游既有的退款处理说明扩展为自动退款系统。重复回调、重试和订单状态转换不能重复占额、重复发放或重复入账。
10. **删除与费用收尾**：逻辑销售名额与真实监听、端口占用及账务清理分别判断。保留根规则先结算成功再逻辑删除的本地流程；结算失败不提前标记删除。逻辑删除后库存可释放，真实运行清理仍等待停止确认。受管子副本不计库存，其待结清重试、欠费停用、历史墓碑和最终清理条件照旧保留；不得为合入库存整段覆盖本地删除事务。
11. **并发与事务保留**：保留本地计费用户锁先于数据库事务的顺序、个人分组账号隔离、MySQL 旧快照修复，以及仅在规定死锁条件下对最外层事务完整回滚重试的边界。库存事务与这些既有约束兼容，不局部重跑结算或提交后动作。
12. **展示缓存**：纳入短缓存、并发请求合并、有界排队和写入前后失效。展示缓存按有效角色、账号及完整查询条件隔离；默认新鲜 2 秒，随后 8 秒可沿用旧展示并后台刷新；规则和主机分页列表只保留 2 秒新鲜缓存。失败或部分写入、本地后台结算、权限变更及数据库切换等路径按实际影响失效。读取前后的现有授权检查继续执行。
13. **实时决策边界**：展示缓存不得用于认证、权限证明、余额、支付兑换、库存、流量限额、SNI 完整配置确认、组入口健康或 DDNS 决策。不能用缓存命中绕过权限撤销，也不能以列表暂时旧值改变计费或运行状态。
14. **MySQL 兼容**：在所有相关 MySQL 建连路径按上游禁用可选的查询属性能力，解决受影响旧版 MySQL 的握手兼容问题，保留预处理和参数绑定。初始化、升级、切换和现有数据访问继续受本地迁移保护。
15. **多 IP UDP**：Agent 在支持的 Linux 路径记录数据包实际接收的本地入口 IP，并使用该 IP 回包；同一客户端访问不同本地入口 IP 时分别建立会话。保留 IPv4、IPv6 和平台兼容行为，不把非 Linux 回退路径的构建成功当成 Linux 行为验证。SNI 继续使用 TCP，不扩大为 SNI 数据面设计变更。
16. **网页展示**：纳入运维排名默认前 5、更多前 10，按量资源独立名称、Markdown／HTML 说明与预览，文字清晰度、窄卡片、支付总开关位置和悬停反馈等固定目标变化。沿用本地内容渲染和安全转义、权限及菜单边界，保留本地品牌、来源和升级预检。
17. **流量口径**：链路资源卡片新增北京时间 00:00 起的当日流量，并继续展示累计流量；规则页最近连续 24 小时流量不被替换。累计流量、规则额度已用和账户套餐已用保持各自口径及已有多入口去重、计数归属。
18. **SNI 和规则展示保留**：保留 SNI 独立分类、普通“全部”排除 SNI 的列表与统计、必显域名、完整显示组、异常提示、个人分组和列表偏好。旧异步报告与历史绿色缓存不得覆盖当前配置、明确运行错误或有效占用诊断；创建仍只按既有数据库冲突、端口范围与套餐限制校验，不恢复主机监听占用的创建前置门槛。
19. **入口健康与 DDNS**：遵守 ADR-0006、ADR-0007 和 ADR-0008。SNI 目标检测缺失、过期或失败不单独卡入口或 DDNS，但在线、当前完整分流配置确认、已开启的入口健康检测及观察等待仍必需。仅主机型主备组的普通规则按既定入口运行与健康选择，保留同成员／规则／副本故障重启续算、跳过待删除旧副本、恢复观察和解析发布前复核。其他资源类型继续各自既有策略，国内健康检测与转发组入口健康检测不混称。
20. **长期排除**：原生 Android、iOS／iPadOS 应用及专属版本、依赖、锁文件、下载更新、工程和发布变化均按长期约定排除；网页与服务端变化正常合入，混合文件只取所需部分。作者赞助、捐赠入口及专属素材、地址和文案继续排除，许可证、来源和致谢保留。
21. **工作区与交付**：保留现有全部未提交内容，实施前重新核对 HEAD 与工作区，不创建工作树、不擅自暂存或提交其他任务。规格确认时只约定未来交付终点，后续 `$implement` 已授权实施。大改动按功能拆成中文代码提交，本轮文档在核对后统一为一次中文提交；沿用源码版本推进和 Agent／FXP 一致性规则，不据此创建标签或远程发布。

## Testing Decisions

测试优先使用已有最高层可观察行为入口，以用户结果、状态变化、权限和数据一致性作断言，避免只验证内部函数调用或照抄实现。主要入口是现有带账号上下文的规则、产品／订单、支付及查询 API；网页通过已有组件和浏览器操作补足展示验证。Agent 的网络行为使用既有 UDP 集成入口，数据库兼容使用已有真实数据库升级入口。这些是既有测试边界，不新增测试专用业务接口。

以下为本轮实施的验证要求；实际结果与验证限制记录在对应工单和本文末尾，不以要求代替通过证据。
