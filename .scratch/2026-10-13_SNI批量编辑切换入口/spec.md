# 修复 SNI 批量编辑切换入口时误报端口占用

**日期：** 2026-10-13，Asia/Shanghai。  
**Status:** resolved  
**当前阶段：** 代码实施、自动检查及 `v3.3.4` 正式发布已完成；三张实施工单的结果见[验证记录](验证记录.md)，发布与公开产物证据见[发布记录](发布记录.md)。人工验收待用户确认，生产升级未执行。  
**授权边界：** 用户明确调用 `implement` 并要求完成本目录任务，授权代码实施、测试及技能要求的本地提交。随后于 2026-10-14 明确要求“实施完成后，发布新版本”，补充授权版本准备、向 `sni-panel/main` 推送及正式发布；生产服务器升级和补改生产规则不在本次授权内。

## 问题说明（Problem Statement）

用户在面板批量编辑 7 条 SNI 分流规则、更换入口时，收到：

> 成功 2 条，跳过 0 条，失败 5 条：Port 443 is already used or being allocated on a forward-group entry host

这些规则的域名不同，本来允许在同一合法入口共用 443。面板同时处理多条规则时，却把另一条规则的临时端口预留当成真正占用，提前拒绝后来的请求。另一个问题是允许共用端口的规则名单可能过时：别的任务已迁入，当前任务仍拿迁入前的名单检查，也会误报冲突。

好比几户人家搬进同一栋楼，房间不同，都能用同一个大门；面板却让第一户临时独占大门，其他人被拦下来。等第一户搬完，后面的人又可能因为拿着旧入住名单而被拒绝。

用户看到的是一次批量操作，但其中的成功项已经保存，失败项没有一起完成，用户必须逐条核对。问题也能在同组编辑中出现，不只发生在跨组切换。

已在临时数据库、真实规则接口中确认上述两项原因。后续扩大排查，主机型转发组、端口转发、转发链、直接隧道均能复现同时编辑的端口误判；直接隧道的有效复现场景为 TLS 隧道。详细事实及现场限制见[排查记录](排查记录.md)。

这次问题在 3.3.1 已存在，与此前批量删除卡住的问题不同：本次请求能返回，后台和数据库仍可继续处理。远程面板排查时运行 3.3.3，没有证据说明是 3.3.3 新引入的编辑变化。

## 解决方案（Solution）

在服务端统一协调涉及同一主机的 SNI 规则写入。多个请求一起到达时，让有关请求按顺序完成“重新读取、检查、临时预留、保存和成员整理”，后面的请求使用前一个请求保存后的最新情况判断。使用不同主机的请求继续各自处理。

例如，7 个不同域名从资源 A 切换到资源 B，目标端口都是 443。网页仍可同时提交最多 6 条；服务端让涉及相同主机的写入依次完成，7 条合法规则都保存到 B，端口保持 443。若其中一条域名重复或没有权限，仍单独失败，其余合法规则正常处理。

修复范围按用户已选择的“统一检查所有 SNI 入口”确定：

| 入口类型 | 本单覆盖的规则行为 |
| --- | --- |
| 主机型转发组 | 同组编辑、跨组迁移、多入口成员配置、旧成员撤除。 |
| 端口转发 | 同一主机的创建与编辑、旧新所属主机之间的切换。 |
| 转发链 | 入口、中间成员、出口，以及引用入口组的规则写入。 |
| 直接隧道 | 当前已支持 SNI 的直接隧道，包含主入口、入口组成员和出口；覆盖与转发组之间的转换。 |

上述范围共同使用一套协调办法。按用户确认的拆分，保留原 01 总工单，增加三张实施工单，依次完成“同入口批量维护 → 批量切换入口 → 等待、变化与失败处理及完整验收”。每张均包含实际修复和对应检查，不按四类入口各自建立一套办法。保留现有逐项结果、权限、费用及运行确认流程。

## 实施决定（Implementation Decisions）

### 1. 统一按实际主机协调

新增一个小型内部协调模块，复用现有按编号排队的工具，不增加依赖。规则创建、规则编辑、规则启停的服务端处理共同使用它，导入沿用创建路径纳入。

协调依据是操作涉及的实际主机，不只看转发组或隧道编号。不同资源可能使用同一主机，单按资源编号排队会漏掉冲突。同一主机上的 SNI 写入即使使用不同端口，也需要协调，因为域名唯一要求跨端口生效。

一次操作纳入旧、新路线涉及的主机：

- 主机型转发组：启用入口成员，以及此次需要撤除旧配置的成员主机。
- 端口转发：旧、新所属主机。
- 转发链：入口、中间成员、出口，以及引用入口组的相关主机。
- 直接隧道：主入口、入口组相关成员、出口。

主机编号去重后，按从小到大的顺序取得处理位置；完成或失败均释放。不同主机之间不设置全局队列。该模块只协调当前单面板进程内的请求。

### 2. 先排队，再重读和检查

编辑前或编辑后的规则只要包含 SNI，就进入协调；不能只判断本次输入是否填写 SNI。单规则已有的排队保护继续保留。

排队前只读取确定操作对象和旧、新路线所需的信息，不提前预留端口或保存规则。取得主机处理位置后，还须取得相关资源已有的保存位置，再重新读取规则、资源、成员和允许共用的规则名单，完成原有权限、域名、端口及费用检查。最终重读必须在上述等待全部结束后、临时端口预留和写入前进行，不能复用等待前取得的路线或共用名单。

如果等待主机位置或资源保存位置期间，相关主机集合变化，先退出本轮保存流程，释放本轮已取得的资源保存位置和主机位置，再按最新路线重新排队。两段等待共用最多重试 3 次的上限，不能各自重新计数，也不能占着旧位置等待新主机。持续变化时返回“入口配置已变化，请刷新后重试”，不提前预留端口或部分保存。即使主机集合相同，也要按最新资源内容检查；等待期间规则已被删除、待删除或权限变化，继续按现有规定拒绝。

例如，目标组原来使用 A 服务器。规则编辑已按 A 取得主机处理位置，但还在等待组内保存；排在前面的成员调整把入口换成 B。轮到规则编辑时，必须先发现这次变化，退出本轮并按 B 重新排队，不能沿用 A 的队伍直接保存到 B。

最后一次路线确认到保存完成期间，应持续使用与相关成员、路线调整共用的已有保存保护，不能确认后又在没有保护的情况下等待另一处保存位置，让入口再次被改掉。创建、编辑、启停，以及直接隧道和入口组引用的路线，均须满足这条要求。

2026-10-14 测试及审查补充：成员保存、启停、排序和删除都可能改变路线，必须使用上述共同保护。“不重写资源编辑功能”不排除为满足这条要求补齐短范围的保存保护。停用且没有待清理有效配置的成员，以及已经待删除的旧成员，不额外扩大主机队伍。

### 3. 固定处理次序，缩短占位时间

处理顺序固定为：

1. 保留已有单规则排队，取得旧、新路线所需的主机处理位置。
2. 取得相关资源已有的保存位置后，最终重读并确认路线；主机集合变化时退出并重新排队，确认一致且通过原有检查后才取得临时端口预留。
3. 沿用现有保存流程，完成根规则、成员配置及隧道端口映射整理。
4. 在成功或失败清理中释放临时预留、相关资源保存位置和主机处理位置。
5. 按现有流程继续故障判断、DDNS 和后续刷新。

主机处理位置和相关资源保存位置必须在数据库事务外取得，不能占着数据库等待其他规则交出位置。创建、编辑、启停采用一致的进入次序：先取得主机位置，再取得相关资源已有的保存位置，随后最终重读、检查、预留和保存。不能出现一条路径占着组位置等主机、另一条占着主机等组的反向等待；已有保存流程须配合这一顺序，不能在内部重复申请自己已取得的位置。不能直接拿已有的整组排队包住整个编辑流程。

进入 DDNS 外部等待前，必须释放新增的主机处理位置和临时端口预留。同组另一条规则在 DNS 请求尚未完成时仍须能保存；不要求前一条完整请求已经返回。DNS 返回后继续沿用现有最新配置校验，旧健康决定不能覆盖后来的编辑。

保留 3.3.3 已修正的计量次序：数据库提交并释放后，再做需要延后的结算和入口通知。不得因新增协调把结算重新搬回数据库事务中。

### 4. 保留共享与占用检查的边界

继续沿用已确定的 SNI 共享规则：域名规范化后互不相同、资源允许共用、确实使用同一受管监听时，才允许共用端口。同一根规则的合法成员副本继续排除在自身冲突检查之外。

仍拒绝重复域名、普通规则混用同一端口、不允许共用的资源和面板数据库已登记的真实端口冲突，不把临时预留改成任何请求都能共用，也不把用户的 443 自动换成随机端口。

2026-10-14 测试核对补充：上述“已识别的真实占用”按[创建规则时撤除主机端口占用校验的决定](../../docs/adr/0004-no-host-occupancy-check-during-rule-creation.md)理解。创建、修改时检查数据库中的冲突、端口范围及套餐限制，不读取外部监听快照来阻止保存或要求确认；内核转发仅在有效上报表明占用时显示独立警告，用户态转发绑定失败时显示运行错误。按[占用上报覆盖决定](../../docs/adr/0003-bounded-derived-data-declares-exact-coverage.md)，未覆盖的端口和协议只能算“未经核实”。本次保存检查通过，不能据此声称主机上没有外部监听；本次也不重新引入保存前主机监听校验。

隧道端口映射整理如需要在内部重新申请端口，保留原有先释放调用方预留的处理，避免规则与自己的预留冲突。已有合法共享的出口端口保持稳定，不因重复编辑错误重新分配。

### 5. 沿用保存、费用和逐项结果

不修改接口请求、返回格式或数据库结构，不改变网页最多 6 条同时提交的方式。批量操作仍由多条现有规则操作组成，每条返回结果；成功项保留，不进行整批回滚。

保存失败时保留原配置，不发送未提交配置的通知，释放临时预留和主机位置。回退覆盖本次保存涉及的根规则、成员配置、端口映射和必要隧道状态，不能只恢复其中一部分。直接 TLS 隧道创建、编辑时，根规则、映射整理和必要隧道状态一起保存或一起撤回；创建失败不能留下新规则。配额申请、释放及处理位置等待放在数据库事务外，配置通知在提交后才发出。已经提交后发生 DDNS 失败时，沿用原有错误处理，不擅自把已保存规则撤回。

2026-10-14 测试补充：A→B→A 或再次迁回 B 时，可能重新使用旧成员记录。先前迁出安排的延后清理不能把重新使用的有效成员停用；已经待删除的旧成员不重复安排同一轮清理。迁出用量仍按原规定结算一次，不改变费用政策。此项与上方完整回退要求都是原有“配置正确、失败保留原配置”的具体边界；修复前失败和修复后结果见[验证记录](验证记录.md#测试发现与决策对应)。

权限、用量结算、余额不足停用、旧入口撤除和新入口配置确认继续沿用现有规定。保存成功仅代表面板保存完成，运行状态仍依赖入口与出口的有效确认。

删除流程不重写，但纳入编辑与删除同时发生的回归检查。资源成员编辑、隧道路线编辑和 DNS 服务商编辑不在本单重做范围内；规则写入仍须遵守前述最终重读与保存保护要求，不能因此省略等待资源保存位置后的路线确认。

## 测试决定（Testing Decisions）

### 验证入口与测试方式

沿用此前方案的验证入口：通过真实规则创建、编辑、启停和删除接口发起操作，使用临时 SQLite，再通过真实 Agent 心跳处理取得期望状态和提交模拟运行报告。四类入口使用同一套外部行为检查办法，不为每种资源另造一套替代保存流程。

2026-10-14 测试方式补充：四类入口按各自已有的配置形态核对。直接 TLS 隧道的主入口、入口组成员核对 GOST 隧道配置和对应规则清单，出口核对独立分流器的域名、目标与限制；不能要求其入口出现转发链使用的 `sniRoutes` 分流表。直接 SNI 隧道仍只支持单出口，不支持开启负载均衡、引用出口组或启用附加出口。本次 TLS 验证不代表扩大其他模式或多出口支持，运行中仍按各类入口、出口已有的有效确认标准判断。依据见[独立分流器决定的形态补充](../../docs/adr/0001-sni-splitting-runs-as-a-standalone-fxp-role-at-the-exit.md#2026-10-14直接-tls-隧道的既有配置形态)。

沿用现有 SNI 转发组和 SNI 规则接口测试的独立子进程、临时数据库及合成账号主机做法；参考已有批量删除、费用保护、SNI 生效确认和 DDNS 等待期间继续保存的检查。原则是检查实际返回结果、数据库内容、费用和入口期望状态，不以内部函数调用次数或某个锁名作为通过条件。

必要的等待、失败和占用可以在既有计量、数据库或本地 DNS 测试边界控制，仅用于制造可重复的先后顺序。不得因此增加生产接口，不连接生产 Agent 或真实 DNS 服务商。

先记录旧代码下合法并发操作失败，再实施修复并验证通过。既有临时诊断程序是排查证据，不能替代纳入服务端完整测试的回归用例。
