# SNI 转发组按已确认的入口健康选择并更新 DDNS

**状态：已确认。2026-10-18 用户明确重申为长期上游合并约定。** 本决定延续本地 3.3.2 已确定的行为，替代 ADR-0001 中 2026-10-10“全部落地连接健康后参与选择”的旧要求。

主机型转发组承载多条共用端口的 SNI 规则时，以入口能否正确运行当前完整分流配置判断入口资格。禁止把上游逐条等待规则落地健康检测结果的通用方式套回 SNI 转发组：SNI 落地检测结果缺失、过期或失败，均不得单独卡住入口选择、阻塞 DDNS 或触发整组切换。

## 保留的本地规则

1. 入口 Agent 在线，且入口实际运行的全部应运行 SNI 分流配置与面板当前要求一致，包括域名、目标、端口和限制。仅保存成功、命令已下发、端口存在或曾经确认过，均不能代替当前有效的完整配置确认。
2. 组内已开启的国内健康检测须通过；未开启时没有这一项额外条件。
3. 故障与恢复观察使用面板设置，保留现有优先级、自动回切和有效报告判断。入口失去确认或重启后，按现有规则重新确认并完成必要恢复观察。
4. SNI 落地检测仍可用于展示和排查，但其缺失、过期或失败不单独决定 SNI 入口资格。修改落地目标后，仍须确认新分流配置生效；配置生效后，不另等新目标的连接检测才能选择入口。
5. 同组混有普通规则时，普通部分继续执行原有目标检测。不能因组中有 SNI 而跳过普通规则的要求。

## 为什么不采用逐条等待落地检测的方式

多条 SNI 规则共用一个监听，检测可能只产生代表规则的记录。逐条等待会让入口已经能够完整分流、国内检测也已通过，却因其他规则没有检测记录而一直无法选择入口或更新 DDNS。

例如，两台入口都承载 12 个共用 443 的域名，完整配置已确认生效、国内检测正常，但只有一条代表规则有落地检测记录。其他 11 条缺少检测记录不能阻止入口按现有观察条件取得资格，也不能卡住 DDNS。

再如，`a.example` 的落地 X 停止服务，`b.example` 的落地 Y 正常，而入口的分流和国内检测正常：不因 X 的故障切换整个组。换入口未必能修复 X 的故障，还会让使用 Y 的业务一起经历入口地址变化。

完整配置仍然是必要条件：同样是 12 个域名，如果某个域名的配置没有生效、仍指向旧目标，入口就没有准备好。这与“某条落地检测没有记录”分别判断。

上游对组健康、规则探测、报告新鲜度、成员同步和 DDNS 的改动，都须按本决定兼容，不能整段覆盖本地 SNI 专用判断。只有用户明确要求改变本决定时，才重新讨论。
