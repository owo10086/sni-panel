# SNI 分流由独立 fxp 分流器承担

SNI 分流需要读取客户端 TLS 握手里的域名，再决定连接下一目标。我们把这个能力实现为 `forwardx-fxp` 的一个独立运行时角色，同时部署在转发链入口与链路出口：入口分流器按域名选择对应转发链的下一跳，出口分流器按域名选择落地机。该角色不内嵌进隧道出口，也不借用 nginx 或 HAProxy。

## Considered Options

**nginx `ssl_preread`** —— 面板已有一套完整的受管 nginx stream 管线（配置面板侧渲染、Agent 落盘并平滑重载），加一个 `map $ssl_preread_server_name` 就能分流。否决原因有三：`nginx` 与 `nginx_stream` 在默认协议开关里是关闭的；Agent 的 nginx 运行时是**拷贝主机上的系统 nginx 二进制**，能否用 `ssl_preread` 取决于该发行版怎么编译，装不上就没有分流；每条 SNI 规则的流量只能靠解析 session access log 得到。

**HAProxy** —— 姊妹项目 relay-panel 的做法。否决原因是引入一个 ForwardX 从未托管过的新依赖，而安装脚本一贯的策略是不碰主机上已有的同名服务，为此要新增一整套安装、探测、能力上报和配置校验。

**内嵌进 FXP 隧道出口** —— 出口本来就是 fxp 进程，分流长在里面可以做到零额外跳。否决原因是它把分流能力绑死在 `mode = forwardx` 的隧道上；GOST 隧道、Nginx 隧道和转发链的出口都不是 fxp 进程，这些链路形态就用不了分流。

## Consequences

分流器与链路类型完全解耦：隧道、转发链、端口转发的最后一跳都可以把流量交给它，换 KR→HK 那一跳的实现不需要重配任何分流规则。

Agent 已经在解析 TLS 记录和握手头（`detectTLSProtocol`，用于协议阻断），取 SNI 是往下读扩展的增量改动。

转发链、单机端口转发和直接隧道的每条 SNI 规则的流量、限速和连接数上限全部由出口分流器按匹配到的规则执行。入口组可能包含多台并行接收流量的入口主机，如果在入口执行限速与连接数上限，实际额度会随入口主机数量增加。出口分流器是连接到达落地机前的唯一必经点，因此能够统一执行限制并提供唯一的计量来源。

代价是非 FXP 链路多一次本机回环拷贝。

## 2026-10-10：主机型转发组

主机型转发组的每台启用成员直接承担最终分流，业务端口就是分流器监听端口。增加一个公共出口会使主备入口仍依赖同一台出口，无法解决这次需求，因此不推断“最后一个成员”为出口，也不增加本机回环端口。

限速和连接数按每台最终分流器执行。旧连接与 DNS 缓存可能让多台入口同时服务，不能称为全组严格总上限；实际流量由各成员报告并按现有转发组机制去重、汇总到根规则和归属用户。成员只在最新目标和限制已实际生效、到所有启用规则的落地机连接健康时参与选择；故障切换仍以整个转发组为单位。

## 2026-10-14：直接 TLS 隧道的既有配置形态

批量编辑测试核对了直接 TLS 隧道与转发链的区别：直接 TLS 隧道的主入口和入口组成员沿用 GOST 隧道配置，合法规则共用业务监听；域名匹配、每条规则的计量、限速与连接数上限由出口独立分流器执行。入口检查应核对 GOST 配置及对应规则清单，出口检查分流表，不能把转发链入口的 `sniRoutes` 要求套到直接 TLS 隧道上。保存成功仍与实际运行确认分开，各类入口和出口沿用已有的有效报告判定。

直接 SNI 隧道当前仅支持单出口，开启负载均衡、引用出口组或启用附加出口均不支持。本次核对的是有效的直接 TLS 场景，不代表扩展其他隧道模式或多出口支持。这是对既有配置形态的澄清，具体测试和证据见[本次验证记录](https://github.com/owo10086/sni-panel/blob/3b0394a0efd087a38708591089f3dc212c34c1ff/.scratch/2026-10-13_SNI批量编辑切换入口/验证记录.md#测试发现与决策对应)。
